A mapper, in this document, is any piece of code whose whole job is: take data in one shape, return the same information in another shape. This system is almost entirely mappers connected by two queues. Understanding it means knowing: what shapes exist, which mapper converts which shape into which, and which program calls each mapper, when.

Color code used everywhere below: programa running process filea file on disk tablea database table mappershape-converting code facta canonical event

2. The two data shapes everything revolves around

2.1 RawEvent — "someone saw these bytes"

Every observation, from any source, becomes this one dataclass before it is stored:

@dataclass(frozen=True)
class RawEvent:
    raw_event_id: RawEventId      # unique name for this observation
    harness: str                  # "claude_code" or "codex"
    source_type: str              # "hook", "transcript", "process", "watch", "terminal", …
    source_name: str
    source_position: str          # how far into the input the source was
    session_id: SessionId
    actor_id: ActorId             # the lead agent, or a subagent
    parent_actor_id: ActorId | None
    observed_at: float
    encoding: str
    payload: bytes                # the EXACT bytes observed, unmodified
    source_identity: str = ""     # which observer produced it (the resume key)
contracts/harness.py:31

The important property: payload is untouched input. A hook's raw event contains the exact stdin the harness wrote; a transcript raw event contains the exact line from the file. Meaning is extracted later, and can be re-extracted, because the original bytes are always still there.

2.2 CanonicalEvent — "this fact happened"

A fact is one meaningful thing that happened in a session, in a vocabulary shared by all harnesses: session.started, message.created, operation.started, session.finished, and about thirty more. Facts are what the dashboard and the terminal panes display.

Each fact has an event_id built deterministically from five parts:

event_id = stable_event_id(harness, session_id, actor_id,
                           subject_type,   # "session", "message", "operation", …
                           subject_id,     # which session / message / operation
                           phase)          # "started", "created", "finished", …

Because the id is computed from what the fact is about and not from who saw it, two different observations of the same happening produce the same id. The store's rule for a second write under an existing id: keep the first stored body, record only "this raw event also saw this fact." So one fact can be seen by a hook and by the transcript file without appearing twice — and whichever observation is translated first decides the stored body. Remember this rule; it explains a deliberate oddity in section 3.4.

2.3 The two queues

The tables are used as queues, by asking "which rows have no follow-up row yet":

  • The translation queue: raw events that have no verdict in translation_records yet. The query that reads it is called untranslated_raw_events — but note what it actually does: 
    SELECT raw_events.* FROM raw_events
LEFT JOIN translation_records USING(raw_event_id)
JOIN session_harness USING(session_id)          -- ★ only REGISTERED sessions
WHERE translation_records.raw_event_id IS NULL
ORDER BY raw_events.id LIMIT 500
    runtime/canonical_store.py:59
    The starred line means: evidence belonging to a session that has no row in session_harness is invisible to translation. It sits in raw_events, untouched, until the session gets registered. This is intentional — it guarantees no facts ever exist for an unknown session, and it means evidence recorded before registration is not lost, just delayed. But nothing in the function's name says any of that.
  • The orphan queue: raw events whose session has no session_harness row at all. The query is unregistered_raw_events (same shape, WHERE session_harness.session_id IS NULL, LIMIT 200). The interpreter reads this queue to discover sessions that no wrapper registered. An event in this state is called an orphan.

3.1 The hook gateways — push evidence in

When a hook process POSTs its stdin to POST /api/harnesses/<name>/hooks, the daemon hands the exact bytes plus a small set of environment variables (only the ones the hook process shipped: its terminal window id, its account variables) to the harness's gateway. The gateway parses the JSON once and returns two things: the raw events to store, and the bytes to send back as the hook's reply.

The Claude gateway (plugins/claude_code/hooks.py) can produce up to four raw events from one delivery, plus a reply:

The Codex gateway (plugins/codex/hooks.py) is the same idea, smaller: always the hook event, plus the terminal event when the window id is present. The reply is always empty.

Notice what the gateway does not do: it does not write the session_harness table, does not translate, does not touch the terminal. It stores bytes and returns. Every gateway output is one of the small builders from 3.9 or the raw stdin itself.

3.2 – 3.4 The file readers — pull evidence in

These mappers all follow one protocol: read(after_position) → RawEvents. The interpreter tells the reader how far it got last time; the reader returns everything after that point. The position is not stored in any separate bookkeeping table — it is read back from the last raw event this reader stored (recorder.position(source_identity) = the source_position of the newest row with this source_identity). A reader may only move forward by storing what it read; therefore its progress marker can never disagree with what was actually stored.

Claude transcript reader — reads the transcript file line by line, at most 100 lines per tick. Each line becomes one raw event; the position is the byte offset where the line starts. The same class also reads each subagent's transcript file (source_type child_transcript or teammate_transcript).

Claude task reader — reads all task JSON files, computes a digest of the whole set, and if the digest changed since last time, emits one raw event per task plus one "membership" event listing the surviving task ids. Position = the digest.

3.5 The Codex process reader

A reader whose "file" is a process. Constructed only when the session row has a process id (which only a wrapper could have provided). Each tick it runs ps to check whether that pid is still a codex process; the moment it is not, it emits one raw event saying the process finished. Position is a latch: once "finished" has been stored, it returns nothing forever.

3.6 The watch reader

Recall from 3.1 that a gateway can store a watch directive: "operation X's output is in file F." The interpreter, when it later processes that directive, inserts a row into the watches table. From then on, every tick, a FileWatchRawEventSource is constructed for each row and reads the file from where it left off, emitting up-to-64KB chunks as raw events (source_type foreground_output). When a finish directive has marked the row, the reader drains the file to the end, deletes the row, and deletes the file if we created it. A watch older than two hours is dropped regardless.

3.10 The row loader

SessionRegistry._session(row) turns a session_harness database row back into a Session object, attaching the harness's plugin. 4. How the mappers get invoked: the three flows

4.1 The push flow — a hook fires

  1. The harness runs the hook script with a JSON description on stdin.
  2. The script boots the daemon if needed, POSTs the exact bytes, ships the few env vars only it can see (KITTY_WINDOW_ID, account vars) in a header. 2-second timeout; any failure is swallowed (a hook must never break the harness) after writing an audit row.
  3. The daemon routes to the harness's gateway, which parses the JSON once and builds the raw events listed in 3.1 plus the reply.
  4. The events are appended to raw_events.
  5. –⑥ The reply travels back as the HTTP response body; the hook script prints it and exits. For a Claude foreground command this reply is what rewrites the command to make its output watchable.

4.3 The wrappers — the complete picture

A wrapper is a small standalone Python program that starts the real CLI as its child process and stays alive next to it until it exits. It exists because a parent process can know four things that no other part of the system can ever observe:

  1. The process id of the CLI — needed later to notice a killed process.
  2. The exact moment of exit, including a crash or a kill -9 — the CLI fires no hook when it dies violently.
  3. The terminal window it runs in — the wrapper runs inside your kitty tab, so its own KITTY_WINDOW_ID environment variable is the session's window. The daemon, running somewhere in the background, has no trustworthy idea of "the current window".
  4. (Claude only) the session id before the CLI even starts — Claude Code accepts a --session-id argument, so the wrapper can invent the id and pass it in.

A wrapper writes to the database directly (it does not go through the daemon): it inserts the session row, and it appends process raw events. It never translates, never creates facts, never builds the daemon's machinery — in that sense it is an evidence writer like the hook path, plus the one extra act of registering.

4.3.2 The Claude wrapper, step by step

plugins/claude_code/command.py — 192 lines; run as: command.py <command-or-account> <claude args…>
  1. Pick the command. The first argument, if it does not start with "-", is the command to run — "claude" or an account alias like c1. Everything after it is passed to the CLI untouched.
  2. Choose the session id. If the arguments contain no resume flag (--resume/-r/--continue/-c) and no explicit --session-id, generate a fresh UUID and append --session-id <uuid>. On resume, Claude decides the id itself and the wrapper will have to discover it from the disk (step 6).
  3. Start the child. The command is run through a login, interactive shell — $SHELL -lic '<command> "$@"' … — because an account alias like c1 only exists inside your shell's configuration; a plain exec would not find it. 
    def launch_argv(arguments, command="claude"):
    shell = os.environ.get("SHELL") or "/bin/zsh"
    return [shell, "-lic", f'{command} "$@"', command, *arguments]
    plugins/claude_code/account.py:60
  4. Ignore Ctrl-C. The wrapper sets its own SIGINT handler to "ignore": when you press Ctrl-C, only the CLI should react; the wrapper must survive to record the exit. (Restored at the end.)
  5. Open the panes immediately, under a temporary id. The real session id may be unknown (resume) or unconfirmed, but the wrapper wants panes on screen now. It reads its own window id, invents pending-<child-pid>, and opens the activity + scoreboard panes labeled with that. Any failure here is written to the audit log and otherwise ignored — panes are cosmetic and must never break a launch.
  6. Poll the disk for the transcript, every 50 ms, while the child is alive. With a forced id it looks for exactly projects/*/<id>.jsonl; on resume it takes the newest .jsonl modified after launch. It searches every transcript root: $CLAUDE_CONFIG_DIR, ~/.claude, and each configured account's own config directory (different accounts keep separate transcript trees).
  7. Register. Build the Session (_session_for — builder ① of 5.2: id from the file name, the transcript path, os.getcwd(), the child pid) and INSERT it into session_harness, unless a row already exists (a resumed session is already registered from its first life).
  8. Adopt the panes — re-label them from pending-<pid> to the real session id and write the temporary→real mapping file (6.3). Failures audited, ignored.
  9. Boot the daemon (ensure_running()) so the interpreter starts pulling the transcript within a tick.
  10. Wait. process.wait() blocks until the CLI exits; the wrapper's own exit code is the CLI's.
  11. Record the death. In the cleanup that runs no matter how the wait ended: if a session was identified, append one process raw event, state finished, payload {"process_id", "state"} — the translator turns it into session.finished (reason process_exited). If no session was ever identified (the CLI died before its transcript appeared), close the temporary panes instead. Either way, delete the temporary-id mapping file.

Note what the Claude wrapper does not record: no process started event. Its launch leaves no evidence in raw_events at all — only the session row. (The translator would ignore a Claude started event anyway; see the box in 3.7.)

4.3.3 The Codex wrapper, step by step

plugins/codex/command.py — 164 lines; run as: command.py <codex args…>

Codex accepts no session-id argument and buries its real process one level deep, so the Codex wrapper must discover everything the Claude wrapper could dictate:

  1. Start the child: codex found on PATH, run directly (no shell, no accounts). SIGINT ignored, same reason as Claude.
  2. Find the real codex process. The started child may be a launcher whose own child is the actual codex binary. Poll: list the child's children (pgrep), keep the one whose command name is codex (ps). Refuse (crash) if there are several.
  3. Open the panes under pending-<native-codex-pid>, anchored at the wrapper's own window. Unlike Claude, a pane failure here raises — the wrapper process dies, while the codex CLI keeps running, now effectively unwrapped: no registration, no process events; its hooks will register it later via the orphan scan. (The two wrappers genuinely disagree on this; see the comparison table.)
  4. Find the rollout. Poll: ask the operating system which files the codex process holds open (lsof -p <pid>); for each open .jsonl, call rollout_session(path) (builder ③ of 5.2) — it reads the file's first line and returns a Session only for a lead rollout. Refuse if the process holds several distinct lead rollouts.
  5. Register and record the birth. Attach the pid to the Session, then record_process(…, "started"), which does three things in a row: INSERT the session row if absent; append a process raw event, state started, payload {"process_id", "rollout_path", "state", "working_directory"}; boot the daemon.
  6. Adopt the panes (temporary id → real id). Again: failure raises.
  7. Wait for the child, then record the death: record_process(…, "finished"). If no session was ever found, close the temporary panes. Clear the mapping file.

Because the row has a pid, the interpreter also builds the process reader (3.5) for this session every tick — a second, independent way to notice the death, in case the wrapper itself was killed.

6. The session lifecycle, birth to death

6.1 Birth

A session exists, as far as this system is concerned, the moment its row lands in session_harness. Two birth paths:

  • Wrapped: the wrapper registers it during launch (R1/R2), usually before any evidence has been processed. The row has a pid.
  • Unwrapped: the first hook's evidence is stored (push flow), sits in the orphan queue, and on the next tick the orphan scan registers it (R3). The row has no pid. Until that moment the session's evidence is invisible to translation (the ★ filter) — nothing is lost, everything waits.

6.2 Life

Once registered and not finished, the session is watchable: step 1 of every tick builds its readers and pulls its files. Facts accumulate: session.started (from the SessionStart hook, or the rollout's first line), messages, operations, live command output through watches, task changes, subagent activity, usage. The dashboard and the terminal panes are read-only views over these facts.

6.3 Panes — how the session gets its terminal display

Definitions first. kitty is the terminal application. A kitty tab can be split into several rectangular areas; kitty calls each one a window, and each has a numeric id. baqylau opens two extra windows next to a session's CLI — the activity pane and the scoreboard pane — and labels windows with the session id so it can find them again. The window the panes are opened next to is called the anchor.

  • Wrapped: the wrapper runs inside your tab, so it knows the anchor (its own KITTY_WINDOW_ID). It opens the panes immediately — but the real session id may not be known yet, so it labels them with the temporary id pending-<pid>. When the real id is discovered (step 5/6 of the wrapper flow), it re-labels the panes with the real id and writes a small file mapping temporary → real, so any display code still holding the temporary id can look up the real one. The code calls this re-labeling "adopting" the panes.
  • Unwrapped: no one is inside the tab at launch. Instead, every hook delivery records the terminal event from 3.1 ("this session's hooks run in window N"). When the interpreter commits session.started, its react step opens the panes anchored at that recorded window. The daemon never consults its own idea of a "current window" — it has none worth trusting; it uses only what a hook observed from inside the session's tab.

6.4 Death

A session is finished when a session.finished fact is committed. Every producer of that fact, per harness:

The session leaves the watchable set; its files are never read again. Late-arriving evidence (a straggler hook) still gets translated — the session is registered — but nothing is pulled anymore.

7. The problems

Everything below uses only the vocabulary introduced above.

P1 — One session, three independent constructions

Builders ①, ② and ③ of section 5.2 each encode, in their own code, how to turn a transcript/rollout path into a session: id from the file name, lead actor is <id>:lead, make the path absolute, pick up the working directory. For Claude this knowledge is written twice (wrapper and evidence mapper) and its identity-extraction half a third time (the gateway). A change to what a Session is — a new field, a changed rule — must be found and repeated in each place by hand. Nothing connects them; nothing fails if one is updated and another is not.

P2 — The same bytes are parsed three times by three mappers

One Claude hook delivery is JSON-parsed by: the gateway (3.1, to stamp the raw event), the translator (3.7, to make facts), and — if the session is unwrapped — the session-evidence mapper (3.8, to build the Session). Three parsers of identical bytes, maintained separately, able to drift apart separately. The evidence mapper and the translator in particular answer overlapping questions ("what session is this? what directory?") with independent code.

P3 — The sessions table has three writers

R1, R2, R3 (section 5.3). Two of them run in wrapper processes outside the daemon, one inside the interpreter. To answer "where do sessions come from?" you must know all three, plus their launch-path coverage (which command goes through a wrapper and which does not), plus the race between them. Every other table in the store has exactly one writer.

P4 — The orphan scan re-reads forever and can jam

Step 0 of every tick reads the orphan queue: oldest 200 orphan rows, every 0.25 seconds. An orphan that will never name a session — for example a Codex hook pointing at a subagent rollout, which the evidence mapper deliberately refuses — is re-fetched and re-refused four times a second for the rest of the database's life. Worse: the query is "oldest first, LIMIT 200". If 200 permanently refusable orphans ever accumulate, they occupy the whole batch forever, and a brand-new unwrapped session's evidence never gets scanned — it is behind them in line. The jam would be silent: no error, just a session that never appears.

P5 — Names that hide what things do

  • untranslated_raw_events — actually returns "untranslated raw events of registered sessions". The ★ filter, the single most surprising behaviour in the collection path, is invisible in the name. (It cost this very analysis a wrong design: a plan built on "translation sees everything" would deadlock unwrapped sessions.)
  • session_harness — the table is the list of sessions. The name suggests some session-to-harness mapping detail rather than "the sessions table".
  • HarnessSessionEvidence — the name does not say "builds a Session from an orphan raw event". You must read it to learn it is a constructor.
  • source_position — means "byte where the line starts" for transcripts/rollouts, "byte after the chunk" for watches, a digest for tasks, a state word for process events. Four meanings, one column, distinguishable only by reading each reader.

P6 — Two wrappers, one design, written twice

Both wrapper programs do: start child → open temporary panes → discover identity → register → re-label panes → wait → record exit. Around 190 lines each, structurally identical, maintained as two unrelated files. They have already drifted (P7). A fix to one (say, the pane-failure handling) does not reach the other.

P7 — The wrappers disagree about process events, so Claude cannot be registered from evidence it produces

The Codex wrapper stores process started and finished, and the started payload describes the session (rollout path, working directory, pid). The Claude wrapper stores only finished, whose payload is {"process_id", "state"} — from which nothing about the session can be reconstructed. Consequence: for a wrapped Claude launch there exists no stored evidence that could ever identify the session until the first hook arrives; the wrapper therefore must write the sessions table directly (R1). The direct write is not a design choice — it is forced by the missing evidence.

P8 — Payload contents are accidental, not designed

Why does the Codex process payload contain the rollout path? Not because anything specifies "a process event must describe its session" — but because process_event(session, state) happened to receive a Session object and copied some fields in (3.9). The Claude counterpart, written separately, copied nothing. There is no stated rule for what any payload must contain, so: if Session gains a new field tomorrow, someone must remember to add it to process_event, to the Claude builder, to both gateways' extraction, to both evidence mappers — and nothing will fail loudly where they forget. The information each mapper can produce is whatever its author happened to have in scope on the day it was written.

P9 — Insert-once plus racing writers means fields can be lost forever

Registration keeps whichever writer ran first (5.3) and the row can never be completed afterwards (5.1). For a wrapped Claude launch, the wrapper's registration and the first hook's arrival race; the wrapper usually wins, but nothing guarantees it. If the orphan scan ever won, the row would be born without a pid — permanently. For Codex the stake is concrete: the process reader (3.5), the only finish signal a killed Codex session has, is constructed only if the row has a pid.

P10 — Two unrelated code paths produce the same panes

Wrapped sessions get panes via temporary ids and re-labeling, driven by the wrapper (6.3). Unwrapped sessions get panes via recorded terminal events and the react step, driven by the interpreter. Same result, two mechanisms, both must keep working, each with its own failure modes (a temporary pane that was never re-labeled; a session whose hooks all arrived before kitty set the env var).

P11 — Sessions without a wrapper can never finish (Codex), or finish only politely (Claude)

From the table in 6.4: an unwrapped Codex session has zero finish producers — no wrapper to record the exit, no pid for the process reader. It remains "watchable" forever: its rollout is re-checked every tick until the end of time (cheap per tick, but unbounded accumulation). An unwrapped Claude session finishes only if the SessionEnd hook is actually delivered — a kill, a crash, or a dead daemon at that moment leaves it immortal too.

P12 — The registration filter and the orphan scan must be understood together, and nothing says so

The ★ filter (2.3) and the orphan scan (step 0) are two halves of one invariant: "facts only for known sessions; early evidence waits, then is recovered." The halves live in different files (runtime/canonical_store.py, app/interpreter.py), under names that reveal neither the filter (P5) nor the pairing. Changing either half without the other silently breaks unwrapped sessions — which is exactly the trap the first redesign draft in this conversation walked into.

8. The proposed design: one flow

This section is the design to approve or reject. It uses only the vocabulary of sections 1–7; the few new names it introduces are defined where they first appear. The design follows from four decisions already made:

  1. Launching is just running the CLI. No wrapper program exists. The dashboard's launch button opens a kitty tab running claude/codex directly — exactly what typing it in a terminal does. One kind of session, not two.
  2. Every session is born the same way: from its own hook evidence, by the interpreter. One registration path, not three.
  3. The session row carries where the session lives — its terminal window and its process id — and those two columns are kept current from later evidence, because a resumed session shows up in a new window with a new process.
  4. Nothing "ensures" anything. A hook fires its delivery at the daemon; if the daemon is not there, the delivery fails, is audited, and is gone. Nobody boots anybody as a side effect. You start the daemon; that is the only way it starts.

8.2 The queue — and the honest answer to "can we delete it?"

No — and the reason is not crashes or restarts. Strip all of that away and the need remains: evidence is produced by several concurrent writers — the daemon's HTTP threads (one per hook delivery, at any moment), the tick's file readers, and the otel receiver, which is a separate process writing straight into raw_events. Interpretation is one thread that wakes four times a second and must ask: "what arrived that I have not looked at, in what order?" The writers and the reader meet nowhere except the database — so the question must be answerable from the database, and this query is that answer:

def unverdicted_raw_events(self, limit: int) -> tuple[RawEvent, ...]:
    # renamed from untranslated_raw_events; the registration filter is REMOVED —
    # the name is finally the whole truth: every raw event without a verdict, in order.
    with connect(self.database_path) as connection:
        rows = connection.execute(
            "SELECT raw_events.* FROM raw_events "
            "LEFT JOIN translation_records USING(raw_event_id) "
            "WHERE translation_records.raw_event_id IS NULL "
            "ORDER BY raw_events.id LIMIT ?",
            (limit,),
        ).fetchall()
    return tuple(self._raw_event(row) for row in rows)

Deleting it would mean an in-memory work queue plus routing every producer through it — including re-architecting the otel receiver into an HTTP client — to end up with more machinery and a second structure that can disagree with the tables. "No verdict yet" cannot disagree with anything, because writing the verdict is the act of leaving the queue. That it also survives restarts is a side effect, not the purpose. Recommendation: keep, renamed.

8.4 The point of the whole refactoring: the fact comes first, the session second

Asked directly: can a session.started fact be produced when no Session object exists anywhere? Yes — that is the designed normal case, not an edge. The law of the new design: a Session is a read-model derived from facts. Nothing upstream of the store — gateways, the queue, translators, the commit — ever requires one. Here is the full timeline of the case this whole refactoring exists for, the bare terminal launch:

  1. You type c1 'fix the tests'. No wrapper runs. No row exists. Nothing anywhere knows a session began.
  2. The CLI starts and fires its SessionStart hook. The hook process reads stdin, collects its four flat header values, POSTs a HarnessHookRequest. Still no session anywhere.
  3. The gateway's handle() parses the payload once and returns a HarnessHookResponse; the hook raw event — window and pid stamped on the row — is appended to raw_events. The gateway did not look up, create, or need any session.
  4. Within 0.25 s the tick's queue hands the raw event to the Claude translator. Translation is a pure function of the raw event — it needs no Session object, which is precisely why this works. Out come session.started (carrying working_directory and source_reference) and actor.started, each stamped with the envelope's window and pid.
  5. The store commits them. At this instant, facts exist for a session that does not. The old design forbade this (the ★ filter) and needed the orphan scan to break the resulting deadlock; the new design embraces it — the fact is the announcement.
  6. The reaction pipeline runs. SessionUpsertCanonicalEventReaction sees session.started and performs the first and only creation of the Session: identity from the fact's payload, location from the fact's envelope, one save(). The session now exists because the fact did. In the same pass, PaneCanonicalEventReaction opens the panes at the row's window, and ClaudeOtelCanonicalEventReaction starts the telemetry receiver.
  7. Next tick, watchable() includes the new row; the pull readers are built from its source_reference and read the transcript from byte 0 — the prompt you typed in step 1 is backfilled even though it happened before the session existed.

What legitimately does require a Session — the pull readers, the controls, the panes — all sits downstream of the reaction that creates it, so the dependency can never run backwards. And the dashboard launch is now the same story with a different step 1: it opens a kitty tab running the CLI, then waits to be told, through facts, like everybody else.

Reaction 2 — OperationOutputCanonicalEventReaction: command output

Clearing the confusion first: nothing here fires "every time output is produced." Output chunks never pass through reactions at all — they are evidence, read from the file by the collect phase and translated into operation.progressed facts. This reaction handles exactly three one-time moments in an operation's life: its output file becomes known (start following), the operation finishes (stop following), the session finishes (stop everything). How the file becomes known, per command kind:

  • Foreground command: at PreToolUse, the gateway rewrites the command (via the synchronous reply) so a copy of its output also lands in a file the gateway creates, and records an output-location directive — a raw event carrying the path and the file's observed state. The gateway must do this, not the translator: only the delivery moment can rewrite the command and observe the file before it grows. The directive translates (8.3) into operation.output_located with until="operation_finished"; the reaction starts following. When the same operation's operation.finished commits (from the PostToolUse delivery), the reaction marks it done — the reader drains the file to its end and the row and tee file are removed.
  • Background command: the harness writes the output file itself; its path only becomes known at PostToolUse (found by the task id). Same directive, same fact, but until="session_finished" — because a background command's launch reports "finished" immediately while output keeps flowing, so operation.finished must be ignored for it; the session's end is its end.
class OperationOutputCanonicalEventReaction(CanonicalEventReaction):
    def __init__(self, operation_output: OperationOutputStore,
                 recorder: RawEventRecorder) -> None:
        self.operation_output = operation_output
        self.recorder = recorder

    def react(self, canonical_event: CanonicalEvent) -> None:
        payload = canonical_event.payload
        if isinstance(payload, OperationOutputLocated):
            self.operation_output.save(canonical_event.session_id, canonical_event.harness,
                                       canonical_event.actor_id,
                                       canonical_event.parent_actor_id, payload)
        elif isinstance(payload, OperationFinished):
            # ends foreground followings only (until="operation_finished");
            # affects zero rows for operations that never had an output file
            self.operation_output.finish(canonical_event.session_id,
                                         str(payload.operation_id))
        elif isinstance(payload, SessionFinished):
            self._drain_all(canonical_event.session_id)

    def _drain_all(self, session_id: SessionId) -> None:
        # a finished session leaves watchable(): read each remaining file to its
        # end and remove the row (and the tee file, when we created it)
        for source in self.operation_output.for_session(session_id):
            raw_events = source.read(self.recorder.position(source.source_identity))
            if raw_events:
                self.recorder.record(raw_events)
            self.operation_output.remove(session_id, source.operation_id,
                                         source.delete_source, source.source_path)

TICK_INTERVAL_SECONDS = 0.25
TRANSLATION_BATCH_SIZE = 500

class Interpreter:
    def __init__(self, sessions: SessionStore, harnesses: HarnessRegistry,
                 recorder: RawEventRecorder, operation_output: OperationOutputStore,
                 canonical_store: CanonicalEventStore,
                 core_translators: Mapping[str, CoreTranslator],
                 reactions: tuple[CanonicalEventReaction, ...],
                 controls: HarnessControlService) -> None:
        self.sessions = sessions
        self.harnesses = harnesses
        self.recorder = recorder
        self.operation_output = operation_output
        self.canonical_store = canonical_store
        self.core_translators = core_translators
        self.reactions = reactions
        self.controls = controls              # handed to harness reactors per call

    def run(self, stop_event: threading.Event) -> None:
        while not stop_event.is_set():
            try:
                self.tick()
            except Exception:
                _audit_failure("tick", {})     # the loop must outlive anything below
            stop_event.wait(TICK_INTERVAL_SECONDS)

    def tick(self) -> None:
        self._pull()
        self._translate()

    # ── pull: the outside world → recorded evidence ─────────────────────────

    def _pull(self) -> None:
        for session in self.sessions.watchable():
            try:
                sources = (
                    *session.plugin.sources.for_session(session),
                    *self.operation_output.for_session(session.session_id),
                    SessionLivenessSource(session),   # ALWAYS built — no silent skip:
                )                                     # a pid-less session raises, loudly
            except Exception:
                _audit_failure("source construction",
                               {"session_id": str(session.session_id)})
                continue
            for source in sources:
                self._pull_source(session, source)

    def _pull_source(self, session: Session, source: HarnessRawEventSource) -> None:
        try:
            raw_events = source.read(self.recorder.position(source.source_identity))
            if raw_events:
                self.recorder.record(raw_events)
        except Exception:
            _audit_failure("source read", {"session_id": str(session.session_id),
                                           "source": type(source).__name__})

    # ── translate: meaning decided, stored once, reacted to ─────────────────

    def _translate(self) -> None:
        for raw_event in self.canonical_store.unverdicted_raw_events(TRANSLATION_BATCH_SIZE):
            self._translate_one(raw_event)

    def _translate_one(self, raw_event: RawEvent) -> None:
        plugin = self.harnesses.plugin(raw_event.harness)
        translator = self.core_translators.get(raw_event.source_type, plugin.translator)
        try:
            translation = translator.translate(raw_event)
        except Exception as error:
            # any translator problem is a decision, not a crash: the queue moves on
            translation = TranslationResult((), "translation_failed",
                                            f"{type(error).__name__}: {error}")
        canonical_events = self.canonical_store.store_translation(   # the ONE store call;
            raw_event, plugin.info.plugin_version, translation)      # returns plain CanonicalEvents
        for reaction in self.reactions:          # reaction-outer, events-inner: each reaction
            for canonical_event in canonical_events:   # finishes the batch before the next starts
                try:
                    reaction.react(canonical_event)
                except Exception:
                    _audit_failure(type(reaction).__name__,
                                   {"event_id": str(canonical_event.event_id)})
        for reactor in plugin.reactors:          # then the harness's own reactors — dispatched
            for canonical_event in canonical_events:   # by the event's harness, controls per call
                try:
                    reactor.react(canonical_event, self.controls)
                except Exception:
                    _audit_failure(type(reactor).__name__,
                                   {"event_id": str(canonical_event.event_id)})

class SessionLivenessSource(HarnessRawEventSource):
    """Built by the interpreter for every unfinished session. Emits ONE raw event
    when the CLI process is gone. Replaces CodexProcessRawEventSource and both
    wrappers' exit recording."""
    def __init__(self, session: Session) -> None:
        if session.harness_process_id is None:
            # per your call: never swallowed. The failure lands in the
            # source-construction audit every tick until the pid arrives.
            raise ValueError(f"session has no harness process id: {session.session_id}")
        self.session = session
        self.source_identity = (f"{session.plugin.info.name}:liveness:"
                                f"{session.session_id}:{session.harness_process_id}")

    def read(self, after_position: str | None) -> tuple[RawEvent, ...]:
        if after_position == "exited":
            return ()                          # the latch: the exit was already recorded
        if process_alive(self.session.harness_process_id,
                         self.session.plugin.info.cli_process_name):
            return ()
        return (RawEvent(
            raw_event_id=RawEventId(self.source_identity),
            harness=self.session.plugin.info.name,
            source_type=LIVENESS_SOURCE_TYPE,
            source_name=f"process:{self.session.harness_process_id}",
            source_position="exited",
            session_id=self.session.session_id,
            actor_id=self.session.lead_actor_id,
            parent_actor_id=None,
            observed_at=time.time(),
            encoding="json",
            payload=json.dumps({"process_id": self.session.harness_process_id,
                                "state": "exited"}).encode("utf-8"),
            source_identity=self.source_identity),)

def process_alive(process_id: int, cli_process_name: str) -> bool:
    # alive AND still the harness CLI — pids get reused by the OS, which is
    # the only reason HarnessInfo.cli_process_name exists
    completed = subprocess.run(["ps", "-o", "comm=", "-p", str(process_id)],
                               capture_output=True, text=True, timeout=2)
    return (completed.returncode == 0
            and os.path.basename(completed.stdout.strip()) == cli_process_name)

class SessionStore:

            connection.execute("BEGIN IMMEDIATE")
            connection.execute(

                "  session_id, lead_actor_id, harness, harness_session_id,"
                "  source_reference, working_directory,"
                "  terminal_window_id, harness_process_id, created_at"
                ") VALUES(?, ?, ?, ?, ?, ?, ?, ?, ?) "
                "ON CONFLICT(session_id) DO UPDATE SET "
                "  terminal_window_id = excluded.terminal_window_id,"
                "  harness_process_id = excluded.harness_process_id",

                 session.harness_session_id, session.source_reference,
                 session.working_directory, session.terminal_window_id,
                 session.harness_process_id, time.time()))

        with connect(self.database_path) as connection:
            row = connection.execute("SELECT * FROM sessions WHERE session_id=?",
                                     (str(session_id),)).fetchone()
        return self._session(row) if row is not None else None

    def watchable(self) -> tuple[Session, ...]:
        with connect(self.database_path) as connection:
            rows = connection.execute(
                "SELECT sessions.* FROM sessions "
                "WHERE NOT EXISTS ("
                "  SELECT 1 FROM canonical_events "
                "  WHERE canonical_events.session_id = sessions.session_id "
                "  AND canonical_events.event_type = 'session.finished'"
                ") ORDER BY ("
                "  SELECT MAX(raw_events.observed_at) FROM raw_events "
                "  WHERE raw_events.session_id = sessions.session_id"
                ") DESC, sessions.created_at DESC").fetchall()
        return tuple(self._session(row) for row in rows)

            terminal_window_id=row["terminal_window_id"],
            harness_process_id=row["harness_process_id"])
        if self.harnesses is None:
            return session
        return replace(session, plugin=self.harnesses.plugin(row["harness"]))
