# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**baqylau** (Kazakh *бақылау*, "observation"; formerly *claude-kitty*) — a kitty-terminal integration for Claude Code, built entirely out of Claude Code **hooks** plus detached background processes. Three user-facing features:

1. **Tab colors** (`claude-tab-status.py`) — the kitty tab color reflects the session state (grey idle · magenta busy · blue running/awaiting · red asking-you · green your-turn) via `kitten @ set-tab-color` over the socket in `$KITTY_LISTEN_ON`.
2. **Command mirror pane** (`claude-split.py` + `claude-mirror.py`) — a right-side vertical split showing every command, file op, subagent, teammate, monitor, and codex run as colored streaming blocks — fg/bg command blocks carry clickable ` ⧉cmd ⧉out` copy links, and Read/Update/Write one-liners click-to-EXPAND their content in place — highlighted code for Read/Write, a line-numbered soft-red/green diff for Update; second click collapses (both via OSC 8 hyperlinks → `claude-copy.py` via `~/.config/kitty/open-actions.conf`, docs/wiring.md / docs/click-to-view.md) — plus a 5-row scoreboard window (`claude-scorebar.py`) underneath (session id · ✉ message census · ▪ activity (cmds + time) · Σ token breakdown + cost · files + ± line-diff + tools).
3. **Audit trail** (`core/audit.py` — the always-on WRITE path every hook imports; `core/auditcli.py` — the read/report tier behind the CLI `bin/claude-audit.py`, imported by nothing else) — always-on SQLite recording of every hook event, tab transition, slot claim, stream lifecycle, paint op, and swallowed exception, at `~/.claude/baqylau-audit/audit.db`.
4. **Web dashboard** (`dashboard/` + `bin/claude-dashboard.py`, docs/dashboard.md) — a localhost web UI (127.0.0.1:8377, `CLAUDE_DASH_PORT` overrides) over EVERY session, live and parked: the mirror stream rendered to HTML (`dashboard/opshtml/` — a package split by concern: ansi/ops/markdown/tools; html-escape is the `neutralize()` analog; ⧉ copy / click-to-view work via the same `core/copy.collect` + kv stashes; MAIN-AGENT-ONLY, unlike the terminal mirror: agent/teammate/secondary-codex ops carry a producer-source stamp — `core/ops.py` `src`, ambient per-process `set_src`/`$CLAUDE_OPS_SRC` — and `op_items` drops them, EXCEPT a subagent's `⇢ prompt` + `⇠ result` blocks, which the substream stamps `web=1` to surface in the main mirror alongside the lead's launch header; the rest of the agent's detail lives in that agent's own scope), AGENT SCOPE — clicking a subagent/teammate re-points the WHOLE session view at it (`#/s/<sid>/a/<aid>/<tab>`, a real route): mirror, monitors and jobs filter to that agent via `?agent=` while memory/errors stay session-wide, and outside scope the session view is the LEAD's own work (its ops, its jobs, its monitors, badge counts included). The scoped mirror is the SAME pipeline with the `src` filter inverted (`opshtml.in_scope` — the one predicate `op_items` and `_cut_blocks` share; `read/mirror.agent_scope` resolves a codex run's `codex:<label>` stamp), not a second read model — the agent's PROSE ops are dropped in exchange (`actclass.prose_block`) and its conversation comes from its own transcript through the same merge, MAIL IN BOTH DIRECTIONS included: an outgoing `SendMessage` is a `sendmsg` conversation record (`transcript.mail_send` owns that payload shape; `conversation_for` asks for it only on an AGENT read, since `mail_fmt.py`'s unstamped rows already carry the LEAD's — and every teammate's — sends), so the web shows the WHOLE message where the op carries a 12-line excerpt, and `actclass.as_lead` normalises every remaining block into the lead's vocabulary — including a generic `· <tool>` call, which joins the quiet `⏺` register and gets its own `ACT_TOOL` class rather than folding into "ran 1 teammate" — which is what let the old drill-down TIMELINE go entirely (`plugins.activity`/`activity_since`, `transcript.timeline`, `codex/rollout.timeline`, `/api/session/<sid>/agent/<aid>`, `/events/agent/...`, `/activity` are all deleted; only `plugins.agent_usage` survives, folding one agent's tokens for the scoreboard swap). Internal dep direction: config ← read/control/notify ← http. Patchable knobs / cross-module helpers the handlers call are read MODULE-QUALIFIED (`config.X`/`launch.X`/`presence.X`) so a test patches the one owning module. There is no build system or package manifest. Scripts are invoked directly by hooks wired in `~/.claude/settings.json` (the hook table is in docs/wiring.md — the settings file itself is *not* in this repo). Python scripts target the system `python3`; only `pygments` is an (optional, probed-for) runtime dependency. The e2e test suite lives in `tests/` (`make test`, dev-only deps in `requirements-dev.txt` — see docs/testing.md); it drives the real hook scripts as subprocesses against per-test temp dirs and a fake `kitten` recorder.

**Layout (core / plugins / frontends — docs/architecture.md).** `core/` is the tool- and terminal-agnostic runtime; `plugins/<tool>/` adapts one agent tool each (`claude_code` — a host; `codex` — a secondary source inside a Claude session AND a standalone host on its own, via codex's native SessionStart hook → `claude-codex-session.py`), registered in `plugins/__init__.py` (`all_plugins` / `on_session_start` / `census` / `agent_usage` — the last folds ONE agent's tokens for the web scoreboard, docs/sessionapi.md); both hosts drive the shared `core/hostpane.py` pane lifecycle; a third plugin `plugins/otel/` is NOT an agent tool but a cross-cutting subsystem — a per-machine singleton OpenTelemetry OTLP receiver (`claude-otlp-receiver.py`, spawned at SessionStart when `CLAUDE_CODE_ENABLE_TELEMETRY=1`) that is the AUTHORITATIVE source of the scoreboard's token/cost counters (it captures Claude Code's hidden `auxiliary` agents that transcript-folding never could; the transcript fold survives only as a SessionEnd fallback). Raw datapoints land in the audit `otel` table; `frontends/` adapts one terminal each behind the `Frontend` interface (`frontends.get()`; kitty is the only implementation, `$CLAUDE_FRONTEND` overrides). Dependency rule: core imports only core; frontends at most core; plugins import core + frontends, never each other; `dashboard/` (the web-dashboard consumer tier, docs/dashboard.md) sits above all — it imports core + the plugins registry root + frontends (the last for its control plane: the write endpoints reach the terminal through `frontends.get()`), and nothing imports it back except its bin/ entry and tests. "The plugins registry root" has a written-down exception list — five modules reach `plugins/claude_code/` directly (the opshtml presenter's file-op tables, the memory tab, the take-back stash), enforced both ways by `DASHBOARD_PLUGIN_REACHES` in tests/test_l1_contracts.py: a new reach fails until it is routed through a provider or argued into the list, and a stale row fails too (docs/styleguide.md *Layering*). The `bin/` directory holds EVERY executable entry point (`bin/claude-*.py` — hook entries, renderers, streamers, the audit CLI `bin/claude-audit.py`, plus `bin/retarget-python.py`); their FILENAMES are load-bearing (they name the audit's handler/script vocabulary) — never rename an entry (moving is fine, the vocabulary is the basename); put implementation in the packages, and spawn siblings via `core/paths.py`'s `BIN`, never a re-derived path. **Naming convention (deliberate, not drift):** hyphenated `claude-*.py` = executable entry, un-importable by design; underscored `*.py` inside `core/`/`plugins/`/`frontends/` = importable module. The repo root contains no Python files. **All hook events are wired (in `~/.claude/settings.json`, outside the repo) to ONE dispatcher entry, `claude-hook.py` → `plugins/claude_code/dispatch.py`** — except `WorktreeCreate`/`WorktreeRemove`, which must stay UNWIRED (delegating hooks: registering one overrides Claude Code's native worktree creation and must print the worktree path; the dispatcher's silent exit-0 broke `EnterWorktree` — docs/wiring.md), which reads the payload once and fans out IN-PROCESS to the tab dispatch, the matcher-selected formatter, and the universal audit subscriber (matcher routing lives in `dispatch.py`'s `_plan()`; docs/wiring.md). Because every subsystem runs under argv[0]=`claude-hook.py`, the dispatcher stamps `audit.set_handler("claude-<x>.py")` around each call so `hook_events.handler`/`errors.script` keep their per-entry vocabulary (argv[0] is no longer the sole source — an explicit override is). The per-script entry shims (`bin/claude-cmd-fmt.py` …) still exist and still run standalone (the e2e tests drive them directly). The historical root-level compat shims (`claude_state.py`, `claude_ops.py`, …) are DELETED — import the package modules directly (`core.state`, `core.ops`, `plugins.claude_code.hookkit`, …).

To debug a reported session bug, prefer the **`audit-debug` skill** (`.claude/skills/audit-debug/SKILL.md`) — it walks the triage order (anomalies → errors → timeline → targeted SQL) and documents the full audit schema.

Script edits take effect immediately (hooks re-exec them). Only `kitty.conf` changes (e.g. `listen_on`) need a full kitty restart, and a renderer/interpreter change needs a mirror toggle off/on.

**The web dashboard is the ONE exception — it does NOT hot-reload.** It is a long-running singleton server process (`bin/claude-dashboard.py serve`) started from the MAIN checkout, so a dashboard change is invisible until BOTH happen: the new code is on disk in the main checkout (merged to `main` and the checkout fast-forwarded — not just pushed to `origin/main` from a worktree) AND the server is restarted. Concretely:
- **Backend** (`dashboard/*.py`, or any `core`/`plugins`/`frontends` module the server imports): the code is loaded into the live process's memory — it keeps running the OLD code until `./bin/claude-dashboard.py stop && ./bin/claude-dashboard.py start` (verify with `status`; confirm with `curl -s http://127.0.0.1:8377/api/...`).
- **Frontend** (`dashboard/static/app.NN-*.js` / `style.css` / `index.html`): served as static files, so a restart serves fresh bytes — but the BROWSER caches the old ones. The restart bumps the server's `BOOT_ID`, so an open page's SSE reconnect toasts "dashboard updated — refresh"; the user must hard-reload (Cmd+Shift+R) to pick up new JS/CSS.
So: after ANY dashboard front- or back-end change, restarting the dashboard is part of finishing the work (see the worktree-merge section below), and the user is told to hard-reload the browser.

## Architecture

**Producer/renderer split via paint ops.** Hook handlers and tailers never print to the pane. They append width-INDEPENDENT **paint ops** (`rule`/`label`/`code`/`gut`/`line`, built by `core/ops.py`) as rows of the per-session state DB's `ops` table (`/tmp/claude-mirror-<session_id>.log.state.db` — the `.log` path is only the KEY everything derives from; no log file exists). The single renderer `claude-mirror.py`, running inside the pane, polls new rows by id, paints ops at the live pane width and re-renders everything on SIGWINCH so content reflows. Consequence: anything width-dependent (wrapping, gutters, dividers) belongs in the renderer; anything width-independent (syntax highlighting, one-liner reflow) runs once at op creation.

**Process model.** ~20 short-lived hook processes plus detached long-lived tailers/watchers, coordinating through SQLite: a per-session state DB (`core/state.py` — ops, scoreboard, slots, hand-offs; the live DB is in `/tmp` but at SessionEnd it is MOVED to the durable park `~/.claude/baqylau-mirror-history/` — `core/paths.py` `HISTORY_DIR`/`parked_db` — and restored on resume, so a resumed session replays its mirror history even across a machine reboot that wipes `/tmp`), a global window-keyed tab DB (`/tmp/claude-kitty-tab.db` — tab colour + watcher pid locks), and `~/.claude/kitty-mirror.db` (remembered pane sizes). The only plain files left are what physics demands: the fg tee'd `.out` streams + `.done` sentinels (written by the rewritten command itself). Everything is Python; `claude-tab-status.py` reads the state/tab DBs read-only (`mode=ro`, so a probe can never create a DB whose existence is a liveness signal):
- `claude-cmd-pre.py` (PreToolUse Bash) rewrites foreground commands via `updatedInput` to tee output into a side file so it streams live; `claude-cmd-fmt.py` (PostToolUse) hands the real outcome to the tailer via a take-once hand-off record in the state DB. A **subagent's** foreground command is teed the same way (keyed by `tool_use_id`), but `claude-substream.py` spawns its tailer and hands off the outcome; gated by `CLAUDE_MIRROR_LIVE_FG_SUB`.
- `claude-stream.py` tails background/monitor/fg output files; `claude-substream.py` tails a subagent/teammate transcript (`subagents/agent-<id>.jsonl`) — the only in-order source of its prompt/messages/tools/result; `claude-codex-watch.py` (one per session) discovers every codex run from two global directories and spawns `claude-codex-stream.py` per run.
- Detached processes are spawned with `start_new_session=True` — spawning from a hook with bash `&` leaves them in the hook's process group, which Claude Code waits to drain (this hung SessionStart once; see `claude-codex-launch.py`).

**Slot rows** (`core/slots.py`, the state DB's `live` table) do double duty: they assign each concurrent stream a palette color (5-color palettes per kind: bg/monitor/subagent/teammate/codex) AND they are the tab tracker's liveness signal — `claude-tab-status.py stop` keeps the tab blue exactly while a live-pid row (kind `bg`/`monitor`/`fg`/`sub.pid`) exists. Rows store the owner pid and are liveness-checked (`core.state.pid_alive` — the ONE probe, where EPERM = exists-but-foreign-owned = alive) before being trusted; stale ones are stolen.

## Hard-won invariants (violating these reintroduces fixed bugs)

- **Hooks must never block or fail.** Every hook path exits 0 and swallows exceptions — but every swallow site must record to the audit first (the audit `errors` table). The tab-color path writes audit rows fire-and-forget.
- **Claude Code fires NO hook on cancel/interrupt** — no Stop, nothing. Every cancellation path needs its own recovery signal: writer-liveness for commands, `meta.json` `stoppedByUser` for a killed/cancelled subagent, the **parent transcript's `tool_result`** (keyed by the agent's `meta.json` `toolUseId`) for a *rejected/abandoned* Task — which fires neither `SubagentStop` nor `stoppedByUser` — a **`StopFailure` carrying the subagent's `agent_id`** for a subagent turn that *died on an API error* (e.g. 529 — fires no `SubagentStop`; `claude-stop-fmt.py` hands it to `subagent_fmt.finalize`, the same finaliser `SubagentStop` uses; async agents can't be recovered via the parent `tool_result` because its only entry is the "launched successfully" ack), and the transcript's `[Request interrupted by user]` RECORD for plain replies (`interrupt-watch` — which must (a) match that marker as a RECORD, never as raw bytes: it has to be the content of a `type:"user"` record, because growth that merely QUOTES the marker — a `nested_memory` attachment injecting THIS file, which documents it; a Read of `tabstatus.py`; a grep hit in a `tool_result` — flipped the tab green mid-turn, and (b) check what FOLLOWS the record: a queued message is delivered the instant the interrupt lands, its user-prompt record right after the line is the tell, and flipping green there painted "done" over the delivered turn's think). All are **events**, never idle timeouts: cancel-before-first-hook has no signal at all and is deliberately left unhandled for a TERMINAL Esc — do not re-add an idle-timeout backstop; it false-positived on every long think. The ONE sanctioned exception is the dashboard's `escape-recheck` (docs/tab-colors.md): a WEB interrupt is itself an event we generated, so its ~2s recheck may flip the dead magenta — but only on total silence (any tab-state movement or transcript growth over the press-time baseline bails).
- **Main session only:** any hook event carrying an `agent_id` is a subagent/teammate inner call — tab dispatch ignores it, and cmd/file formatters skip it (the substream owns subagent rendering; handling both would duplicate/mis-order). **Exception:** `claude-cmd-pre.py` does tee a subagent's foreground command for live streaming (marker + `updatedInput` only — the substream still owns rendering).
- **Release slot rows *before* calling `bg-recheck`**, or the recheck sees its own row. `bg-recheck` flips only a currently-blue tab and only when no live row remains.
- **Duplicate events are real:** `SubagentStart` and `SubagentStop` can each fire more than once for background agents — both handlers guard on slot state.
- **Failures arrive on `PostToolUseFailure`, not `PostToolUse`** — any new PostToolUse hook must be wired to both or failures silently vanish.
- **SessionStart can arrive with a SCRUBBED env** — Claude Code's agents view spawns `claude daemon run`, whose hook children have no `KITTY_WINDOW_ID`/`KITTY_LISTEN_ON` (the socket still resolves via the ppid walk, so pane calls *work*, anchorless). Pane ops must anchor to `KITTY_WINDOW_ID` or the `claude_session=<sid>`-tagged window and SKIP the whole lifecycle when neither exists (a daemon agent session / headless `claude -p` has no pane) — the focused-tab fallback let a phantom session close the focused tab's mirror and open an empty one (docs/mirror-pane.md, *Anchoring, and daemon-origin SessionStarts*).
- **`--resume` AND backgrounding a session can FORK the session id** — the conversation continues under a NEW sid with no SessionStart of its own (resume: SessionStart fires under the OLD sid, `source=resume`; backgrounding: the new sid is the background-job id), so the mirror/scorebar/tab freeze on the old sid. `plugins/claude_code/adopt.py` (run first by `dispatch.py`) adopts the predecessor at the fork's first event — renames its state DB to the new sid's path (symlinks at the old paths), retags the panes, writes the missing `sessions` row — driven by the take-once `adopt_pending` note (written by `split.cmd_open` for every HOSTED session) + `sids` registry in the global tab DB. The un-adopted regression is the canned anomaly "hook traffic under a sid with no sessions row" (docs/mirror-pane.md, *Resume (and backgrounding) can FORK the sid*).
- **Replayed output must not execute: every op's text passes `render.neutralize()` at paint** (only SGR styling and OSC 8 hyperlinks survive). The ops stream carries RAW command output and the renderer replays it on every reflow — an escape sequence in some command's output re-executes forever, not once (a tee'd `@kitty-cmd` DCS scrolled the mirror to the top on every repaint, masquerading as a scroll bug). Any new paint path must route op text through `_render`/neutralize.
- Empirically-confirmed but undocumented Claude Code behaviors this repo depends on (`updatedInput` command rewriting, Ctrl+B's `backgroundTaskId`+`backgroundedByUser` payload, `stoppedByUser` in meta.json, the interrupted-transcript line) are called out in the docs/ design docs (docs/streaming.md, docs/subagents.md, docs/tab-colors.md) — check there before assuming a payload field exists or not.

## Every new feature must be audit-covered

The audit trail is only useful if it has no blind spots — a mechanism that leaves no rows is undebuggable after the fact (the no-hook-on-cancel bug class was only cracked once auditing existed). When adding or changing a feature, wire it into the audit (`core/audit.py`) **in the same commit**:

- **New hook handler** → call `A.hook_event(payload, handler=, decision=)` with a `decision` string that says what the handler chose to do and why (the decision column is what makes `hook_events` diagnostic, not just a log).
- **New detached process / tailer** → `A.stream_start(...)` on spawn and `A.stream_end(stream_id, end_reason=)` on every exit path, plus `A.spawn(...)` at the launch site (wrap the tailer in `core.tail.stream_lifecycle` and spawn via `hookkit.spawn_streamer` and all of this comes for free). A stream with `ended_at IS NULL` is an anomaly signal — don't create streams that legitimately never end.
- **New coordination/marker/sentinel file** → `A.state_file(log, path, action, content)` on write and remove; new slot kinds go through `core/slots.py` so `A.slot(...)` rows come for free.
- **New tab-state input** → record via `A.transition(...)` with `applied` and a `reason`, including (especially) the bailed/skipped paths.
- **New swallow site** → `A.error(...)` before the `except: pass` (existing invariant above — it applies to new code too).
- **New accounting/derived numbers** (scoreboard fields, cost math) → make the inputs reconstructible: either the raw source is already audited (e.g. the transcript path in `sessions`) or add rows for it. "The number is wrong" must be answerable from the DB plus the named source, as the `message.id` token-dedup bug was.
- Then extend the **`anomalies` canned queries** in `core/auditcli.py` (`ANOMALY_SECTIONS`) if the feature has a known failure signature, and update **`.claude/skills/audit-debug/SKILL.md` in BOTH places**: the **schema table** (what the new rows/columns/kinds are) *and* the **"Known bug shapes" playbook** (which symptom should now consult that evidence, and what the tell-tale value looks like). These drift independently — the schema table alone got updated once while the playbook kept pointing at the old sources, which makes the skill *look* current while it triages blind. A new evidence source that no bug shape references is a smell: either wire it into an existing shape or add the shape it exists for. New tables/columns belong in the same migration style as the existing ones (WAL-safe, spool-file fallback, never raise into a hook).

## Experimenting with live sessions (spawning throwaway `claude` sessions)

Some behaviors can only be checked against a **live** Claude Code TUI in kitty — anything that screen-scrapes the terminal (the interrupt/`out: N tok/s` verify, the ghost-suggestion / ask / plan / rewind screen drivers). When you need to reproduce or measure one, spawn a **throwaway** session — but this opens a **visible tab in the USER'S kitty** and is disruptive, so treat it with care. Hard-won rules (2026-07-24, from getting every one of these wrong):

- **Get the user's OK first**, and **`kitten @ close-tab --match id:<win>` EVERY throwaway tab the moment you're done** (track the launched window id — `kitten @ launch` prints it on stdout). Never leave experiment tabs lying in the user's terminal.
- **The only valid subscription accounts are `c1` and `c2`** (aliases for `claude-subscription <slug>`). A bare `claude` launched from GUI kitty resolves to a **logged-out** config and just shows "Please run /login" — it never runs your prompt, so you're testing nothing. Launch under an account: `kitten @ launch --type=tab --cwd <trusted-dir> /bin/zsh -lic "c1 claude '<PROMPT>'"` (inline the prompt in the script string — the dashboard's `'claude "$@"'` argv form double-passes here and the prompt silently becomes the literal `claude`).
- **Use a folder Claude Code already TRUSTS** (e.g. the repo root). An untrusted `--cwd` opens a blocking *"Is this a project you trust?"* prompt that stalls the launch. Prefer a cwd where a benign, tool-free prompt (e.g. "print the numbers 1..300 as text, no tools") can't touch anything that matters.
- **An argv prompt does not reliably auto-submit / the startup greeting interferes** — the session may greet ("What's the task?") and idle instead of running your prompt, so there may be no real turn to act on. **Confirm the session is actually working before measuring**: poll `kitten @ get-text --match id:<win>` for the live indicator (`out: N tok/s` in the footer = generating; `<spinner glyph> <Gerund>…` = thinking; an empty `❯` box + a `[Model] │ …` footer WITHOUT `tok/s` = idle/done).
- **Screen markers are version-fragile — prefer "is the screen still CHANGING" over any string.** Glyphs animate, gerunds vary, thinking levels differ, agent-activity lines collide with naive patterns; two successive marker guesses (`esc to interrupt`, then `tok/s`) each shipped a broken verify. A running Claude Code turn always ticks its spinner/elapsed-timer/stream, a stopped one is static — so a **screen-delta** (diff two `get_text` captures a beat apart) is a robust, level-independent "still live" signal that needs no literal. If you must match a string, re-measure it against a real window; never guess.
- **`editorMode: vim` makes the input modal — a single Escape ≠ interrupt.** The user runs Claude Code in vim mode (`~/.claude/settings.json` + the c1/c2 configs show `"editorMode": "vim"`). While a turn runs the input is in INSERT (`-- INSERT --`); during the thinking phase the FIRST Escape only exits INSERT and does NOT interrupt the turn — you need a second Escape (or a re-press loop). This is why the web STOP "did nothing", and why the terminal answer/rewind drivers that send Escapes must account for the mode. Check `editorMode` before assuming Escape semantics.
- **Prefer the audit trail over spawning at all.** For most "does the web control plane work" questions, have the user drive their REAL session (press STOP / send / rename) and read the resulting `state_files` rows (`bin/claude-audit.py`) — it's non-disruptive and the rows are the ground truth. Reach for a throwaway only when you must watch the live screen.

## Branch in an isolated worktree, merge to main, push

This is a personal repo with a linear `main` history — there is no PR/review flow — but MULTIPLE agents often work here concurrently, and an agent that edits the shared checkout tramples (and gets confused by) the others' uncommitted changes. So:

1. **Never work directly in the main checkout.** Before touching any file, create a fresh branch off the latest `main` in an **isolated git worktree** (a branch alone does NOT isolate you — everyone in the same directory shares the same working tree and sees each other's uncommitted files). Use the harness's worktree isolation (`EnterWorktree`, or `isolation: "worktree"` for subagents) when available; otherwise `git worktree add <dir> -b <branch> main` yourself.
   - **Once in a worktree, EVERY file edit must land inside that worktree — under `.claude/worktrees/<name>/`, NOT the main checkout root.** The trap: after `EnterWorktree` the shell cwd moves into the worktree, but tools that take an ABSOLUTE path (Read/Edit/Write) don't follow it — passing the main checkout's absolute path (`/…/baqylau/dashboard/…`) silently edits `main` while relative-path tools (Grep/Bash) read the worktree, so your edits and your greps diverge. Always target the worktree path (`/…/baqylau/.claude/worktrees/<name>/…`), or use paths relative to the shell cwd. When in doubt, confirm with `git rev-parse --show-toplevel` (must print the worktree, not the main checkout) before and after editing, and check `git -C <main-checkout> status` stays clean.
2. Do all work and commits on that branch, in that worktree.
3. When the change is complete and verified (code + its audit wiring + docs/ + skill docs, per the sections above, and `make test` green), **merge it into `main` and `git push`** — every time, without being asked. Keep history linear: rebase the branch onto the latest `main` first, then fast-forward merge (`git merge --ff-only`). If `main` moved underneath you, rebase and re-verify before merging.
4. Clean up: remove the worktree and delete the merged branch. Do not open PRs or leave work sitting on an unmerged branch.
5. **If the change touched the web dashboard (`dashboard/` front- or back-end, or a `core`/`plugins`/`frontends` module the server imports), RESTART the running dashboard before you consider the work done** — it is a long-running singleton that does not hot-reload (see the "does NOT hot-reload" note above). The live server runs from the MAIN checkout, so first make sure `main` there includes your just-merged commit (the main checkout must be fast-forwarded to it — a push to `origin/main` from a worktree does not touch the main checkout's working tree), then `./bin/claude-dashboard.py stop && ./bin/claude-dashboard.py start`, confirm with `status` + a `curl` against a new endpoint, and TELL THE USER to hard-reload the browser (Cmd+Shift+R) — a server restart cannot evict their cached `app.js`/`style.css`; it only bumps `BOOT_ID` so their open page toasts "dashboard updated — refresh". Skip this step only for a non-dashboard change.

(This is about *using* worktrees — the `WorktreeCreate`/`WorktreeRemove` hooks must still stay unwired, per the wiring section above.)
