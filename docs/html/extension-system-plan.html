Baqylau · Design proposal

Extension system plan

Add one extension runtime, clear data contracts, and extension views for the web dashboard and Kitty.

  • Date: 2026-09-14
  • Status: Proposed
  • Scope: System design and delivery plan

Proposed design

Add a small extension runtime to baqylau. Keep each extension in a separate package outside the main source tree. Each package can provide data transforms, stored data, commands, web views, and Kitty views. One manifest declares these parts.

Use a separate worker process for each enabled backend extension. Use versioned messages between the worker and the host. Load web modules from each extension package at runtime. Let Kitty receive extension display data through the daemon.

The first release assumes trusted local extensions. A worker process gives failure control and a clear restart boundary. It does not restrict access to the user's files. Web code also runs with the dashboard's access. Support for untrusted code would need a separate security design.

This is a plan. No application code has changed. The proposed refactor is part of the design to review before implementation.

Use the existing meaning of “fact.” Canonical events are stored facts. Session facts and actor facts are derived state. Both need extension support, but they do not need separate event systems.

Data flow and transform rules

Store the original observation first. Apply extension transforms to the data that the next stage receives. Store the transform decisions with their source references.

1Record inputKeep the original bytes
2Transform raw inputThen run translation
3Transform factsThen validate and store
4Build derived dataTransform and store changes
5Update viewsWeb and Kitty

Expose a small set of contracts. The following names are proposed API names:

Table 2. Extension contracts
ContractInputAllowed result
sourceA declared file watch, process result, or submitted observation.Add raw events through host storage. Record source position and identity.
transform_rawA recorded input batch.Keep, replace, drop, or add derived inputs before translation. Preserve the original observations.
transform_canonicalA proposed canonical event batch.Keep, replace, drop, or add canonical facts before storage and reactions.
projectCommitted facts and prior extension state.Build extension records, feed entries, and counts. Use the same writer during replay.
transform_projectionProposed session, actor, entry, and extension record changes.Change, suppress, or add valid changes before one atomic write.

A transform returns explicit operations. A drop includes a reason. The host validates the whole output batch. It checks schemas, identities, references, and session state rules. For example, a transform cannot leave an actor that refers to a removed session. Display filters can hide an item without changing session state.

Preserve core event types. Add one extension event envelope and one extension entry envelope. An extension owns names such as adapters.logs.started. Its package supplies schemas. Persist the schema and a plain display summary with the data. The host can still read history when the extension is disabled, removed, or upgraded.

Add a typed scope to extension observations and facts: session, workspace, repository, or installation. Core session events keep their required session and actor IDs. An extension event has its own scope branch in the stored envelope. Session writers receive only session events. This lets the Git pane work when no coding session is active. Extend source routing to identify an extension source without requiring a harness plugin.

Transforms use only supplied input and recorded state. Network requests, file reads, model calls, and commands run as separate work. Their results become recorded inputs. Replay then has the data needed to repeat the transform.

Apply transforms in a fixed order. Required dependencies and explicit before/after rules define that order. Use the extension ID to order otherwise equal entries. Reject cycles at activation. A later transform receives the earlier transform's result. Added events continue from the next transform. They do not restart the same chain.

Generated records need stable IDs based on the logical source operation and an extension output key. A retry must produce the same ID. Do not use arrival time or a random value. Record parent references and limit generated output to stop extension event cycles.

Keep logical identity separate from interpretation revision. Repeated observations reuse the accepted result for that logical fact in the active history revision. A settings change cannot overwrite it with different bytes. A history rebuild creates a new revision linked to the same sources.

Storage, history, and failures

Keep database access in repository/. Extensions receive storage methods for their own records. Each collection has a schema, scope, key, and revision. Support the filters and indexes required by the first extensions. The worker does not receive a database connection.

Extend the current storage transactions. Commit accepted facts, transform decisions, and source links together. Commit derived records, feed entries, and the consumer cursor together. Send change notices only after commit.

For each processed batch, record the active extension versions, package hashes, order, settings revision, decisions, output references, and errors. Keep non-secret settings snapshots. Store secret references without copying secret values into the audit record.

Give each transform a time limit and an output limit. On a worker crash, timeout, or invalid result, discard that extension's partial result. Continue with its input unchanged and record the failure. Repeated failures stop the extension and show a failed state. A queue limit must not cause silent loss of original events.

Slow commands use a separate queue. They cannot hold the event worker. Record command progress and outcome. After a crash, check an external command's result before a retry. A push or commit must not run twice because a reply was lost.

Disabling an extension changes future processing. It does not undo facts already accepted. Remove its active views and commands, but keep history and settings. Use a generic display for stored extension entries.

Provide a separate, explicit history rebuild. First support rebuilding extension data and display entries from stored facts. If canonical transforms must be applied again, build a new interpretation revision from raw history. Compare it before activation. Switch revisions atomically and reset client cursors. Keep the prior revision for recovery. Replay must not send messages, run Git commands, or repeat other external actions.

Packages and runtime loading

Use a configured extension directory outside this repository. EXTENSION_ROOT below means that directory. A development link can point to a separate source checkout.

EXTENSION_ROOT/
└── adapters/
    ├── extension.json
    ├── backend/        # Worker code and package dependencies
    ├── schemas/        # Events, records, settings, commands
    ├── web/dist/       # Built JavaScript and CSS
    └── tests/e2e/      # Tests owned by this extension

The manifest declares the ID, package version, host API range, worker entry point, web assets, contracts, dependencies, settings schema, and E2E test entry points. Backend code and web code are optional. A display-only extension does not need an idle worker.

Read manifests without executing extension code. Find packages at startup and when the user selects Rescan. The user can enable, disable, or reload an extension while the daemon runs. A development watcher can request the same reload operation after a complete build.

  1. Validate the candidate packageCheck versions, schemas, dependencies, asset paths, and package identity. Keep an incompatible extension visible with a reason.
  2. Prepare the workerStart its process with its own dependency environment. Complete the API handshake and prepare any data migration.
  3. Activate one new runtime revisionFinish the current event transaction. Switch the active extension set at that boundary. Each batch uses one fixed revision.
  4. Update both displaysPublish the new extension catalog through the existing change streams. Replace web mounts and Kitty contributions.
  5. Release the old revisionDrain or cancel work, remove subscriptions, close owned resources, and stop the old process. Reject late replies from it.

If preparation fails, retain the active version and data. During disable, stop accepting new extension commands first. Let an active external action finish or report its state before stopping its worker. Retain a package version while active work still uses it.

Use JSON-RPC 2.0 over local process streams for worker calls. Test an existing implementation such as jsonrpcserver in the first prototype. Select and pin the library after checking bidirectional calls, timeouts, and shutdown. Use jsonschema to validate extension schemas. The project-specific work is the extension contract and process lifecycle.

Web and Kitty extension views

Define named display slots with stable IDs. The first set covers feed entries, session tabs, workspace pages, toolbar actions, status items, and settings panels. Extension routes use an extension ID and a view ID. Keep the existing route forms valid.

Web dashboard

Each extension builds an independent JavaScript module and CSS file. The module exports a mount function that returns update and dispose functions. Pass a host API, current scope, theme values, and an abort signal. The public boundary contains data and callbacks, with no dependency on private Svelte stores.

Use Vite library mode for the package build. A Svelte extension can implement its view with the documented mount and unmount APIs. Bundle its UI runtime for the first release. This adds some download size but avoids a shared private runtime contract.

The host serves declared assets at URLs that contain the extension ID and package hash. Import them at runtime. No main dashboard build is needed when an extension changes. Use a dedicated view root and scoped styles. Supply shared theme values through the SDK.

On disable or reload, dispose the view and release its timers, subscriptions, and host API handles. JavaScript modules can stay in the browser module cache; disposal ends their active work. A new package hash gives the new module a new URL. Add a recovery view for mount and update errors.

Extensions can decorate or replace supported core views. A replacement names its target explicitly. If two extensions claim the same exclusive target, report the conflict and require a selected owner. Additive contributions use stable ordering.

Kitty

Add a terminal display contract based on the existing render primitives. An extension returns blocks such as text, tables, diffs, trees, status values, and action references. The client owns width handling, colors, wrapping, resize, and terminal escape output.

Expose feed renderers, mirror sections, scoreboard items, and named panes. Add a pane selector and typed key or click actions. Send actions to the extension command API with the active repository or session scope.

The same backend records supply both frontends. Web views can use richer layouts. Kitty views use the terminal block contract and can request a pane through the existing terminal service. Test the contract with a real diff, a file tree, and thread navigation before fixing its first version.

Extension discovery and cooperation

Expose extensions.list(), extensions.get(id), and lifecycle subscriptions through the SDK. Return package version, enabled state, health, and available contracts. An installed extension is not necessarily active.

An extension can publish versioned events, query methods, and command methods through the host. Other extensions use these declared interfaces. Keep cross-extension calls out of deterministic transforms unless their recorded input already contains the required result.

Required dependencies control activation order. Optional dependencies add features when available. If a required dependency is disabled, stop its dependents in the same runtime change and show the affected list. An optional dependency change removes only the related integration.

For the example pair, the adapters extension publishes a versioned command activity contract. It includes adapters commit and adapters push. The Git extension optionally consumes that contract and updates its repository view. Both extensions still have useful behavior when the other is absent.

Use the session, actor, shell, and invocation identities to link records. If one operation appears in more than one source, show one operation with multiple source links. Matching only command text or time is not sufficient.

Settings page

Add a top-level Settings page with an Extensions section. Each row shows name, version, source path, enabled state, health, and dependency problems. Add enable, disable, reload, rescan, and diagnostic controls.

Select an extension to see its description, declared access, dependencies, settings, and recent failures. Show states such as disabled, starting, enabled, stopping, failed, and incompatible. A failed activation must not appear as enabled.

Generate standard fields from the settings schema: text, number, choice, boolean, list, and secret reference. An extension can supply a custom settings panel through the same web view contract. Both forms use the same validated settings API.

Start with installation settings and explicit workspace overrides. Each schema declares the supported scope. Save a settings revision atomically. Reject stale writes from another browser. Distinguish display changes from data-processing changes, and explain when a history rebuild is needed. Secret fields are write-only and use host credential storage.

Extension query and command routes use the current origin and read-only checks. The host checks that the extension and command are still active when a request runs. Changing the browser UI alone must not change that result.

Future adapters extension

Start from canonical shell start, progress, and finish events. These already carry a shell ID and output order. Add command recognition inside the extension. Parse shell syntax with the existing parser package. Request structured CLI output where available.

Assign each detected invocation its own identity. A shell command can contain several invocations. Track running, completed, failed, and canceled states. Large output uses stored content references and paging.

Future Git extension

Use a repository scope identified by the resolved worktree and Git directory. Several sessions can share one repository. Linked worktrees have separate working changes. Session views should refer to this shared repository state.

Add a Git page or pane with a commit log, commit details, file tree, and diffs. Separate staged, unstaged, and untracked files. Let the user select the files to commit. Show binary files and large diffs with clear limits.

Refresh on relevant recorded commands and file changes. Include direct Git commands, adapters commit, adapters push, and actions from this pane. Query Git to confirm the current repository state. A command start is not proof of a commit or push.

Use Git's machine-readable command output for repository operations, including the documented porcelain status format. Pass argument arrays and an explicit repository path. Keep a command queue per repository. Check the branch and index again before a write if they changed during review.

Provide an editable commit message field and a Generate message action. Use the existing inference/contract.py service through the host API. Generate from the selected staged diff. Keep the message as a draft until the user selects Commit.

The Push action shows the remote and branch. Show progress and failures from Git hooks, authentication, or a rejected push. A failed action keeps the user's draft and selection. The first version covers the requested read, commit, and push workflow.

Tests owned by each extension

Ship an installable extension SDK and test kit. Every extension keeps its E2E tests in its own package. Test the built package through the public host API and both declared display surfaces.

The host test runner loads extension test declarations. CI checks that every declared feature has a relevant E2E case. The runner starts a private daemon, data directory, port, and workspace. It must not use the normal dashboard on port 8377.

Add performance checks for a representative recorded session. Measure event delay, queue growth, worker memory, and view update cost with extensions disabled and enabled. Choose time limits from this measurement. Test that a failed extension does not stop normal session processing.

Decisions and limits

The proposed defaults are trusted local packages, one process per enabled backend extension, independent web bundles, host-rendered Kitty blocks, fixed transform order, and explicit history rebuilds. Enable and disable take effect without a daemon restart.

The main cost is the addition of process messaging and lifecycle control. Batch calls and keep slow work off the transform path. The first prototype must check this cost before the full runtime is built.

The repository code and current framework APIs were inspected for this plan. The adapters CLI output contract was not inspected. Its structured output, operation identities, and thread content remain the main unknowns for the future adapters extension.

The HTML communication skill supplied the document structure and styles. The design decisions come from the code review and the requested behavior.
