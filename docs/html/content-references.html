Design review

Content references, as they are and as they could be

A content reference is the address of one piece of full-size text inside a canonical event. Today that address is an ad-hoc string, and the knowledge of which addresses exist is split between the code that mints them and the code that resolves them — which is why the resolver needs an allow-table, an rpartition, and an isinstance guard, and why one real address in the running system gets a 400.

  • Author: Claude
  • Updated: 2026-08-18
  • Scope: engine/queries/content.py and everything that feeds it

Summary

The dashboard and the terminal mirror both show blocks of activity. When a block's text is large, they don't ship it twice — they attach an address the frontend can call back with to fetch the exact full text for copy, or a rendered diff for expansion. That address is the content reference, and CanonicalContentService.resolve is what turns it back into text.

The concept is sound. The implementation has one defect that causes every symptom you pointed at: the reference is a formatted string rather than a value, so the set of legal addresses is never written down anywhere. Instead it exists twice — as field-name literals scattered across the fold and eight presenters, and as a hand-maintained table in the resolver. The two copies have already drifted apart in both directions.

◆
Key point: rpartition, the isinstance guard, and the allow-table are not three separate messes. They are what a resolver has to do when the token it receives carries no type and no shared vocabulary: it must re-discover, at runtime, what the minter meant.

The concepts

Six things carry the reference from the event store to a click. Each is named as the code names it.

Canonical event
The immutable stored fact, identified by a CanonicalEventId. Its payload is one of the typed classes in domain/events.py — MessageCreated, OperationFinished, FileAccessed. Some payload fields hold arbitrarily large text.
Activity
What the fold in engine/projections/activity.py produces: a folded view of one thing that happened, built from every event about it. An OperationActivity is the start, all the progress chunks, and the finish, collapsed into one object with command_text() and output_text() methods.
Content slot no such type today
The idea this document is about: which piece of text you want from an event. "The command an operation ran." "The unified diff of a file edit." Today this idea is spelled as a raw field name — the strings content, operation_content, operation_command, operation_output, unified_diff, result, brief, prompt, feedback.
Content reference
An event id plus a slot, written as "{event_id}:{field}". Example: progress-two:operation_output. It has no type; it is a str everywhere it appears.
Dashboard item
One rendered block for the browser (dashboard/render/items/item.py). It carries three reference fields: content_reference, command_reference, output_reference, each str | None.
Opened view
Terminal-only state: which references the mirror has expanded in place. Stored in the opened_views table, whose primary key is the reference string.

How it works today

A reference is minted on the way out and parsed on the way back in. These are the five stages, and the drift happens between stages 2 and 5.

1Foldrecords event id + field name
2Mint8 presenter sites format the token
3Shipitem field, or OSC 8 hyperlink
4Clickbrowser fetch, or client subprocess
5Resolvesplit the token, guess its meaning

Stage 1: the fold records a field name

Every activity that can carry large text gets two loose fields. There is no type relating them, and nothing constrains the second to a known set.

Ten sites in the fold assign content_field, each as a bare string literal chosen by the branch it sits in.

Stage 2: eight sites mint the token

The wire format lives in eight places. One of them is a helper that also applies a size rule; the other seven are inline f-strings, and they do not all agree.

Note: The 4096-character rule is a presentation decision — "only offer copy and view links when the text is big enough to want them" — and it reaches only one of the eight sites. The other seven offer the affordance unconditionally. That inconsistency is invisible today because the rule hides inside the same helper that formats the token.

Stage 3 and 4: two very different rides

The token travels two ways, and the second one constrains any redesign: in the terminal it becomes a URI inside an OSC 8 hyperlink, which the emulator hands to a subprocess as argv[1].

Stage 5: the resolver re-discovers what the token meant

This is the code you objected to, and every line of it is a consequence of the token having no type. Read it as three separate acts of guessing.

Note what act 2 admits. Operation output does not live in a field: it is folded from every progress chunk. So operations get a second, completely different resolution strategy — re-fold the activity and call output_text() — while everything else is read off the payload by attribute name. One concept, two mechanisms, chosen by a string comparison.

The problem

Both halves of the split authority are already wrong, in opposite directions. I checked each against the code, and reproduced the first.

1allow-table row nothing can ever reach
8places that know the wire format

A live bug: the fold mints an address the resolver refuses

When a file-editing operation finishes with a result, the fold moves the file activity's content pointer to the finish event and sets the field to "operation_content" — but if the file activity took the other branch it can be left holding "result". The resolver's table has no row for OperationFinished, so the token it hands the browser comes back as a 400. I reproduced it against the real fold and the real resolver:

The user-visible symptom: the file block shows its ⧉view link, the click returns 400, and the browser throws content request failed. Nothing in the suite catches it, because no test walks a minted reference back through the resolver for that shape.

Dead permission: a row nothing can reach

The table allows OperationInputProvided.content. No projection and no presenter ever mints a reference to that payload — grep finds it only in the codex translator, the event definition, and the resolver itself. It is a permission granted to an address that cannot exist.

I also checked what is not broken, so the review is honest: rpartition and :-splitting appear nowhere else in the tree, and the other type-keyed dispatch tables (_PRESENTERS in dashboard/render/items/__init__.py, _CALL and _TOP in the codex translator) are honest registries over foreign vocabularies, which is the right shape for parsing someone else's JSON.

To be: one vocabulary, owned once

The fix is a value type and a single enum, plus one decision about who does the parsing. Everything you objected to disappears as a side effect rather than being individually cleaned up.

The one new idea: a content slot

Name the thing the strings were standing in for, in the domain, once. Every minter and the resolver then share one vocabulary that the type checker enforces.

i
Note: A slot is deliberately not a payload field name. content appears on five different payload types meaning five different things, while OPERATION_OUTPUT corresponds to no field at all — it is folded from progress chunks. Naming slots after fields is what forced the resolver to consult the payload type before it could interpret the name.

Who owns what, after

Each stage keeps exactly one job, and no stage repeats another's knowledge.

domain/references.py owns the vocabulary: which slots exist. Nothing else declares one.
engine/projections/ owns which slot each activity HAS. Replaces the loose pair with typed fields: OperationActivity gets command and output references; FileActivity gets one content reference.
dashboard/render/, terminal/mirror/ own presentation only: whether the text is big enough to offer the affordance. They pass a reference through; they never format one.
api/ owns the wire form. The single place a ContentReference becomes URL text, and the single place URL text becomes a ContentReference.
engine/queries/content.py owns resolution: reference in, text out. Receives a typed value, so it validates nothing and guesses nothing.

The resolver becomes an exhaustive match

With a typed reference arriving, resolution is one match over the slot. Each case narrows to the activity it needs and asks it for text — the strategy operations already used, now used by all of them.

Now

Split the string. Guess whether the field belongs to the folded family. Look the payload type up in a table of allowed names. getattr by name. Check the result is textual, because nothing guaranteed it.

Adding a slot means editing the table, and forgetting to means a 400 that only a user finds.

After

One match on reference.slot. Each arm narrows to a typed activity and returns its text. assert_never on the fallthrough.

Adding a slot means adding an enum member, and mypy fails the build until the arm exists.

Three domain errors get simpler too. MalformedRequest for a bad reference shape disappears — the shape is now validated before a handler runs. UnsupportedRequest ("referenced content is not textual") disappears — each arm returns a str by construction. UnknownReference survives, and means only what it says: no such event.

The decision I need from you: where the slot goes on the wire

The two options differ in whether we ever parse a reference again. Both are honest; the first is stricter, the second is smaller.

Option A — path segments

The slot is its own URL segment, so FastAPI splits the path and pydantic validates the slot against the enum. An unknown slot is a 422 before any handler runs. No parsing code exists in the tree at all.

Costs: an opened_views schema change, and the JS carries two data attributes instead of one.

Option B — one token, slot first

Stays a single opaque string on the wire, in the DOM dataset, and in the database. One parse function survives, in domain/references.py, called once at the api boundary.

Costs: MalformedRequest stays, one partition stays, and the slot is validated by our code rather than by the schema.

Under either option the view and path query parameters go away: FILE_DIFF versus FILE_SOURCE already says which renderer to use, and the file path comes off the FileAccessed payload instead of off the client's word.

What migrates

Almost nothing, which is the good news about a projection-only concept.

  • Stored eventsUntouched

    No canonical payload holds a reference. Slots are derived on every read, so no schema version bump and no backfill.

  • Dashboard itemsRegenerated per request

    Items are rendered fresh from the fold. A browser tab open across the deploy holds stale tokens in its DOM; a refresh fixes it.

  • opened_viewsRecreate the table

    Ephemeral UI state — which blocks are expanded in a terminal pane right now. Dropping it costs a reader nothing but a second click.

  • ClientsTwo files change

    client/terminal_content.py and client/terminal_view.py strip a scheme and forward the rest. Under option A they forward a path and stop building a JSON body, so _wire.py gains a path template and loses one.

The guard that keeps it fixed

The reason to prefer a shared enum over two lists is that it makes the original bug unrepresentable. Two mechanisms, both cheap:

  1. Exhaustiveness in the resolver assert_never plus mypy strict means a new slot cannot ship without a reader. That kills the dead-permission half.
  2. A round-trip test over the fold For a fixture session covering every activity kind, take every reference the presenters mint and resolve each one. That kills the finish:result half, which today no test can see because minting and resolving are tested separately.

What I have not settled

Caution: Three open questions. I would rather agree on them than guess.
Scope of the activity-id cleanup
_activity_id has the same disease and is a bigger job: the fold's 31 branches all key on that string, and item_id's wire format changes with it. Same change, separately, or not now?
Whether FILE_SOURCE and FILE_DIFF are two slots or one
Two slots make the renderer choice a type-level fact and delete the view parameter. One slot plus a rendering mode keeps the reference closer to "the content of this file event". I lean two.
The name of the resolver
CanonicalContentService says nothing. ContentQueries.text(reference) matches the neighbouring SessionQueries and reads as what it does at the call site. Open to a better one.
