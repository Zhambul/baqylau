Why this redesign

The current read path computes everything per request. Every dashboard tick folds the whole session's canonical events through activities_of (engine/projections/activity.py), then two presenters turn the result into pre-escaped HTML (dashboard/render/) and ANSI frames (terminal/mirror/presenter.py). The measurement in docs/html/after-the-event.html put one session-stream tick at 97.7 ms against a 250 ms budget on the largest session.

97.7 msper session-stream tick today (largest session)
42,272canonical events in the live store, 52 sessions
17 → 5GET routes after the redesign

The redesign replaces the pull-based fold-per-request model with:

  • SessionData — one small aggregate per session (state, actors, usage, context, statistics, goal, tasks), written at event time by a reactor, read in one indexed query.
  • Entries — the session feed, materialized at push time into its own table by the same writer pipeline. Immutable, append-only, typed. The API reads only the read model, never the canonical log.
  • Client-side rendering — the daemon serves data only. The browser paints HTML, the kitty client paints ANSI. dashboard/render/ and terminal/mirror/ are deleted.
◆
Key point: Everything the frontends see is materialized at push time: the writer pipeline turns each canonical event into aggregate updates and, where the event is feed-worthy, one immutable entry row. The API layer reads exactly two things — session_data and session_entries — and never opens the canonical log. Canonical events become internal evidence: the audit trail and the replay source.
▲
Caution: Backward compatibility is not a concern. This is a decided constraint of the project, not an open question. No old API route survives for old clients, no old event row is migrated, no migration is written, and no dual-format period exists. MAIN_SCHEMA_VERSION bumps to 4 with no MAIN_MIGRATIONS entry; the deploy step deletes <data_dir>/main.db and the fresh DDL creates everything. All history is discarded.

Target architecture

The interpreter loop (engine/interpret/loop.py) keeps translation and its two translation inputs, and sheds everything else. SessionUpsert and the shell-output following are not reactions — the pull phase reads the rows they write (sessions.watchable(), the following table), so they stay on the interpreter thread, exactly as today. Every genuine reaction moves to a separate reaction loop — a new daemon worker that follows the canonical cursor through a progress row. Per event, in this fixed order: Pane, Interrupt, and a new TabColorReaction that paints the kitty tab on status transitions (today terminal/panes/streams.py:151 drives tab_appearance from the read path, and that read path dies), then the harness reactors, then the SessionDataWriter list — EntryWriter first, the aggregate writers after. A reaction or writer failure lands in the audit store and processing continues, exactly today's policy.

The stream, end to end

One cursor space makes the whole mechanism. The writer thread stamps every write with the next value of one monotonic counter: an entry row gets it as its cursor, and a changed session_data or session_data_actors row stores it as its revision. So "everything after cursor C" is one question with one answer across both kinds of change.

Backend: from canonical commit to a committed read-model row

Two loops, decoupled by the canonical store itself. There is no queue between them — the canonical cursor is the handoff:

  1. The translator loop translates and feeds itself engine/interpret/loop.py keeps record_translation plus the two translation inputs: SessionUpsertCanonicalEventReaction (the pull phase reads sessions.watchable()) and OperationOutputCanonicalEventReaction (the pull phase reads the following rows, and this reaction unlinks the files the pull phase reads — one thread keeps that safe). Everything else leaves. The interpreter never touches a pane, an interrupt, or the read model.
  2. The reaction loop follows the cursor The "baqylau-reactions" worker ticks every 0.25 s: read canonical_events WHERE cursor > ? (the progress row), process each event in canonical order through the fixed sequence — PaneCanonicalEventReaction, InterruptCanonicalEventReaction, the harness reactors (with their controls context), then the writers. The tab paint runs after apply(), fed the actor rows it just committed — a status painter that ran before the StatusWriter would paint the previous event's status. It is therefore not a CanonicalEventReaction but a small applied-status listener in terminal/. Any exception becomes an audit.errors row and the loop continues — today's policy, unchanged.
  3. All of one event's read-model rows commit as one transaction The writers do not write. Each returns a change object — an entry to append, an aggregate row to replace. The loop collects them and calls one repository method, apply(session_id, changes, canonical_cursor), which in one transaction inserts the entry with cursor = R, upserts the aggregate rows with revision = R, and advances reaction_progress. One repository method, one transaction — the repository rule holds, and an SSE poll can never observe half an event. A crash replays from the progress row through the same apply, and the entry's UNIQUE entry_id keeps the replayed insert idempotent.
  4. The progress row is the source of truth reaction_progress (DDL below) records the canonical cursor of the last fully processed event. On daemon start the loop resumes from it. The rebuild command clears the three read-model tables first, then runs this catch-up from zero, driven through the writers only: side-effect reactions (panes, notifications, OTel) must never replay history.
  5. Revision allocation survives restarts At start the counter initializes to MAX(session_entries.cursor, session_data.revision, session_data_actors.revision). Entry rows are inserted with an explicit cursor value — SQLite accepts an explicit value into an INTEGER PRIMARY KEY AUTOINCREMENT column and keeps the sequence consistent — so entries and aggregate revisions come from one allocator and the cursor space stays single.

Note: The split adds at most one 0.25 s tick of latency to every reaction — pane opening, interrupt clearing, notifications, and the read model alike. In exchange, translation throughput no longer depends on any reaction, and a slow or failing reaction can never stall the evidence pipeline.

Backend: the SSE handler

Each connection is one async generator in api/sessiondata/streams.py, built on the existing api/sse.py helpers (STREAM_POLL_SECONDS = 0.25, STREAM_HEARTBEAT_SECONDS = 15.0, off_loop for blocking reads). Per iteration it calls three repository methods on the threadpool — entries_after(session_id, C), data_after(session_id, C), actors_after(session_id, C), each one transaction — assembles at most one frame from the api-owned response models, sets the frame id to the highest revision it read, and sleeps. No news for 15 s → a heartbeat comment. There is no broker and no per-client buffer: a slow client delays only its own generator, and its next poll simply returns a bigger batch. The global stream is the same generator without the entries query, using changed_after(C) across the two aggregate tables.

How a client connects, and what the handler does:

  1. Snapshot first — one boundary, one cursor The client fetches GET /sessionData/{id}. Its top-level cursor is the session's high-water mark — MAX across the entry cursors and the aggregate revisions of this session, computed inside the same repository read as the aggregate rows (one method, one transaction). The client then fetches /entries?at=C: the page is read as of that cursor (cursor <= C), so the page and the snapshot describe one instant. The aggregate's own revision is not a stream boundary — it routinely lags the newest entry, and using it would duplicate or drop entries.
  2. Open the stream from C GET /sessionData/{id}/stream with Last-Event-ID: C. A reconnect after a network drop is the same request — the browser's EventSource sends the header on its own.
  3. The handler loop, every 0.25 s Three indexed reads, off the event loop as today (api/sse.py:off_loop): All three empty → no frame (a heartbeat comment goes out every 15 s, as today). Otherwise the handler emits one frame carrying everything found, sets the frame's id to the highest cursor it saw, and advances C.
  4. The client applies the frame Replace session if present; replace each actor object by actor_id; append each entry in cursor order, idempotently by entry_id — an entry the client already holds is skipped, so an overlapping frame can never show twice. Immutable entries mean append-or-skip is the only feed operation.

Properties that fall out of this design, for free:

  • Batching. Ten context reports inside one poll window collapse into one actor object in one frame — the last committed state wins. No coalescing rule exists; the poll interval is the batch boundary.
  • Lossless resume. The frame id is a database cursor, not a sequence number the server invents. Whatever the client last saw, the next poll returns exactly what committed after it — across a reconnect, a laptop sleep, or a daemon restart.
  • Consistency. The writer commits in event order on one thread; the handler reads committed rows only. A frame can never show an entry whose aggregate change is older than the client's cursor.
  • No fan-out state. Each connection is an independent loop over the same indexed queries. No broker, no subscription registry, no per-client buffer — the repo's existing SSE stance, kept.

The global stream (GET /sessionData/stream) is the same loop without the entries query, across all sessions: WHERE revision > ? on the two aggregate tables. It drives the session list and the tab colors.

The session stream frame:

Transport stays the repo's deliberate design: the stream polls the read model every 0.25 s — no broker, no bus. The poll is WHERE cursor > ? on the entries index plus the two aggregate rows, instead of a full fold, and it batches everything between two polls into one frame, which is all the coalescing the system needs.

Performance, before and after

Before — measured

97.7 ms per session-stream tick on the largest session (7,180 events): eleven folds over the whole event page, three of them identical. Cold first read 481 ms. Every SSE consumer repeats the folds daemon-side.

After — by construction

One indexed WHERE cursor > ? read per tick plus two small-table reads, all against the materialized read model — the API never opens the canonical log. Status and statistics were computed once, at write time; chunk folding and collapse move to the client, bounded by what is on screen.

Open risks

  • The scale of steps 4 and 5. The dashboard layer is ~3.1k lines plus the static JS; the terminal layer ~3.8k. These are rewrites, not edits.
  • The test suite. ~14.7k lines across 20 files touch the layers this changes. Step 1 alone reshapes every translator test.
  • The status logic is a rewrite, not a port. Table 0 is its specification; StatusWriter is the one writer with real state-machine logic and needs its own tests, verified branch by branch against engine/projections/tabstate.py before that file dies.
  • All history is discarded. main.db is deleted at deploy; preferences go with it. Accepted, decided.
  • Payloads are stored twice. Feed-worthy payloads live in canonical_events and again in session_entries — a few MB per session on local disk. Accepted; a missed entry write is repaired by the rebuild replay.
  • Replay must distinguish writers from side effects. The rebuild command and any catch-up from an old progress cursor drive the writers; the pane, interrupt, notification, and OTel reactions must be excluded from historic replay, or old sessions reopen panes. The loop needs an explicit "live versus replay" boundary, and a test for it.
  • Every reaction gains up to 0.25 s of latency. Pane opening and interrupt clearing now ride the reaction loop's tick. Accepted as the price of an unstallable translator; if a gesture ever feels slow, the interpreter can set a wake event the loop waits on instead of sleeping.
