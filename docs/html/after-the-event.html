Implementation plan

The read side: eight defects, one measurement, and about a hundred lines

Eight correctness defects with exact line numbers, eight performance and hygiene changes, and the smallest version of each. The measured problem is 67 ms of redundant folding, removable in ten lines.

  • Author: Claude
  • Updated: 2026-08-18
  • Scope: everything between canonical-event storage and the two clients

Summary

8correctness defects; two of them latent, the rest live today
67 msof a 98 ms stream tick spent folding the same events three times
~110lines that fix every defect and three quarters of the cost

Do the eight defects and items B–H2 first: that is every defect plus the measured cost, and it removes more code than it adds. Items I1 and J–M are a worthwhile second change that deletes duplication. Nothing here needs a new package except one leaf, and only one item adds a type (plus one alias).

◆
Key point: An earlier draft proposed a resident SessionState with its own registry. It is not needed: EventPages (engine/projections/pages.py, 104 lines) is already per-session, cursor-keyed, locked and replaying-on-miss, and the redundant work is three calls to one pure function with identical arguments — so a memo on that function is ten lines and keeps the property that makes this system debuggable, that no read can be stale.

Cost figures come from running the read path against the real store on this machine (306 MB, 43 sessions, 35,720 events, largest 7,179). Line numbers are exact; line counts are estimates. No speculative fallbacks anywhere, with audit logging the one exception, because it is the only record left after a failure.

What the read path costs

97.7 msone session-stream tick on the largest session, against a 250 ms budget
~75%of one core, with a browser tab, a mirror and a scoreboard on that session
67 msof the 98 spent folding the same events three times

statistics (engine/projections/work.py:66), background_operations (:53) and activity_after (engine/projections/paging.py:30) each call activities_of in full over the same page, at the same cursor, with the same scope — three identical folds inside one tick, where the cursor cannot have moved. The other 31 ms is eight cheap single-purpose folds plus a 1.4 ms warm page read; a session's first read costs 481 ms once per process, which EventPages already handles.

Caution: The 97.7 ms measures DashboardStreamService.frame only. api/dashboard/streams.py:128 also calls workspace.snapshot every tick, carrying the uncached full-session read that item G removes — so the real per-tick cost is above 98 ms, and item G may matter more than items B and C. Re-measure with it inside the loop before trusting "98 → 25 ms".

Two things the measurement killed. The problem is not "a fold per query", which is what a per-session folded state would have addressed. And the O(k²) progress rebuild that three earlier drafts leaned on does not exist at this scale: the worst operation in the store has 11 progress chunks. One contrast worth keeping — the mirror folds a bounded tail (terminal/panes/streams.py:130-135), which is why its cost does not grow with history, while the dashboard folds the whole session for the same job.

Eight traps

The constraints that are not obvious and would be got wrong:

  1. Item D needs OrderedDict and move_to_end. through() reassigns an existing key (pages.py:68,72), and a plain dict does not reorder on reassignment — so "drop the oldest" would evict the first session ever seen, which on a busy machine is the busiest one.
  2. Item F's comparison needs a None guard. Both the cached and the requested cursor are int | None (pages.py:21,51) and today the None cases are absorbed by the guard at :56-57; a bare > raises. The prefix branch goes alongside the existing miss branches, not in place of them.
  3. Item C's write-back must compare cursors. With the lock released, two threads can build entries at different cursors and the later writer would otherwise regress the cache.
  4. Item E is a no-op without item H. The memo lives on a service instance, and the stream currently uses a second one whose sessions() is never called.
  5. Item M must not put the pane stream behind the guard. api/terminal/panes.py:21 carries Depends(control_plane()) while api/terminal/streams.py:21 is deliberately open; merging them into one router breaks the pane client, and no test asserts that negative.
  6. RGB cannot move for item L: terminal/models/** is restricted to four imports (tests/test_canonical_architecture.py:276-291). And terminal/'s allowlist (:386-396) must gain presentation for item J — that test edit is mandatory, not optional.
  7. Item B needs a few slots, because two evictors run continuously. A single slot cannot survive one tick. _refresh_sessions is a daemon thread that every 250 ms folds all sessions at a different cursor with ActivityScope() (dashboard/services/sessions.py:34,70-73,139), and the pane path is a guaranteed miss — tail_with_actors rebuilds its tuple on every call (pages.py:96-102), so it can only ever evict. Either alone zeroes the win, and both run whenever a pane and a tab share a session. So: a handful of slots keyed on (id(events), scope); return element 0 as a tuple so a future caller cannot mutate a shared value (none does today); add cache_clear() to the test fixtures; and record that paging.tail is a deliberate miss, so nobody "fixes" tail_with_actors to chase it.
  8. Item F must not write back the older page. Today the miss branch overwrites the entry with the page it just read (pages.py:69-72), which is half of the alternation. The prefix branch has to return the prefix and leave the newer entry in place, or the read is fixed and the regression kept.

Item I1 in detail, and why I2 waits

The drift behind defects 1 and 3 is countable: the legal set of references exists in two copies — the mint sites, and the allow-table at engine/queries/content.py:73-83. The cheapest guard is one assertion that the two agree, but it is not free as an earlier draft implied: neither set is visible to a test today. The allow-table is a local dict inside resolve(), with a second literal set at :42-46, so both must first be hoisted to module constants; and the minted set does not exist as data at all until ContentKind does. So the guard is either I1-dependent, or it costs that hoist first. Worth knowing before it is promised as a quick win.

I1 is a readability change: six sites mint from two parallel optional fields with the same both-non-None guard (terminal/mirror/presenter.py:100-104,171-175, terminal/panes/streams.py:173-175, dashboard/render/items/files.py:74-78, dashboard/render/items/operations.py:106-110,118-120), and then presenter.py:289,291 re-tests the field name as a string — the arm that misses in defect 1. What makes merging the two fields sound is that they are provably both-or-neither: every one of the eight assignment sites in activity.py sets them together.

What I am not building

A resident SessionState and a registry for it
EventPages is already that object, and the redundant work is one pure function called three times — so item B is ten lines rather than a new tier, and no read becomes stale.
Per-event folding
~25 ms to microseconds, for a rewrite of the subtlest 437 lines in the read side.
An ItemView tier, with wrapper dataclasses, a body-segment union and a role enum
~100 lines of duplicated semantics do not justify six modules and ten types on the hot path. Item J keeps the countable part. This one is still open if the objection is to the concept rather than the duplication.
Renaming opened_views to expansions
Seven files, the repository contract, the audit-debug skill and a schema migration on a 306 MB store, to improve one word.
Deleting SessionQueries
214 lines of one-liners whose docstring explains why that shape was chosen. It is not the problem.

Four things to leave the code saying

Each replaces a question that has been asked more than once during review:

  • terminal/mirror/visibility.py's docstring should say it answers "the pane does not echo you back", where ActivityScope answers "whose tab am I in" — they are opposite questions, not two spellings of one, which is why they stay separate.
  • pages.py's docstring should record that through_cursor=None means the store's latest cursor. Its existing claim — "the page, not the fold, is where the caching belongs" — stays true under item B, since the memo is keyed by the page's own events.
  • If anything outside engine/ ever needs the page, add a public SessionQueries.events(...) rather than reaching through queries.pages.through(...) — one object reaching into another's collaborator is worse than the extra method. Item G's one-line version needs neither.
  • Rename _latest_pages_lock to _lock and say it covers both maps — item D adds the second one.

Open questions

  1. Do items I1 and J–M happen at all? B–H2 fixes every defect and the measured cost. The rest removes duplication that costs nothing today except the next drift bug.
  2. Do the two presenters stay? Item J shares their label tables and keeps both, because the duplication measures ~100 lines rather than a tier. If the objection is to the concept — a presenter deciding both what to show and how to paint it — then the ItemView version is the answer, at roughly six modules and ten types, with the strongest gate in the plan (golden ANSI and jsdom output byte-identical). I recommend item J and may be weighing the concept objection too lightly.
