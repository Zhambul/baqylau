Design review — final

The read side: twelve bugs, one measurement, and the smallest change that fixes both

Five review passes and one benchmark cut this from a redesign to a plan. The measured problem is 67 ms of redundant folding; the structural problem is a stringly-typed reference and one duplicated decision table. Most of the rest was taste.

  • Author: Claude
  • Updated: 2026-08-18
  • Scope: everything between canonical-event storage and the two clients

Summary

This began as a redesign of everything downstream of canonical-event storage: a per-session folded state, a display tier, a typed content reference, a repackaged API. Then it was measured, and then someone counted what the new types would actually replace. What survived is much smaller, and it fixes everything that is genuinely broken.

12real defects in the code today, six of them user-visible
67 msof a 98 ms stream tick spent folding the same events three times
~110lines that fix every defect and three quarters of the cost

The plan, in order:

  1. Fix the twelve defects About 40 lines across six files, plus tests. Every one has a file and a line number, and six are visible to you today. Specified exactly in Table 1.
  2. Take the measured performance fixes About 70 lines: memoise the fold, release a lock, evict two caches, agree on one cursor, route one query through the page cache. The tick goes from 98 ms to roughly 25 ms.
  3. Stop and re-measure Anything further is judged against that number, not the one at the top of this page.
  4. Later, when it is the thing in front of you ContentRef — the one new type worth building — one shared label-and-format module, one shared protocol, six shared colour constants. About 250 lines, removing the duplication that actually exists.
◆
Key point: The original centrepiece — a resident SessionState with its own registry — is not recommended, and the reason is worth keeping. EventPages (engine/projections/pages.py, 104 lines) already is that object: per-session, cursor-keyed, locked, replaying on a miss, advancing incrementally. A 25-line memo hung on it delivers every structural claim the larger design made — one door onto session facts, field reads instead of repeated folds, private caches deleted, a resolver that does not re-fold — without giving up the property that makes this system debuggable: today a wrong screen is always explained by the store, because no read can be stale.

One rule shaped the final pass: no speculative edge-case handling and no fallbacks, with audit logging the single exception — it may always be defensive, because it is the only record left after a failure. That rule removed more than it added. Defect 6 inverted from a rename across four files into a ten-line deletion; defect 2 went from an Optional threaded through three files to one raise; item I stopped deleting two working query parameters and so no longer needed the route that repaired them; and item J dropped two changes whose justification did not survive checking — one would have altered what a surface prints, the other cited a styleguide that was deleted in commit 0d2a31a.

The cost figures come from running the read path against the real store on this machine (306 MB, 43 sessions, 35,720 canonical events, largest session 7,179). Everything else comes from reading the working tree. Line counts are estimates; defect line numbers are exact.

The twelve defects, and their fixes

Six are visible to you today; the rest cost time or memory. Every line number is exact and was verified against the working tree. Two design choices are settled in the table so an implementer needs none of their own: defect 1 is the narrow fix only — the OperationProgressed-as-file-content path at activity.py:193-197 is not touched, because a test pins it and it is how a read file's bytes reach the UI — and defect 5 is fixed by making the started branch match the finished one, which is also what makes a new "attributed actor" field unnecessary.

What the read path costs

Measured against the real store on this machine — 306 MB, 43 sessions, 35,720 canonical events, largest session 7,179. These three numbers are the whole performance argument:

97.7 msone session-stream tick on the largest session, against a 250 ms budget
~75%of one core, with a browser tab, a mirror and a scoreboard on that session
67 msof the 98 spent folding the same events three times over

The redundancy is the finding. statistics (engine/projections/work.py:66), background_operations (:53) and activity_after (engine/projections/paging.py:30) each run activities_of in full over the same page, at the same cursor, with the same scope — three identical folds inside one tick, where the cursor cannot have moved. Item B removes them. The other 31 ms is eight cheap single-purpose folds plus a 1.4 ms warm page read, and the first read of a session costs 481 ms once per process, which EventPages already handles.

Two things this measurement killed. The problem is not "a fold per query", which is what earlier drafts assumed and what a per-session folded state would have addressed. And the O(k²) progress rebuild that three earlier drafts used as justification does not exist at this scale: the worst operation in the entire store has 11 progress chunks, so 121 tuple copies. Items B and C take the tick to roughly 25 ms with no new types; per-event folding would take it to microseconds, which is not worth rewriting the subtlest 437 lines in the read side for. One contrast worth keeping: the mirror folds a bounded tail (terminal/panes/streams.py:130-135), which is why its cost does not grow with session length, while the dashboard folds the whole session for the same job.

One note on item J

The duplication item J removes is ~100 lines of shared semantics, not the ~257 lines of parallel rendering. The two largest rows of any duplication census survive it and should: the One-Dark syntax ladder (dashboard/render/highlight.py, 84 lines, versus terminal/mirror/highlight.py, 173) and the diff row walk (render/diff.py versus presenter._file_diff_rows) produce genuinely different things — CSS strings versus RGB values, HTML rows versus styled cells. Sharing them would mean parameterising output format, which is more machinery than the copies cost.

Item I in detail: the one new type

The cause of defect 1 is countable. The set of legal content references exists in two copies — ten mint expressions, and a hand-maintained allow-table at engine/queries/content.py:73-83 — and they drifted apart. One type puts the vocabulary in one place, with mint and parse adjacent.

Three notes, one of them a limit:

  • parse raising is boundary validation, not a fallback. engine/queries/content.py:35-37 already raises MalformedRequest for a token it cannot split; moving those three lines into the type is free.
  • The routes and query parameters do not change. ?view= and ?path= already do the job — the copy action fetches the bare URL and the view action adds the query — so there is no second route to add and nothing to delete. An earlier draft deleted them, discovered that ⧉copy on a file would then receive HTML, and proposed a /rendering sub-resource to repair self-inflicted damage.
  • It does not make defect 1 impossible. Exhaustiveness holds over slots, not over (slot, payload-type) pairs, so a UNIFIED_DIFF reference minted against the wrong event still constructs. One mint-and-resolve round-trip test per slot is what forbids that, and its absence is why defect 1 shipped. If you only ever do one thing from item I, do that test.

What I am not building

Each of these was proposed in an earlier draft and dropped. Recorded compactly so the reasoning is not re-derived — and because one pattern explains nearly all of them: a type that groups fields, renames a method, or wraps an existing cache does not remove a decision, it moves one behind a dot. Every change that survived deletes a copy of something.

A resident SessionState and a SessionStates registry
EventPages (engine/projections/pages.py, 104 lines) is already per-session, cursor-keyed, locked, and replays on a miss. A memo on it names the fold's output, which was the entire structural argument — and it keeps the property that a read can never be stale. The registry version also carried two unresolved questions of its own (what bounds its enumeration, what drives eviction), and its widest consumer, the notifier, wanted something smaller than a full state per session.
Per-event folding
~25 ms to microseconds, for a rewrite of the subtlest 437 lines in the read side. Its own proposed mitigation — keep both implementations in the tree until the suite agrees — was the signal it is not earned.
ItemLog, ActiveClock, scope.py, fold.py
paging.py is 87 lines of clear pure functions needing a memo, not a persistent vector with a cap, a cursor floor and a replay-on-underflow path. active_seconds is one function, not a three-method class for now - measured_at. And visibility.py's 12 lines answer a different question from ActivityScope — "the pane does not echo you back" versus "whose tab am I in" — so unifying them hides that.
An attributed_actor_id field
Redundant once defect 5 lands: that fix makes context.actor_id mean "the attributed actor" in all seventeen branches.
An ItemView tier — with ItemIdentity, ItemRefs, FileCounters, a five-member BodySegment union and a Role enum
~100 lines of duplicated semantics do not justify six modules and ten types built per activity per client per tick. The wrappers group fields; the segment union needed a second discriminator to be useful, which means it was the wrong one; and both palettes already hold the same RGB values, so shared constants (item L) are the fix. Item J keeps the countable part.
Renaming the two present() methods to html_item and ansi_blocks; a PaneScreen type; a version counter on the expansion service
A rename moves no boundary — the real fault is that one dispatch is an if/elif ladder the styleguide forbids (item J). PaneScreen is _MirrorModel with fields deleted. And a frozenset comparison already detects the expansion change (terminal/panes/streams.py:156-158).
Renaming opened_views to expansions
Seven files, the repository contract, the audit-debug skill, a MAIN_SCHEMA_VERSION bump and a fresh-versus-migrated database test — a migration on a 306 MB store to improve one word.
Repackaging api/dashboard, api/terminal and api/common into one resource-named api/; deleting SessionQueries
~23 test references and an edit to the architecture suite's path-hardcoded no-broker rule, for no user-visible change. The consumer-based split does leak — api/common/content.py serves both surfaces — but that is a naming irritation. And queries.py is 214 lines of one-liners whose docstring explains why that shape was chosen; it is not the problem.
An event bus; persisting projections to SQLite
The poll is cheap once the fold is memoised, and an architecture test forbids queues. A read-model table would need a migration every time a fold changed.

Open questions

  1. Do items I–L happen at all? They are optional. A–H fixes every user-visible bug and the measured cost; I–L removes duplication that costs you nothing today except the next drift bug like defect 1.
  2. The agent-note tinting is dead code today (defect 4). Table 1's fix corrects the selector to [data-actor-assignment-id] and deletes the duplicate write; say so if you would rather delete tintAgentNotes outright.

Of the three ideas this review started with, one survives in full (ContentRef), one survives shrunk to a shared module (the display layer), and one was replaced by twenty-five lines (the folded state became a memo). Five review passes and one benchmark did that — along the way finding twelve defects a redesign would have carried forward.
