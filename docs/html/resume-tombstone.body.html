The bug in one sentence

Claude Code restarted three times under one session id when the fable limit forced an account switch, and baqylau treats the first session.finished as final: the session left watchable() at 17:43:58 and nothing ever put it back.

The session still looks half alive. Hook and OTLP deliveries land on the HTTP threads and need no watcher, so tool calls and usage keep flowing; messages and reasoning come from the transcript, which only the interpreter pulls, so they stop dead.

◆
Key point: Lifecycle facts are identified by the session id alone, so a session's second run collides with its first. The resume's session.started is deduplicated, and the tombstone from run 1 outlives every later run.

Why it can never recover

Two mechanisms combine. Either one alone would be survivable.

1. Watchability tests existence, not the latest fact

Interpreter._pull() in engine/interpret/loop.py:142 iterates self.sessions.watchable(), and that query excludes a session the moment any session.finished row exists for it:

Leaving that set stops the transcript source, the subagent transcripts, the output followings and the liveness probe for good. Nothing outside this query decides what gets pulled.

2. Lifecycle facts are named after the session, not the run

The identity a translator builds is (subject_type, subject_id, phase), and for both ends of a session's life the subject id is the session id:

engine/interpret/translators.py:37 does the same for the liveness probe, deliberately: a clean exit and a kill are meant to converge on one session.finished. That convergence is right within a run and wrong across runs.

So the resumed start has nowhere to land. canonical_events keeps the first writer and does not compare bodies, which is the correct rule for an idempotent projection — it just means the second run's start is silently the same fact as the first's.

Everything downstream already handles a resume

The projections fold their events and let the last one win, so a later SessionStarted would flip them back on its own. They never see one:

That is the useful part of the diagnosis: the fix belongs where facts are named and where watchability is decided, and no view code needs to change.

The fix

Two changes, both small, and they only work together.

  1. Name the run in the lifecycle fact identity The envelope already carries harness_process_id, and one process is exactly one run — 65919, 79100, 81559 above. Use it as part of subject_id for session.started and session.finished in harness/impl/claude_code/canonical/messages.py, harness/impl/claude_code/canonical/hooks.py, engine/interpret/translators.py and the Codex equivalents. Hook, transcript and liveness within one run still carry the same pid and still converge on one fact. A session with no pid — a headless launch — falls back to the session id, which is today's behaviour.
  2. Make watchability a fold, not an existence test Exclude a session only when its latest lifecycle fact by cursor is session.finished:
Today

A session id has one start and one end for all time. The second run of an id is invisible, and the first end is permanent.

After

Each run is its own pair of facts. The last lifecycle fact decides whether the session is watched, and the projections already agree with it.

An alternative worth naming, and why not

Giving every SessionStart hook its own identity (its hook_event_id) is a smaller diff. It also breaks the convergence between the hook and the transcript record that describe the same start, so one run would emit two session.started facts. The projections tolerate that; the event store stops meaning what it says. The pid keys the fact to the thing that actually differs.

▲
Caution: A pid can be reused by the operating system. Reuse across two runs of the same session id on one machine is unlikely, and the consequence is the behaviour we have today rather than something worse.

Recovering session 498434ba

The fix cannot resurrect facts that were deduplicated three hours ago. Once it ships, restart the CLI once: the new SessionStart carries a pid that has never been seen for this session, so it produces a start fact, the session re-enters watchable(), and the transcript source resumes from position 987,347.
