Steps 1–14 are the recommendation: every defect, plus the measured cost, removing more code than they add. Steps 15–17 are a second, optional change. Each step gives the file, the exact text to replace, the exact replacement, the test, and the reason the obvious version is wrong. Apply them in order — four of them depend on an earlier one.

◆
Key point: An earlier draft proposed a resident SessionState with its own registry. It is not needed: EventPages (engine/projections/pages.py, 104 lines) is already per-session, cursor-keyed, locked and replaying-on-miss, and the redundant work is three calls to one pure function with identical arguments — so a memo on that function is twenty lines and keeps the property that makes this system debuggable, that no read can be stale.

Cost figures come from running the read path against the real store on this machine (306 MB, 43 sessions, 35,720 events, largest 7,179). Line numbers are exact as of this commit. No speculative fallbacks anywhere; audit logging is the one exception, because it is the only record left after a failure.

What the read path costs

97.7 msone session-stream tick on the largest session, against a 250 ms budget
~75%of one core, with a browser tab, a mirror and a scoreboard on that session
67 msof the 98 spent folding the same events three times

statistics (engine/projections/work.py:66), background_operations (:53) and activity_after (engine/projections/paging.py:30) each call activities_of in full over the same page, at the same cursor, with the same scope — three identical folds inside one tick, where the cursor cannot have moved. The other 31 ms is eight cheap single-purpose folds plus a 1.4 ms warm page read; a session's first read costs 481 ms once per process, which EventPages already handles.

▲
Caution: The 97.7 ms measures DashboardStreamService.frame only. api/dashboard/streams.py:128 also calls workspace.snapshot every tick, carrying the uncached full-session read that step 14 removes — so the real per-tick cost is above 98 ms, and step 14 may matter more than steps 9 and 10. Re-measure with it inside the loop before trusting "98 → 25 ms".

Two things the measurement killed. The problem is not "a fold per query", which is what a per-session folded state would have addressed. And the O(k²) progress rebuild that three earlier drafts leaned on does not exist at this scale: the worst operation in the store has 11 progress chunks. One contrast worth keeping — the mirror folds a bounded tail (terminal/panes/streams.py:130-135), which is why its cost does not grow with history, while the dashboard folds the whole session for the same job.
