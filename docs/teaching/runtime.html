1. What this layer is for

Baqylau watches coding tools it does not own. plugins/ knows how to read one such tool. dashboard/ and terminal/ know how to draw. runtime/ is everything in between: it takes what a plugin observed, stores it so it can never quietly change, and answers questions about it.

Its own docstring says the four jobs:

runtime/__init__.py:1 
"""Harness-neutral ingestion, storage, ownership, and semantic projections."""
wordwhat it means here
ingestionTake one observation, ask the right plugin what it means, write both down.
storageSQLite. Evidence tables that are append-only, and interpretation tables that are idempotent.
ownershipRemember which plugin owns which session and which actor, and refuse writes that contradict it.
projectionsFold thousands of small facts into the handful of objects a screen actually needs.

Harness-neutral is the first word for a reason. Nothing in this directory may contain the words claude, codex, transcript, or rollout — a test enforces it (tests/test_canonical_architecture.py). The runtime knows that a session has a harness, stored as a plain string, and never which one. That is what lets one storage engine and one read model serve two very different tools.

What the layer is allowed to import. domain/ (the vocabulary: events, ids, values, codec) and contracts/ (the interfaces). Nothing else. It cannot import app/, dashboard/, plugins/, or core/. So it can never call a plugin directly — it is handed one, through the registry.

2. The seven files

runtime/ ├─ database.py 20 lines — one function: how a connection is opened ├─ event_store.py 810 lines — the SQL, identity, ownership, the cursor ├─ ingest.py 29 lines — translate, then store, in that order ├─ state.py 34 lines — how far each source has been read ├─ evidence.py 113 lines — read-only: raw bytes + their interpretations ├─ registry.py 145 lines — which plugin owns which session └─ projections.py 1,381 lines — events → activities and summaries

The size distribution is the point. Over half the layer is projections.py, and every line of it is derived — you could delete the file, rewrite it differently, and lose nothing, because it holds no state of its own. The 810 lines of event_store.py are the opposite: they are the only thing standing between you and a corrupted record.

a plugin observed something │ ▼ EventPipeline.ingest() ingest.py │ asks the registry which plugin owns this harness │ calls plugin.events.translate(raw_event) ▼ EventStore.record() event_store.py — one transaction │ writes raw_events (the bytes, verbatim) │ writes translation_records (the verdict) │ writes canonical_events (the facts, if new) │ writes canonical_provenance (which bytes produced which fact) ▼ SessionQueries projections.py — reads it all back │ folds events into Activity objects and summaries ▼ a presenter turns those into blocks

3. database.py — one connection policy

Twenty lines, one function, and every SQLite connection in the canonical runtime goes through it.

runtime/database.py:11 
@contextmanager
def connect(database_path: str) -> Iterator[sqlite3.Connection]:
    connection = sqlite3.connect(database_path, timeout=10)
    connection.row_factory = sqlite3.Row
    connection.execute("PRAGMA foreign_keys=ON")
    connection.execute("PRAGMA busy_timeout=10000")
    try:
        with connection:
            yield connection
    finally:
        connection.close()

Four decisions are encoded here, and each of them would be a bug if it were made per-call-site instead.

Context manager. @contextmanager turns a function into something usable with with. Everything before yield runs on entry, everything after runs on exit — including when the body raised. That is why close() is in a finally: a connection is released whether the caller succeeded or blew up.
  • row_factory = sqlite3.Row — without it, a row is a plain tuple and you read it by position: row[3]. With it, you read it by name: row["harness"]. Every read in this layer relies on that, which is why it belongs here and not at each call site — one forgotten line and the whole file would fail with a type error.
  • PRAGMA foreign_keys=ON — SQLite disables foreign keys by default, and the setting is per connection, not per database. It cannot be turned on once when the file is created. So it has to be set on every connection, forever, which means it has to live in the one place every connection is made. Turn it off and DELETE FROM session_harness stops cascading, leaving raw events pointing at a session that no longer exists.
  • timeout=10 and busy_timeout=10000 — the same ten seconds, expressed twice because the Python driver and the SQLite engine each have their own knob. When another process holds a write lock, this connection waits up to ten seconds instead of failing immediately with database is locked. Several processes write here at once: the dashboard server, each hook invocation, the audit CLI.
  • with connection: — this is SQLite's own transaction context. On a clean exit it commits; on an exception it rolls back. That is the safety net under every write in event_store.py: a half-written record cannot survive an exception.
Note what is not here: PRAGMA journal_mode=WAL. Journal mode is a property of the database file, not of the connection — it is set once, in EventStore._initialize, and it persists. Setting it on every connection would be harmless but dishonest: it would suggest it were a per-connection concern.

4. event_store.py — the nine tables

payload is a BLOB, not TEXT, and that is deliberate. A blob is bytes; text would invite the database to think about encoding. Whatever the source produced is what comes back out, byte for byte, however malformed it was. If an interpretation later turns out to be wrong, you can re-derive it from the original — that only works if the original was never cleaned up on the way in.

runtime/event_store.py:110 
CREATE TABLE IF NOT EXISTS canonical_events(

    event_id TEXT NOT NULL UNIQUE,              -- the identity of the FACT
    schema_version INTEGER NOT NULL,
    event_type TEXT NOT NULL,
    session_id TEXT NOT NULL,
    actor_id TEXT NOT NULL,
    turn_id TEXT,
    parent_actor_id TEXT,

    accepted_at REAL NOT NULL,                  -- when we wrote it. Never null.
    payload TEXT NOT NULL                       -- canonical JSON
);
Two ids, two jobs. event_id answers "which fact is this?" — it is a hash of what the fact is (harness, session, actor, subject, phase), computed by stable_event_id() in domain/ids.py. It contains no timestamp and no payload, which is exactly why two different sources describing the same moment produce the same id. cursor answers "what came before this?" — an integer the database hands out in write order. event_id is never an ordering key and cursor is never an identity.
occurred_at is nullable and that is not an oversight. It means "when the source said this happened". A transcript line carries its own timestamp, so it is populated. A hook payload carries no clock, so it is honestly left unset rather than filled with a lie. Every read path must fall back: COALESCE(occurred_at, accepted_at). A contract test — test_no_read_path_orders_on_a_bare_occurred_at — fails any query that forgets. So a mostly-NULL column here is normal and is not worth investigating.

The provenance table

runtime/event_store.py:138 
CREATE TABLE IF NOT EXISTS canonical_provenance(
    event_id TEXT NOT NULL,
    raw_event_id TEXT NOT NULL,
    event_order INTEGER NOT NULL,
    storage_result TEXT NOT NULL CHECK(storage_result IN ('accepted', 'deduplicated')),
    PRIMARY KEY(event_id, raw_event_id),
    UNIQUE(raw_event_id, event_order)
);

Three things fall out of those constraints:

  • One raw event may produce several facts — event_order keeps them in the order the translator emitted them.
  • One fact may come from several raw events — that is convergence, and it is why the primary key is the pair.
  • storage_result records which write created the row (accepted) and which merely re-observed it (deduplicated). When two sources disagree about a fact, this column tells you whose version is the one you are looking at.

5. Opening the store, and the version guard

runtime/event_store.py:207 
def _initialize(self) -> None:
    with connect(self.database_path) as connection:
        connection.execute("PRAGMA journal_mode=WAL")
        connection.executescript(SCHEMA)
        row = connection.execute(
            "SELECT value FROM event_store_metadata WHERE name='schema_version'"
        ).fetchone()
        if row is None:
            connection.execute(
                "INSERT INTO event_store_metadata(name, value) VALUES('schema_version', ?)",
                (str(SCHEMA_VERSION),),
            )
        elif row["value"] != str(SCHEMA_VERSION):
            raise EventStoreError(f"unsupported event-store schema version: {row['value']}")
    os.chmod(self.database_path, 0o600)
WAL — write-ahead logging. SQLite's default mode makes writers block readers. WAL sends writes to a side file, so readers keep reading the last committed state while a write is in flight. This matters because the dashboard reads continuously — four times a second — while hooks write at unpredictable moments. It also has a practical consequence for debugging: a plain cp of a WAL database gives you a corrupt copy, because the data you need is partly in the side file. Use sqlite3 "file:<path>?mode=ro" ".backup '<dest>'".

The version check is a refusal, not a repair. There is no migration code anywhere in the repository. When domain.codec.SCHEMA_VERSION is bumped, a store written by the old version will not open, and the process that tried to open it dies.

What that looks like when it happens. The dashboard crash-loops. The operational audit fills with unsupported event-store schema version: N, and beside it a long run of dashboard serve (lock denied) rows every ten seconds — the supervisor retrying against a port the dying process still holds. Both signatures are in the audit-debug skill. The fix is to get code and store to the same version, never to edit the metadata row.

os.chmod(0o600) is the last line for a reason: this file contains the full text of every prompt and every file the agent read. Owner-only, always. The directory is created with mode=0o700 in the constructor for the same reason.

6. Ownership: who is allowed to speak for a session

Before any event can be stored, its session must be registered — a row in session_harness saying which plugin owns it. This is what makes a foreign key on every raw event possible, and it is checked on every write.

runtime/event_store.py:223

    ...

        if existing_owner != values[:3]:
            raise HarnessOwnershipConflict(f"conflicting owner for session {session.session_id}")

Registration is idempotent for the identity, updating for the details. Read the slice carefully: the first three values are lead_actor_id, harness, native_session_id — the things that make this session this session. Those may never change; a second registration claiming otherwise raises. The remaining fields — source_reference, working_directory, native_process_id — are updated, because they legitimately do change: a session moves directory, a file is rotated, a process is restarted.

Note the COALESCE on the process id:

"native_process_id=COALESCE(?, native_process_id)"

A registration that does not know the process id passes None, and COALESCE keeps the value already stored. Without it, an observer that happens not to see the process would erase what another observer learned. Not knowing is not the same as knowing it is absent, and this one SQL function is where that distinction is enforced.

7. record() — the write path, line by line

This is the most important method in the layer. Everything it does happens in one transaction, opened with BEGIN IMMEDIATE.

BEGIN IMMEDIATE. SQLite's default (BEGIN DEFERRED) takes a read lock first and only upgrades to a write lock at the first write — and that upgrade can fail with database is locked after you have already read and decided. IMMEDIATE takes the write lock up front. So a concurrent writer waits at the door instead of halfway through, and the decisions made inside cannot be invalidated by someone else writing while you think.

Step 1 — has this evidence been seen before?

runtime/event_store.py:395 
existing_raw = connection.execute(
    "SELECT session_id, harness, source_type, … , encoding, payload "
    "FROM raw_events WHERE raw_event_id=?", …
).fetchone()
if existing_raw is not None:
    if tuple(existing_raw) != _raw_identity(raw_event):
        raise EventIdentityConflict(f"raw event identity reused: {raw_event.raw_event_id}")
    return self._verify_recorded_translation(…)

Sources are re-read constantly — a transcript file is drained from its checkpoint every 0.25 seconds, and the same lines are often offered again. So arriving at an already-stored raw event is normal. What is compared is every field including the payload bytes (_raw_identity, line 179). Same id and same bytes: fine, this is a re-read. Same id and different bytes: the id is a lie, and that is corruption, not convergence. Note the asymmetry with canonical events, where bodies are deliberately not compared — evidence must be identical, interpretations need not be.

Step 2 — is the session registered?

runtime/event_store.py:587 
def _verify_registered_session(self, connection, raw_event) -> None:
    row = … "SELECT lead_actor_id, harness FROM session_harness WHERE session_id=?" …
    if row is None:
        raise EventStoreError(f"unregistered session: {raw_event.session_id}")
    if str(raw_event.actor_id) == row["lead_actor_id"] and raw_event.harness != row["harness"]:
        raise HarnessOwnershipConflict(…)
    actor_owner = … "SELECT harness FROM actor_harness WHERE session_id=? AND actor_id=?" …
    if actor_owner is not None and actor_owner["harness"] != raw_event.harness:
        raise HarnessOwnershipConflict(…)
    connection.execute(
        "INSERT OR IGNORE INTO actor_harness(session_id, actor_id, harness) VALUES(?, ?, ?)", …)

The last statement is easy to miss and does real work: actors register themselves on first sight. Nobody announces a subagent in advance. The first event carrying a new actor_id creates its ownership row, and every later event from that actor is checked against it. INSERT OR IGNORE makes that safe to run on every single write.

Step 3 — write the evidence and the verdict

The raw event goes in. Then exactly one translation_records row, carrying the plugin's version string and its decision:

decisionmeaninghow common
translatedProduced one or more canonical events.Common.
ignored_nonsemanticPlumbing the translator deliberately drops.Very common — expected in bulk.
ignored_unknownA record shape this translator has no rule for.Common. Only interesting when a missing thing matches it.
translation_failedThe translator raised. reason says why.Rare, and the actionable one.

The CHECK constraint in the schema means a fifth value cannot be invented without a schema change. And the verdict is stored even when nothing came of it — that is why "nothing appeared" is always answerable: either there is no raw event (the source never produced it) or there is a verdict saying why it produced nothing.

The provenance row is written whether or not the event was new. That is the whole mechanism of convergence: a second source describing the same fact adds a link, not a row. The caller gets back an EventRecordResult (line 53) that separates the two:

@dataclass(frozen=True)

That split is what lets the delivery layer act only on news — a notification should fire when a fact is learned, not every time it is re-observed.

8. The eight invariants of a canonical write

_record_canonical_event (line 629) checks eight things before writing. Each is a rule the rest of the system is then free to assume, and each raises rather than storing something questionable.

#rulewhy it exists
1The event's session_id equals its raw event's.A fact cannot be filed under a session other than the one whose bytes produced it.
2Its harness equals its raw event's.Same reason. A translator cannot attribute its output to another tool.
3Its actor_id equals its raw event's.Keeps per-actor filtering trustworthy: an actor's feed is exactly what that actor's evidence produced.
4Its parent_actor_id equals its raw event's.The actor tree comes from evidence, not from a translator's guess.
5The session is registered.Nothing may be written about a session nobody owns.
6Session-level events use the lead actor.session.started, .title_changed, .working_directory_changed, .account_changed, .finished describe the whole session; a subagent may not claim to have started it.
7ActorStarted.role == "lead" exactly when the actor is the registered lead.Two sources of truth about leadership — the recognized session and the event payload — must agree.
8An actor is not its own parent.A one-line check that stops an infinite loop in every tree walk downstream.

Rule 7 is the one worth pausing on. (A) != (B) on two booleans is "these disagree" — it catches both directions in one line: a lead actor whose event says it is a subagent, and a subagent whose event claims to be lead.

9. Convergence — the branch that does nothing

Just before the insert, the store looks for the event id. If it is there, it returns without writing — and the comment explaining that is longer than the code, because the reasoning is not obvious and was learned the hard way.

runtime/event_store.py:680 
if existing is not None:
    # A canonical event is an IDEMPOTENT projection: the identity names the fact,
    # so re-observing it is a no-op that only adds provenance. Several independent
    # sources legitimately converge here and may render one fact differently; the
    # first writer stays authoritative. Nothing is lost by not comparing the
    # bodies -- the later rendering is fully recoverable from its own raw event,
    # which is stored verbatim and linked below. Raising on a disagreement instead
    # used to abort the whole observation pass and killed the scheduler thread.
    return self._stored_event(connection, existing), "deduplicated"

Three claims, in order:

  1. The identity names the fact, not the observation. stable_event_id() hashes what happened — harness, session, actor, subject, phase — and deliberately excludes the timestamp and the payload. So a hook and a transcript, describing the same message from different angles, compute the same id. That is by design.
  2. The first writer wins, and the bodies are not compared. Two sources may render one fact with different detail. Whichever landed first is what you see.
  3. Nothing is lost. The loser's rendering is still in raw_events, byte for byte, and the provenance row points at it. python3 bin/baqylau-audit.py raw <raw_id> shows exactly what it said.
The last sentence is a scar. An earlier version raised when two observations of one fact disagreed. That exception escaped into the observation pass and killed the scheduler thread — and because pushed sources (hooks, otel) kept flowing, every session still looked alive while its conversation silently stopped. This is the headline failure mode in the audit-debug skill. If the stored rendering is ever the poorer of two, the fix belongs in the ordering or in the identity derivation. Not here.

10. Replay — what happens the second time

When the same raw event arrives again, _verify_recorded_translation (line 714) does not re-write anything. It checks that the interpretation has not changed:

  1. The translation record matches — same version, same decision, same reason.
  2. The provenance rows list the same event ids, in the same order.
  3. Each canonical event re-encodes to byte-identical JSON against what is stored.
if canonical_row is None or self._encoded_row(canonical_row) != self.codec.encode(event):
    raise EventIdentityConflict(f"canonical output changed for raw event {raw_event.raw_event_id}")

This is a determinism check on the translators. The same bytes must always yield the same events. If someone writes a translator that reads the wall clock, or iterates a set, or depends on state accumulated earlier in the run, this is what catches it — on the next re-read, which in practice is a quarter of a second later.

Byte-identity is possible because both sides go through the same canonical encoding: sort_keys=True, separators=(",", ":"), ensure_ascii=False. _encoded_row (line 796) rebuilds the document from columns in sorted key order and encodes it the same way, so a stored row and a freshly translated event are comparable as bytes rather than as objects.

record_failure

When a translator raises TranslationError, the evidence is still stored — with a verdict of translation_failed and a reason:

runtime/event_store.py:453 
reason = error.reason if error.context is None else f"{error.reason}: {error.context}"

Real examples from the store: unmapped Codex tool: write_stdin, Codex write_stdin targets finished operation: <call_id>. A missing feature whose reason says "unmapped" is a translator gap, not a data loss — the bytes are safe, and the moment a rule exists the evidence translates. This is why the failure path stores rather than discards.

12. ingest.py — the pipeline

Twenty-nine lines, and the only place in the system where translation is invoked.

runtime/ingest.py:10 
class EventPipeline:
    def __init__(self, registry: HarnessRegistry, event_store: EventStore) -> None:
        self.registry = registry
        self.event_store = event_store

    def ingest(self, raw_event: RawEvent) -> IngestionResult:
        plugin = self.registry.plugin(raw_event.harness)
        try:
            translation = plugin.events.translate(raw_event)
        except TranslationError as error:
            return self.event_store.record_failure(raw_event, plugin.info.plugin_version, error)

        recorded = self.event_store.record(raw_event, plugin.info.plugin_version, translation)
        return IngestionResult(…)

Read the order: translate first, store second, always. Both outcomes end in a write. There is no path through this function that leaves an observation unrecorded — success writes evidence plus facts, failure writes evidence plus a reason.

Note plugin.info.plugin_version being passed to both. Every verdict is stamped with the version of the code that made it. When an interpretation turns out to be wrong, you can find every row produced by the version that made the mistake.

Note also what this class does not do. It does not decide what to observe, it does not schedule, it does not retry, it does not catch anything except TranslationError. A bug inside a translator that raises something else propagates — and it is the caller's job (ObservationRunner in app/observe.py) to contain it per-source and audit the swallow. The pipeline stays honest about what it saw.

    def commit(self, checkpoint: SourceCheckpoint) -> None: …

It implements the CheckpointStore protocol from contracts/harness.py and says so in the class line — this repository requires that declaration and tests for it. position is a TEXT column, not an integer, because only the source knows what a position means: a byte offset, a line number, a record id, a composite string. The runtime stores it and never interprets it.

The write is an upsert:

"INSERT INTO source_checkpoints(source_identity, session_id, position) VALUES(?, ?, ?) "
"ON CONFLICT(source_identity) DO UPDATE SET "
"session_id=excluded.session_id, position=excluded.position"

excluded is SQLite's name for the row you tried to insert. So: insert if new, overwrite if it exists — one statement, no read-then-write race.

Why this is in state.py and not in the event store. The file's docstring is the rule: "small runtime coordination state that is not canonical activity". A checkpoint is not something the session did; it is something we did. Delete every checkpoint and no history is lost — every source simply re-reads from the start and the store deduplicates. That is a real recovery procedure, and it only works because checkpoints are not evidence.
A stuck checkpoint is the single most diagnostic value in the store. Compare source_checkpoints.position against the real size of session_harness.source_reference. A position far below the file size, frozen, with the file still growing, is conclusive proof that a source stopped draining. A measured instance: position 10,744 of 527,284 bytes — twelve lines of 165 — with exactly two messages recorded for a session that had run for hours.

16. projections.py — what a projection is

The store holds thousands of small facts. A screen needs a few dozen objects. Turning the first into the second is a projection, and the file's docstring names the technique:

runtime/projections.py:1 
"""Harness-neutral semantic read models folded from canonical facts."""
Fold. Start with an empty result. Walk a sequence in order. For each item, update the result. Return it. That is all "fold" means, and every function in this file is one — the state is a dictionary, the sequence is events in cursor order, and the update is a chain of isinstance checks.
Read model. A shape built for reading, thrown away afterwards, never stored. Nothing in this file is persisted. Change how a summary is computed and the next read reflects it immediately, with no migration, because the facts underneath did not change.

An example, small enough to hold in your head — the whole of the goal projection:

18. SessionQueries and its two caches

Every projection folds from the beginning of the session. A long session has tens of thousands of events, the dashboard polls four times a second, and re-reading everything each time would be untenable. Two caches make it work.

_page — the incremental cache

runtime/projections.py:425

Three cases, and the first is the common one:

  1. The cache is behind. Fetch only the gap with between() and append. A poll that finds three new events reads three rows, not thirty thousand.
  2. Nothing cached, or the cursor moved backwards. Read the whole thing with through(). Backwards happens when a caller asks for a historical through_cursor — time-travel for debugging.
  3. The cursor is unchanged. Return what is cached, touching the database only for the cheap MAX(cursor) that got us here.

The cache is safe because canonical events are append-only. A stored event never changes, so an old page can never be stale — it can only be incomplete, and the cursor says by exactly how much. That property comes straight from the write path, and it is what buys the read path its speed.

RLock. A re-entrant lock: the same thread may acquire it more than once without deadlocking itself. It is needed because the dashboard runs the observation scheduler in one thread and serves requests on others, all sharing one SessionQueries. A plain Lock would hang the moment one locked method called another.

_tail_page — the fixed-key cache

Keyed by (session_id, event_limit) and valid only while the cursor matches exactly. It serves the opening of a view: the last few hundred events, without the full history. No incremental extension here, because a tail's contents shift at both ends as new events arrive.

And an operation finishing must not clear a prompt that is still on screen. Without that check, a tool completing behind a permission dialog would turn the tab from "needs you" to "working" while it sat there waiting.

There are two entry points, and their difference is the initial value:

def tab_state(self, session_id, through_cursor=None):
    return self._tab_state(self._page(session_id, through_cursor).events, None)

def tab_state_tail(self, session_id, event_limit, through_cursor):
    events = self._tail_page(session_id, event_limit, through_cursor).events
    return self._tab_state(events, "idle")

The full fold starts at None — no session.started seen means no state, which is how "this is not a session" is expressed. The tail starts at "idle", because it begins mid-session and will never see the start; assuming idle and letting the recent events correct it is right, while returning None would blank a live tab.

How to add a projection

  1. Add the read-model dataclass, frozen, near its relatives.
  2. Add a method on SessionQueries taking (session_id, through_cursor=None) and folding self._page(...).events.
  3. Ignore every payload you do not care about. Never assume ordering beyond cursor order, and never assume the start event is present.
  4. If it is a new Activity type, add it to the Activity alias and handle it in both presenters — they raise TypeError otherwise, which is the point.
  5. No migration is needed. The facts are already stored; you are only reading them differently.

24. Where model.changed falls out

A concrete, current example of how to read this layer — and of a gap that is still open.

When a session's model changes, a model.changed event is stored correctly. Three projections consume it:

  • summary() — updates SessionSummary.model, for the lead actor only (line 513).
  • actors() — updates that actor's ActorSummary.model (line 604).
  • context() — remembers the model so a later context report can be attributed to it (line 752).

Now search _activities for ModelChanged. It is not there. The fold has branches for messages, reasoning, operations, files, attention, tasks, compaction, assignments, and actor messages — and no branch for ModelChanged or EffortChanged. So the event reaches the store, updates the cards at the top of the view, and produces no entry in the feed.

Why it looked like it worked for one harness and not the other. Claude Code's translator emits a message.created for the /model opus you typed, alongside the state event. That message has a branch in the fold, so something appeared — but it was the message, not the model change. Codex has no such message, so nothing appeared at all. The difference was never in the rendering; it was in what each harness happened to produce. That is exactly the shape of bug this layout is meant to make visible: if a fact does not have a branch in _activities, it will never reach a feed, no matter how correctly it is stored.

The fix is a tenth activity type with a branch in the fold and a case in both presenters, at which point both harnesses render identically because both already emit the event. Nothing in the store needs to change.
