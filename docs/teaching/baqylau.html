Part I

How a session becomes pixels

The whole pipeline end to end: sources, evidence, translation, canonical facts, projections, presenters, delivery — and one worked example.

1. The problem the design solves

Baqylau watches coding sessions that it does not own. Claude Code and Codex are separate programs, written by other people. They record what they do in their own file formats, and they change those formats without warning — you saw this today, when codex-cli 0.147.0 removed a screen that 0.144.1 had.

Two things follow, and the whole architecture is built on them.

First: the record must be kept before it is understood. If baqylau only stored its own interpretation of a transcript line, then a bug in that interpretation would destroy the evidence permanently. So the raw bytes are stored first, unchanged, forever. Interpretation is a second, separate step that can be fixed and re-run.

Second: the interpretation must be shared. If the web page knew that Claude Code writes isMeta and codex writes thread_settings_applied, then every new harness would mean editing the page, the terminal renderer, and everything in between. So both harnesses are translated into one vocabulary, and everything downstream speaks only that.

The second rule is not a convention. It is a test:

tests/test_canonical_architecture.py:148 
def test_canonical_shared_code_contains_no_concrete_harness_vocabulary():
    shared_paths = [ROOT / "app", ROOT / "contracts", ROOT / "core",
                    ROOT / "dashboard", ROOT / "domain", ROOT / "frontends",
                    ROOT / "runtime", ROOT / "terminal"]
    concrete_words = ("claude", "codex", "anthropic", "openai", "rollout", "transcript")
    ...
    assert violations == []

The words claude, codex, rollout and transcript may not appear anywhere in those eight directories — not in code, not in a comment, not in a docstring. Earlier today I wrote the word "codex" in a comment in app/services.py and this test failed the build.

Why this matters to you. When you said "the UI is harness-agnostic, as long as canonical events are fired they should render uniformly" — that is not your preference, it is the enforced contract of this repository. So a canonical event that renders for one harness and not another is a defect by definition.

2. The five stages, in one view

Data moves in one direction. Nothing flows backwards.

1
Source
A file on disk, or a process that pushes to us. Produces bytes.
→ app/observe.py, plugins/*/canonical.py
2

→ table raw_events in events.db
3

A harness plugin reads the bytes and says what happened, in the shared vocabulary. This is the last place harness-specific knowledge is allowed.
→ plugins/claude_code/canonical.py, plugins/codex/canonical.py

→ domain/events.py, runtime/event_store.py
5

Replays the events in order and folds them into things worth drawing: activities, summaries, context windows.

6

3. The file tree, layer by layer

The directories are a dependency ladder, and the order below is that ladder. A layer may import the layers above it and never the ones below. domain/ at the top imports nothing but the standard library; dashboard/ and terminal/ at the bottom import a great deal and are imported by nothing.

4. Stage 1 — Sources: pulled and pushed

Bytes reach baqylau in two different ways, and the difference explains an entire class of bug.

Pulled sources polled by us

A file we read on a timer. One thread does all of it:

app/observe.py:11 
OBSERVATION_INTERVAL_SECONDS = 0.25
RECENT_SESSION_COUNT = 4

It runs as a daemon thread inside the dashboard server process:

dashboard/http/handler.py:90

    target=application.observation_runner.run,
    args=(observation_stop,),
    daemon=True,
    name="baqylau-observation",
)
observation_thread.start()

One pass asks every registered plugin for its sources, for every active session, and drains each one:

app/observe.py:55 
def run_once(self) -> None:
    for registered_session in self.registry.recently_observed_sessions(RECENT_SESSION_COUNT):
        self._active_sessions[registered_session.session.session_id] = registered_session
    for session_id, registered_session in tuple(self._active_sessions.items()):
        if self.registry.session_is_finished(session_id):
            del self._active_sessions[session_id]
            continue
        for plugin in self.registry.plugins():
            for source in plugin.events.sources(registered_session.session, self.checkpoints):
                self._drain(source, session_id)

Three things in that loop are deliberate:

  • The session set is sticky. _active_sessions accumulates and only drops a session that has a session.finished event. So a fifth concurrent session is not starved by RECENT_SESSION_COUNT = 4.
  • Sources are rebuilt every pass. plugin.events.sources(...) is called inside the loop. Source objects hold no durable state; everything about position lives in the checkpoint table. That is how a subagent's transcript file that appears mid-session is picked up 250ms later with no special code.
  • Every plugin is asked about every session. Each plugin's sources() declines what it does not own. That is how a codex sidecar can attach to a Claude session.

The failure containment is the interesting part, and its comment says why:

app/observe.py:48 
# The scheduler thread must outlive every failure it can observe: it is the ONE
# driver of every polled event source, and nothing restarts it. An unguarded
# exception here once killed observation for EVERY session silently -- the
# conversation simply stopped arriving while the sources written by separate
# processes kept flowing, so the session still looked alive.
while not stop_event.is_set():
    try:
        self.run_once()
    except Exception:
        _audit_failure("observation pass", {})

Pushed sources they call us

Hooks, OTEL telemetry, and account changes are written by separate short-lived processes. Claude Code runs plugins/claude_code/canonical_hook.py directly on every hook event; that process builds its own application object, delivers its raw events, and exits.

The asymmetry that matters. When the observation thread dies, pulled sources freeze but pushed sources keep flowing. The session therefore keeps producing hook and usage events and looks alive, while its conversation silently stops. This exact failure has happened, which is why the containment above exists and why every swallow is audited.

How one pulled source reads a file

This is the pattern every file source follows. Read it once and you know them all:

plugins/claude_code/canonical.py:158 
def drain(self, delivery: RawEventDelivery) -> None:
    checkpoint = self.checkpoints.load(self.source_identity)
    position = int(checkpoint.position) if checkpoint is not None else 0
    with open(self.source_path, "rb") as source:
        source.seek(position)
        for _ in range(self.EVENT_BATCH_SIZE):          # 100
            line_position = source.tell()
            line = source.readline()
            if not line or not line.endswith(b"\n"):
                return                                   # partial line: stop, do not commit
            raw_event = RawEvent(
                raw_event_id=RawEventId(f"{self.source_identity}:{line_position}"),
                ...
                source_position=str(line_position),
                encoding="jsonl",
                payload=line,                            # the bytes, verbatim
            )
            delivery.deliver(raw_event)
            position = source.tell()
            self.checkpoints.commit(SourceCheckpoint(
                self.context.session_id, self.source_identity, str(position),
            ))

Four details carry weight:

  1. The partial-line guard. A JSONL line that does not end in a newline is still being written. It is not delivered and the checkpoint is not advanced, so the next pass re-reads it from the same byte. This is the entire defence against reading a half-written record.
  2. Deliver first, commit second. If the process dies in between, the line is delivered twice — which is harmless, because of the identity rules in stage 4. If it committed first, a crash would lose the line forever.
  3. The batch is bounded at 100 lines per source per pass, so one enormous backlog cannot starve the other sources.
  4. The source identity is derived from the file path only — sha256(realpath). Not from the session, not from the object. That is why the checkpoint survives a restart: the rebuilt source computes the same identity and resumes at the same byte.

You saw this table earlier today. When you asked why the codex feed stopped, the first thing I checked was:

-- codex:rollout:664c85f8…  |  40727

$ stat -f%z rollout-…01a00391….jsonl

5. Stage 2 — raw_events: evidence that never changes

A RawEvent is a frozen record of one observation:

contracts/harness.py:30 
@dataclass(frozen=True)
class RawEvent:
    raw_event_id: RawEventId       # replay-stable and unique. Never random.
    harness: str                   # which plugin produced it
    source_type: str               # "transcript" | "rollout" | "hook" | "otel" | …
    source_name: str               # the file path, or the hook channel name
    source_position: str           # byte offset, or the native event id
    session_id: SessionId          # known BEFORE delivery — never guessed later
    actor_id: ActorId              # the lead, or a subagent
    parent_actor_id: ActorId | None
    observed_at: float             # when WE received it
    encoding: str                  # "json" | "jsonl"
    payload: bytes                 # the complete raw bytes, newline included

raw_event_id must be reproducible: for a file source it is "{source_identity}:{byte_offset}". Reading the same line twice produces the same id, which is what makes re-delivery safe.

The store enforces that promise:

runtime/event_store.py:402 
if existing bytes differ:
    raise EventIdentityConflict("raw event identity reused")

If the same id ever arrives with different bytes, that is corruption and it is refused loudly. If it arrives with identical bytes, the store short-circuits and reports everything as duplicate — which is what makes a full re-read of a file free.

7. Stage 4 — canonical_events: identity, convergence, cursor

There are exactly 33 event types, catalogued in full in the next section. First, the three properties that make the store work.

The envelope: what is authored and what is assigned

    session_id: SessionId

Notice what is not there. event_type and schema_version are not fields — the codec adds them at encode time, derived from the payload's class. A plugin therefore cannot label a MessageCreated as operation.finished; the discriminator is not in its hands.

event_id — computed from the factcursor — the order we saw it
occurred_at — when the harness says it happenedaccepted_at — when we committed it

The codec also refuses presentation data structurally, checked at startup over every registered payload class:

Identity: what makes two observations "the same fact"

An event's id is computed, not generated:

domain/ids.py:20 
def stable_event_id(*, harness, session_id, actor_id, subject_type, subject_id, phase):
    """Build the same event identity for every observation of one native fact."""
    identity = "\x1f".join(
        (harness, str(session_id), str(actor_id), subject_type, subject_id, phase)
    )
    digest = hashlib.sha256(identity.encode("utf-8")).hexdigest()
    return CanonicalEventId(f"{harness}:{subject_type}:{digest}")

Read the inputs carefully. There is no timestamp and no payload. The id answers "which fact is this?" — not "when did we see it?" or "what did it say?". So the same fact, observed twice, from two different files, by two different sources, computes the same id.

The join character is \x1f, the ASCII unit separator, because it cannot occur in any native id — so ("a","bc") and ("ab","c") cannot be confused for each other. The harness and subject type stay in plaintext in front of the digest, so an id is greppable.

This is the concept you asked about, and it has one rule:

runtime/event_store.py:680 
if existing is not None:
    # A canonical event is an IDEMPOTENT projection: the identity names the fact,
    # so re-observing it is a no-op that only adds provenance. Several independent
    # sources legitimately converge here and may render one fact differently; the
    # first writer stays authoritative. Nothing is lost by not comparing the
    # bodies -- the later rendering is fully recoverable from its own raw event,
    # which is stored verbatim and linked below. Raising on a disagreement instead
    # used to abort the whole observation pass and killed the scheduler thread.
    return self._stored_event(connection, existing), "deduplicated"

Three consequences, and they are the whole of convergence:

  1. The first writer wins. The stored event body is whoever got there first.
  2. Bodies are never compared. A second observation that describes the fact better is discarded from the canonical row. It is not lost — its raw bytes are stored and linked — but it is not what the UI reads.
  3. Every observation is linked anyway, in canonical_provenance, with storage_result being accepted or deduplicated. So you can always ask "which sources claimed this fact?"

This is why I told you the two model events cannot be merged. If the /model opus command and the later assistant record converged on one id, the command would win — and the command only knows the word opus, not claude-opus-5. We would have deliberately locked in the poorer version.

The strictness is asymmetric, and that is the design

EventIdentityConflict sounds like it would fire on the convergence above. It never does. It is entirely about one raw event replaying inconsistently:

situationbehaviour
same raw_event_id, different bytesraises — "raw event identity reused"
same raw event, same bytes, but the translator now produces something differentraises — "canonical output changed". This is the one place bodies are compared, byte-exactly.
same raw event, same bytes, same translationno-op; everything reported as duplicate
different raw events, same event_id, different bodiessilently deduplicated; first writer wins; no comparison, no error

Raw evidence is held to byte-exact reproducibility. Canonical events across independent observers are held only to agreement about identity. That asymmetry is what lets many sources describe one session without fighting.

Note also that observed_at is deliberately excluded from the raw identity comparison — re-reading the same transcript line an hour later is a legal replay, not a conflict.

The cursor: the one ordering key

canonical_events.cursor is INTEGER PRIMARY KEY AUTOINCREMENT. It is the only ordering key. event_id is a hash and orders nothing; occurred_at is nullable by design, because a hook payload carries no clock of its own.

There are three separate clocks, and confusing them causes real bugs:

columnmeaning
raw_events.observed_atwhen baqylau received the bytes
canonical_events.accepted_atwhen the store committed the fact
canonical_events.occurred_atwhen the harness said it happened — NULL when the source has no clock

Every reader must fall back: COALESCE(occurred_at, accepted_at). A contract test named test_no_read_path_orders_on_a_bare_occurred_at forbids ordering on the bare column.

The schema version, and why the store refuses to open

SCHEMA_VERSION is currently 13. It is checked in two places, and the second explains a whole class of "the dashboard is down" reports:

runtime/event_store.py:207 
row = connection.execute(
    "SELECT value FROM event_store_metadata WHERE name='schema_version'").fetchone()
if row is None:
    connection.execute(
        "INSERT INTO event_store_metadata(name, value) VALUES('schema_version', ?)",
        (str(SCHEMA_VERSION),))

    raise EventStoreError(f"unsupported event-store schema version: {row['value']}")

A fresh database is stamped with the version that created it. An existing one whose stamp disagrees makes the EventStore constructor raise — the store refuses to open at all, rather than read rows it might misread. The visible symptom is a server that crash-loops, with a run of dashboard serve (lock denied) rows in the operational audit as the supervisor retries against a port the dying process still holds.

The comparison is exact equality, not "at least" — a database written by newer code is refused just as firmly as an old one.

With the pipeline in view, the defect is precise and small.

The fix is therefore at stage 5, and it is where the intelligence has to live anyway: the projection is the only layer that sees the ordered stream, so it is the only layer that can say "this value differs from the last one" and fill in previous. A translator cannot, because it must stay replayable — if it suppressed events based on memory, re-reading a file from a checkpoint would produce different events and break the idempotence that stage 4 depends on.

1. The idea in one page

Baqylau watches coding tools it does not own — Claude Code, Codex — and shows them in one interface. Those tools have nothing in common: different files, different formats, different ways of being controlled.

contracts/harness.py is the list of questions baqylau is allowed to ask a tool, and the shapes of the answers. Its first line says exactly that:

"""The complete public contract implemented by every harness plugin."""

"Harness" is this codebase's word for one such tool. Claude Code is a harness. Codex is a harness. A plugin is the adapter that answers the contract's questions for one harness.

The file contains two kinds of thing, and telling them apart is most of understanding it:

kindwhat it isexample

2. Four words you need first

Protocol. A Python class that lists method names and signatures with no bodies — the bodies are literally .... It describes a shape. Any class with matching methods satisfies it, whether or not it says so. That is called structural typing: the compiler checks the shape, not the family tree. 
class HarnessHook(Protocol):
    def receive(self, payload: bytes) -> HookIntake: ...
This is convenient and it is also a trap, because a class can drift out of the shape in silence — rename a parameter and nothing objects until something breaks at runtime. That is why this repository requires implementations to name the Protocol they implement (class ClaudeHook(HarnessHook):) and has a test that fails when one does not.
Frozen dataclass. @dataclass(frozen=True) generates a class from a list of typed fields, and makes it immutable — assigning to a field after construction raises. Nearly every noun in this file is one. Immutability matters because these objects are passed between threads and stored as evidence; a value that can be edited after the fact is not evidence.
TypeAlias / Literal. Literal["started", "finished"] means "this string may only ever be one of these two". It is a closed set, checked by tools and by tests. When you see one, read it as a complete list of the possibilities — there is no thirteenth control name hiding somewhere.
Actor. Not a Python concept — this codebase's word for anything that acts inside a session. The main agent is an actor (the lead). Each subagent it spawns is an actor. A teammate is an actor. Every piece of evidence carries an actor_id saying who did it, which is how the interface can filter a whole view down to one subagent.

For a file source the id is "{which file}:{byte offset}", so re-reading line 40 produces the same id, and the store recognises it as something it already has. Random ids would fill the database with duplicates.

payload is the whole bytes, newline included, never trimmed or prettified. It is the evidence.

The four ideas that recur

  1. Separate collecting from understanding. sources and translate are two methods for this reason. Bytes we cannot interpret are still kept, and can be re-interpreted when the interpreter improves.
  2. Hand in capabilities; do not let components reach. RawEventDelivery, CheckpointStore, SessionLifecycleContext, TerminalControl, TerminalScreen are all passed in. A plugin can do exactly what it was handed the means to do — which makes it testable, and bounds what a bug in it can reach.
  3. Closed lists over free strings. Fourteen control names, three statuses, four verdicts, two lifecycle actions. Every one is a Literal, so "did we handle them all?" is a question a tool can answer.
  4. Make the impossible unconstructible. TranslationResult.__post_init__ refuses a contradictory verdict at the moment of creation, rather than letting it travel and fail somewhere far away.

The runtime layer

All seven files in runtime/: the write path and its invariants, convergence, ownership, and every projection.

1. What this layer is for

Baqylau watches coding tools it does not own. plugins/ knows how to read one such tool. dashboard/ and terminal/ know how to draw. runtime/ is everything in between: it takes what a plugin observed, stores it so it can never quietly change, and answers questions about it.

Its own docstring says the four jobs:

runtime/__init__.py:1 
"""Harness-neutral ingestion, storage, ownership, and semantic projections."""
wordwhat it means here
ingestionTake one observation, ask the right plugin what it means, write both down.
storageSQLite. Evidence tables that are append-only, and interpretation tables that are idempotent.
ownershipRemember which plugin owns which session and which actor, and refuse writes that contradict it.
projectionsFold thousands of small facts into the handful of objects a screen actually needs.

Harness-neutral is the first word for a reason. Nothing in this directory may contain the words claude, codex, transcript, or rollout — a test enforces it (tests/test_canonical_architecture.py). The runtime knows that a session has a harness, stored as a plain string, and never which one. That is what lets one storage engine and one read model serve two very different tools.

What the layer is allowed to import. domain/ (the vocabulary: events, ids, values, codec) and contracts/ (the interfaces). Nothing else. It cannot import app/, dashboard/, plugins/, or core/. So it can never call a plugin directly — it is handed one, through the registry.

2. The seven files

The size distribution is the point. Over half the layer is projections.py, and every line of it is derived — you could delete the file, rewrite it differently, and lose nothing, because it holds no state of its own. The 810 lines of event_store.py are the opposite: they are the only thing standing between you and a corrupted record.

3. database.py — one connection policy

Twenty lines, one function, and every SQLite connection in the canonical runtime goes through it.

runtime/database.py:10 
@contextmanager
def connect(database_path: str) -> Iterator[sqlite3.Connection]:
    connection = sqlite3.connect(database_path, timeout=10)
    connection.row_factory = sqlite3.Row
    connection.execute("PRAGMA foreign_keys=ON")
    connection.execute("PRAGMA busy_timeout=10000")
    try:
        with connection:
            yield connection
    finally:
        connection.close()

Four decisions are encoded here, and each of them would be a bug if it were made per-call-site instead.

Context manager. @contextmanager turns a function into something usable with with. Everything before yield runs on entry, everything after runs on exit — including when the body raised. That is why close() is in a finally: a connection is released whether the caller succeeded or blew up.
  • row_factory = sqlite3.Row — without it, a row is a plain tuple and you read it by position: row[3]. With it, you read it by name: row["harness"]. Every read in this layer relies on that, which is why it belongs here and not at each call site — one forgotten line and the whole file would fail with a type error.
  • PRAGMA foreign_keys=ON — SQLite disables foreign keys by default, and the setting is per connection, not per database. It cannot be turned on once when the file is created. So it has to be set on every connection, forever, which means it has to live in the one place every connection is made. Turn it off and DELETE FROM session_harness stops cascading, leaving raw events pointing at a session that no longer exists.
  • timeout=10 and busy_timeout=10000 — the same ten seconds, expressed twice because the Python driver and the SQLite engine each have their own knob. When another process holds a write lock, this connection waits up to ten seconds instead of failing immediately with database is locked. Several processes write here at once: the dashboard server, each hook invocation, the audit CLI.
  • with connection: — this is SQLite's own transaction context. On a clean exit it commits; on an exception it rolls back. That is the safety net under every write in event_store.py: a half-written record cannot survive an exception.
Note what is not here: PRAGMA journal_mode=WAL. Journal mode is a property of the database file, not of the connection — it is set once, in EventStore._initialize, and it persists. Setting it on every connection would be harmless but dishonest: it would suggest it were a per-connection concern.

5. Opening the store, and the version guard

WAL — write-ahead logging. SQLite's default mode makes writers block readers. WAL sends writes to a side file, so readers keep reading the last committed state while a write is in flight. This matters because the dashboard reads continuously — four times a second — while hooks write at unpredictable moments. It also has a practical consequence for debugging: a plain cp of a WAL database gives you a corrupt copy, because the data you need is partly in the side file. Use sqlite3 "file:<path>?mode=ro" ".backup '<dest>'".

The version check is a refusal, not a repair. There is no migration code anywhere in the repository. When domain.codec.SCHEMA_VERSION is bumped, a store written by the old version will not open, and the process that tried to open it dies.

What that looks like when it happens. The dashboard crash-loops. The operational audit fills with unsupported event-store schema version: N, and beside it a long run of dashboard serve (lock denied) rows every ten seconds — the supervisor retrying against a port the dying process still holds. Both signatures are in the audit-debug skill. The fix is to get code and store to the same version, never to edit the metadata row.

os.chmod(0o600) is the last line for a reason: this file contains the full text of every prompt and every file the agent read. Owner-only, always. The directory is created with mode=0o700 in the constructor for the same reason.

7. record() — the write path, line by line

This is the most important method in the layer. Everything it does happens in one transaction, opened with BEGIN IMMEDIATE.

BEGIN IMMEDIATE. SQLite's default (BEGIN DEFERRED) takes a read lock first and only upgrades to a write lock at the first write — and that upgrade can fail with database is locked after you have already read and decided. IMMEDIATE takes the write lock up front. So a concurrent writer waits at the door instead of halfway through, and the decisions made inside cannot be invalidated by someone else writing while you think.

9. Convergence — the branch that does nothing

Just before the insert, the store looks for the event id. If it is there, it returns without writing — and the comment explaining that is longer than the code, because the reasoning is not obvious and was learned the hard way.

Three claims, in order:

  1. The identity names the fact, not the observation. stable_event_id() hashes what happened — harness, session, actor, subject, phase — and deliberately excludes the timestamp and the payload.   2. The first writer wins, and the bodies are not compared. Two sources may render one fact with different detail. Whichever landed first is what you see.

The last sentence is a scar. An earlier version raised when two observations of one fact disagreed. 10. Replay — what happens the second time

When the same raw event arrives again, _verify_recorded_translation (line 714) does not re-write anything. It checks that the interpretation has not changed:

  1. The translation record matches — same version, same decision, same reason.
  2. The provenance rows list the same event ids, in the same order.
  3. Each canonical event re-encodes to byte-identical JSON against what is stored.
if canonical_row is None or self._encoded_row(canonical_row) != self.codec.encode(event):
    raise EventIdentityConflict(f"canonical output changed for raw event {raw_event.raw_event_id}")

This is a determinism check on the translators. The same bytes must always yield the same events. If someone writes a translator that reads the wall clock, or iterates a set, or depends on state accumulated earlier in the run, this is what catches it — on the next re-read, which in practice is a quarter of a second later.

Byte-identity is possible because both sides go through the same canonical encoding: sort_keys=True, separators=(",", ":"), ensure_ascii=False. _encoded_row (line 796) rebuilds the document from columns in sorted key order and encodes it the same way, so a stored row and a freshly translated event are comparable as bytes rather than as objects.

Read the order: translate first, store second, always. Both outcomes end in a write. There is no path through this function that leaves an observation unrecorded — success writes evidence plus facts, failure writes evidence plus a reason.

Note also what this class does not do. It does not decide what to observe, it does not schedule, it does not retry, it does not catch anything except TranslationError. A bug inside a translator that raises something else propagates — and it is the caller's job (ObservationRunner in app/observe.py) to contain it per-source and audit the swallow. The pipeline stays honest about what it saw.

A stuck checkpoint is the single most diagnostic value in the store. Compare source_checkpoints.position against the real size of session_harness.source_reference. 16. projections.py — what a projection is

The store holds thousands of small facts. A screen needs a few dozen objects. Turning the first into the second is a projection, and the file's docstring names the technique:

runtime/projections.py:1 
"""Harness-neutral semantic read models folded from canonical facts."""
Fold. Start with an empty result. Walk a sequence in order. For each item, update the result. Return it. That is all "fold" means, and every function in this file is one — the state is a dictionary, the sequence is events in cursor order, and the update is a chain of isinstance checks.
Read model. A shape built for reading, thrown away afterwards, never stored. Nothing in this file is persisted. Change how a summary is computed and the next read reflects it immediately, with no migration, because the facts underneath did not change.

Every projection folds from the beginning of the session. A long session has tens of thousands of events, the dashboard polls four times a second, and re-reading everything each time would be untenable. Two caches make it work.

Three cases, and the first is the common one:

  1. The cache is behind. Fetch only the gap with between() and append. A poll that finds three new events reads three rows, not thirty thousand.
  2. Nothing cached, or the cursor moved backwards. Read the whole thing with through(). Backwards happens when a caller asks for a historical through_cursor — time-travel for debugging.
  3. The cursor is unchanged. Return what is cached, touching the database only for the cheap MAX(cursor) that got us here.

The cache is safe because canonical events are append-only. A stored event never changes, so an old page can never be stale — it can only be incomplete, and the cursor says by exactly how much. That property comes straight from the write path, and it is what buys the read path its speed.

RLock. A re-entrant lock: the same thread may acquire it more than once without deadlocking itself. It is needed because the dashboard runs the observation scheduler in one thread and serves requests on others, all sharing one SessionQueries. A plain Lock would hang the moment one locked method called another.

_tail_page — the fixed-key cache

Keyed by (session_id, event_limit) and valid only while the cursor matches exactly. It serves the opening of a view: the last few hundred events, without the full history. No incremental extension here, because a tail's contents shift at both ends as new events arrive.

How to add a projection

  2. Add a method on SessionQueries taking (session_id, through_cursor=None) and folding self._page(...).events.
  3. Ignore every payload you do not care about. Never assume ordering beyond cursor order, and never assume the start event is present.

24. Where model.changed falls out

A concrete, current example of how to read this layer — and of a gap that is still open.

When a session's model changes, a model.changed event is stored correctly. Three projections consume it:

  • summary() — updates SessionSummary.model, for the lead actor only (line 513).
  • actors() — updates that actor's ActorSummary.model (line 604).
  • context() — remembers the model so a later context report can be attributed to it (line 752).

Now search _activities for ModelChanged. It is not there. So the event reaches the store, updates the cards at the top of the view, and produces no entry in the feed.

Why it looked like it worked for one harness and not the other. Claude Code's translator emits a message.created for the /model opus you typed, alongside the state event. That message has a branch in the fold, so something appeared — but it was the message, not the model change. Codex has no such message, so nothing appeared at all. The difference was never in the rendering; it was in what each harness happened to produce. That is exactly the shape of bug this layout is meant to make visible: if a fact does not have a branch in _activities, it will never reach a feed, no matter how correctly it is stored.

The fix is a tenth activity type with a branch in the fold and a case in both presenters, at which point both harnesses render identically because both already emit the event. Nothing in the store needs to change.

What _send does to every response

def _send(self, code, body, ctype="application/json", cache="no-store"):

    self.send_response(code)

    self.send_header("Content-Length", str(len(data)))

    self.end_headers()

        pass                            # client went away mid-write
  • gzip above 1 KB (GZIP_MIN), and only if the client's Accept-Encoding genuinely allows it — an explicit gzip;q=0 refusal is honoured.
  • Vary: Accept-Encoding always, even on responses that stayed plain, so a shared cache keys the compressed and uncompressed variants apart.
  • Cache-Control: no-store by default. Only static() overrides it, and only for a URL carrying the current ?v=<BOOT_ID>.
  • A dead client is not an error. The write is wrapped and swallowed.

Cache-busting, and why it is not optional

BOOT_ID is a millisecond timestamp fixed when the process starts. index.html is served no-store and rewritten on the way out, stamping ?v=<BOOT_ID> onto every SPA part, the stylesheet, the icons and the manifest. A stamped URL is then cached hard: public, max-age=31536000, immutable.

The reasoning is in the comment at base.py:198, and it comes from a real report. The origin sending no-store cannot evict an app.js a remote browser already holds — mobile Safari is sticky and a CDN keys by URL. A shipped fix therefore never reached the phone. Changing the URL on every restart is what makes a restart actually deliver new code, and hard-caching the stamped URL is what stops a refresh re-pulling fourteen script files through the tunnel.

This is also why the dashboard does not hot-reload. The bytes behind a stamped URL only change when the process restarts, so the URL only needs to change then. After editing anything the server imports: stop it, start it, and tell the user to hard-reload — a restart bumps BOOT_ID, but it cannot evict what their browser already cached under the old one.

Server-sent events

How the live stream works: the protocol, the two streams, the four events, the loop, and resuming without loss.

1. What SSE is

Server-Sent Events is a GET request that never finishes. The server answers with Content-Type: text/event-stream and then keeps the connection open, writing small text frames whenever it has something to say. The browser's built-in EventSource parses those frames and fires them as DOM events.

A frame is text, and the whole format is three fields and a blank line:

id: 48213
event: activity
data: {"cursor":48213,"items":[…],"snapshot":{…}}
                                    ← a blank line ends the frame

That is the entire protocol. The server-side implementation is nine lines:

dashboard/http/base.py:68 
def _sse_start(self):
    self.send_response(200)
    self.send_header("Content-Type", "text/event-stream")
    self.send_header("Cache-Control", "no-store")
    self.end_headers()

def _sse(self, event, obj):
    """One SSE frame; False when the client is gone (ends the loop)."""
    try:
        self.wfile.write(("event: %s\ndata: %s\n\n"
                          % (event, json.dumps(obj, default=str))).encode())
        self.wfile.flush()
        return True
    except OSError:
        return False
Why SSE and not WebSocket. The traffic is one-way — the server tells the browser what changed, and the browser talks back over ordinary POSTs. SSE is plain HTTP, so it needs no protocol upgrade and passes through the tunnel unchanged, and EventSource reconnects by itself with no client-side retry logic. A WebSocket would add a second protocol, its own reconnect handling, and a second failure domain, in exchange for a direction of traffic that is not used.
flush(). Ordinary HTTP responses are buffered — the server collects bytes and sends them when the response ends. A stream that never ends would therefore never deliver anything. flush() pushes each frame onto the socket immediately. Notice too that SSE never goes through _send: that path sets Content-Length and gzips, both of which need the whole body up front.

Read what this loop is not doing. There is no subscription, no callback, no message bus, and no coupling to whatever wrote the events. It asks the store "anything after cursor N?" four times a second. When the answer is no, frame() returns None and nothing is written.

That is why a pushed hook shows up on screen. A hook is a separate short-lived process. It writes to events.db and exits, knowing nothing about the dashboard. Every open stream discovers the new cursor within a quarter of a second. No process needs to notify another, which is precisely what keeps hooks unable to block or fail on the dashboard's account.

Change detection for the application event is worth noting: the snapshot is encoded to canonical JSON — sort_keys=True, no spaces — and compared as a string against the previous one. Comparing the objects would be unreliable across rebuilt dataclasses; comparing canonical text is exact. Unchanged state costs one encode per tick and sends nothing.

The global stream at canonical.py:277 is the same loop without the activity half, and it sends ready before entering it.

2. The rule that makes it worth having

Hooks must never block or fail. Exit 0, swallow exceptions — but audit before every swallow. The same applies to any long-lived loop: nothing that drives other work may die silently.

Those two sentences are in tension, and the audit is what resolves them. A hook that raises would break the tool being watched, so exceptions must be swallowed. A swallowed exception leaves no trace, so a mechanism that fails becomes undebuggable. Writing a row first makes silence safe.

The repository states the coverage obligation in the same terms. In the same commit as a feature: audit new swallow sites as errors, new coordination writes and control gestures as state_files, new detached processes as spawns or streams. Then update the audit-debug skill — both its schema table and its bug shapes, because they drift independently and a schema-only update makes the skill look current while it triages blind.

3. How it is written

def error(session_or_log: str = "", func: str = "", context: object = None) -> None:
    if not enabled():
        return
    with closing(_connect()) as connection, connection:
        connection.execute("INSERT INTO errors(…) VALUES(?,?,?,?,?,?,?)",
                           (time.time(), _session_id(session_or_log), _script(), func,
                            traceback.format_exc(), _text(context) if context is not None else "",
                            os.getpid()))

Four decisions, all in service of "any process, at any moment, must be able to write one row".

  • No shared handle. A hook is a process that lives for milliseconds; the dashboard lives for days. Neither can hold a connection for the other, and WAL makes concurrent writers workable.
  • The schema is created on every connect. CREATE TABLE IF NOT EXISTS, so it costs nothing and a brand-new machine needs no setup step.
  • enabled() is checked in every function. BAQYLAU_AUDIT=0 makes each one a no-op return, so tests and throwaway runs need not touch the file.
  • traceback.format_exc() is called inside error(). It reads the exception currently being handled — which is why error() must be called from inside an except block, and why the caller passes no traceback of its own.

Two small helpers carry weight. _script() records sys.argv[0]'s basename, so every row says which executable wrote it — a hook, the dashboard, the audit CLI. _text() JSON-encodes anything that is not already a string, so a caller may pass a dict without thinking about it.

4. The four tables

errors — a swallowed exception

CREATE TABLE IF NOT EXISTS errors(
    id INTEGER PRIMARY KEY,
    ts REAL NOT NULL,
    session_id TEXT NOT NULL,
    script TEXT NOT NULL,
    func TEXT NOT NULL,          -- the label the caller chose
    traceback TEXT NOT NULL,     -- the FULL traceback, not a message
    context TEXT NOT NULL,       -- whatever the caller thought would help
    pid INTEGER NOT NULL
);
CREATE INDEX IF NOT EXISTS errors_by_session ON errors(session_id, ts);

func is a human label, not a function name, and the labels in use read like locations: dashboard request, dashboard POST, dashboard serve (port busy), dashboard serve (lock denied), dashboard notifier, dashboard upload (write failed), dashboard dictate (grant failed), statusline capture, webpush keygen, and — from the observation scheduler — observation (source drain) and observation (observation pass), whose context names the failing source.

state_files — a notable non-error act

CREATE TABLE IF NOT EXISTS state_files(
    id INTEGER PRIMARY KEY, ts REAL NOT NULL, session_id TEXT NOT NULL,
    path TEXT NOT NULL, action TEXT NOT NULL, content TEXT NOT NULL,
    script TEXT NOT NULL, pid INTEGER NOT NULL);

This is the widest table in meaning: it records things that worked, or were deliberately refused, and would otherwise leave no trace. content is JSON-encoded and truncated to 2000 characters — the audit stores enough to explain a decision, never a payload.

spawns and streams — detached processes

CREATE TABLE IF NOT EXISTS spawns(
    id INTEGER PRIMARY KEY, ts REAL NOT NULL, session_id TEXT NOT NULL,
    parent_script TEXT NOT NULL, child_pid INTEGER NOT NULL,
    argv TEXT NOT NULL, purpose TEXT NOT NULL);

CREATE TABLE IF NOT EXISTS streams(
    id INTEGER PRIMARY KEY, session_id TEXT NOT NULL, kind TEXT NOT NULL,
    agent_id TEXT NOT NULL, task_id TEXT NOT NULL, src_path TEXT NOT NULL,
    pid INTEGER NOT NULL, started_at REAL NOT NULL,
    ended_at REAL, end_reason TEXT, lines_emitted INTEGER);

spawns is a point in time: a process was launched, here is its command line. streams is an interval, and it is the only table written twice — stream_start inserts and returns the row id, stream_end updates it with a reason. The dashboard's whole run is one such row, which is how uptime and the exit path are queryable:

dashboard/http/handler.py:79 
stream_id = A.stream_start("", "dashboard", src_path=f"http://{HOST_ADDRESS}:{PORT_NUMBER}")
…
A.stream_end(stream_id, "stopped")     # or "port-busy", or "crash"

stream_end tolerates None, so a caller need not check whether auditing was enabled when it started.

6. The control row, and why it exists

The newest action is control, written at the single dispatch point every harness and every gesture passes through:

app/services.py:96 
def _audit_control(request: ControlRequest, outcome, elapsed: float) -> None:
    try:
        audit.state_file(str(request.session_id), "", "control",
                         {"control": …, "request_id": …, "status": …, "reason": …, "ms": …})

Two real rows, minutes apart, from the session that prompted it:

{"control": "select_model", "request_id": "1786765836571-2",
 "status": "indeterminate",
 "reason": "row: no 'all models' under 'Select Model'", "ms": 379}

{"control": "select_model", "request_id": "1786766313588-1",
 "status": "acknowledged", "reason": "", "ms": 1434}

The first is the failure and the second is the fix, and the difference is legible without reading any code: the screen driver was looking for a row that the harness's newer version no longer shows.

Before this row existed, that gesture left nothing. The only trace anywhere was the browser's own command.ok carrying status: 202 — and 202 is indeterminate, the failure code, which the browser had treated as success. The driver's step name went into the HTTP response body and nowhere else, so the one string that named the bug was unrecoverable.

Note the session_id in the first argument. It is there so the row appears in a WHERE session_id = ? triage query — the omission that made this gesture read as "no audit at all" even after other rows existed.

8. What the audit deliberately does not capture

  • No conversation content. Prompts, replies, file contents and diffs are session facts and live in events.db. The audit holds at most 2000 characters of context per row, and that context is about the mechanism.
  • No access log. log_message is overridden to do nothing — the stdlib's per-request line would be noise, and the process runs detached with its output discarded anyway.
  • No tokens, costs or usage. Those are usage.reported and context.reported events, which survive on their own evidence.
  • No successful reads. A GET that worked writes nothing. Only refusals, failures, control gestures, deliveries and process lifecycles are recorded.
The test for whether something belongs here. Ask: if this goes wrong at three in the morning and nobody is watching, what will be left behind? If the answer is "nothing", it needs a row — before the swallow, in the same commit, with the audit-debug skill updated to know its shape.
