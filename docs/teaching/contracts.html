1. The idea in one page

Baqylau watches coding tools it does not own — Claude Code, Codex — and shows them in one interface. Those tools have nothing in common: different files, different formats, different ways of being controlled.

contracts/harness.py is the list of questions baqylau is allowed to ask a tool, and the shapes of the answers. Its first line says exactly that:

contracts/harness.py:1 
"""The complete public contract implemented by every harness plugin."""

"Harness" is this codebase's word for one such tool. Claude Code is a harness. Codex is a harness. A plugin is the adapter that answers the contract's questions for one harness.

The file contains two kinds of thing, and telling them apart is most of understanding it:

kindwhat it isexample
ProtocolA list of things a plugin must be able to do. Behaviour. Verbs.HarnessLauncher — "can start a new session"
dataclassA shape of data passed in or out. Nouns.LaunchRequest — "start one in this folder, with this model"

2. Four words you need first

Protocol. A Python class that lists method names and signatures with no bodies — the bodies are literally .... It describes a shape. Any class with matching methods satisfies it, whether or not it says so. That is called structural typing: the compiler checks the shape, not the family tree. 
class HarnessHook(Protocol):
    def receive(self, payload: bytes) -> HookIntake: ...
This is convenient and it is also a trap, because a class can drift out of the shape in silence — rename a parameter and nothing objects until something breaks at runtime. That is why this repository requires implementations to name the Protocol they implement (class ClaudeHook(HarnessHook):) and has a test that fails when one does not.
Frozen dataclass. @dataclass(frozen=True) generates a class from a list of typed fields, and makes it immutable — assigning to a field after construction raises. Nearly every noun in this file is one. Immutability matters because these objects are passed between threads and stored as evidence; a value that can be edited after the fact is not evidence.
TypeAlias / Literal. Literal["started", "finished"] means "this string may only ever be one of these two". It is a closed set, checked by tools and by tests. When you see one, read it as a complete list of the possibilities — there is no thirteenth control name hiding somewhere.
Actor. Not a Python concept — this codebase's word for anything that acts inside a session. The main agent is an actor (the lead). Each subagent it spawns is an actor. A teammate is an actor. Every piece of evidence carries an actor_id saying who did it, which is how the interface can filter a whole view down to one subagent.

3. HarnessPlugin — the whole surface

This is the object a plugin hands to baqylau. Everything else in the file exists to describe one of these eleven fields.

HarnessInfo

class HarnessInfo:

4. Finding sessions

Before anything can be watched, baqylau must know a session exists. That is two questions, and they are deliberately separate.

contracts/harness.py:135 
class SessionRecognizer(Protocol):
    def discover(self) -> tuple[RecognizedSession, ...]: ...
    def recognize(self, candidate: SessionCandidate) -> RecognizedSession | None: ...
  • discover() — "go look around and tell me every session of yours you can find." The plugin searches its own directories. Nobody tells it where to look; only the plugin knows.
  • recognize(candidate) — "here is one specific file. Is it yours?" Returns None for no. This is how a file can be offered to every plugin in turn until one claims it.

SessionCandidate — the question

contracts/harness.py:130 
@dataclass(frozen=True)
class SessionCandidate:
    source_reference: str                    # a path to inspect
    working_directory: str | None = None

RecognizedSession — the answer

contracts/harness.py:99 
@dataclass(frozen=True)
class RecognizedSession:
    session_id: SessionId          # baqylau's id for it
    lead_actor_id: ActorId         # the main agent inside it
    native_session_id: str         # the tool's OWN id for it
    source_reference: str          # the file that IS this session's record
    working_directory: str | None
    native_process_id: int | None = None

Two ids, deliberately. native_session_id is whatever the tool calls it. session_id is what baqylau calls it. Keeping both means a tool can change its identifier scheme without baqylau losing track, and it means two harnesses cannot collide.

source_reference is the load-bearing field: the file that is the session's record. Everything in the next section reads it.

This class also has a small convenience:

contracts/harness.py:108 
    @property
    def event_source_context(self) -> EventSourceContext:
        return EventSourceContext(
            session_id=self.session_id,
            lead_actor_id=self.lead_actor_id,
            actor_id=self.lead_actor_id,      # the lead is reading its own file
            parent_actor_id=None,             # the lead has no parent
            source_reference=self.source_reference,
        )

A property is a method you read like a field (session.event_source_context, no parentheses). This one builds the context for reading the lead's file: the actor is the lead, and it has no parent. A subagent's file gets a different context, built by hand, where actor_id is the subagent and parent_actor_id is the lead.

5. Watching a session

This is the heart of the contract, and it is two jobs that must not be confused: collecting bytes and understanding them.

contracts/harness.py:143 
class HarnessEvents(Protocol):
    def sources(
        self,
        session: RecognizedSession,
        checkpoints: CheckpointStore,
    ) -> tuple[HarnessEventSource, ...]: ...

    def translate(self, raw_event: RawEvent) -> TranslationResult: ...

They are separate because collecting must never be blocked by a failure to understand. Bytes we cannot interpret are still stored, and can be re-interpreted later when the interpreter is fixed. If the two were one step, a translation bug would lose the evidence of itself.

5a. Sources — collecting

contracts/harness.py:140 
class HarnessEventSource(Protocol):
    def drain(self, delivery: RawEventDelivery) -> None: ...

One method. "Read whatever is new and hand it over." drain does one finite pass and returns — it does not loop, does not sleep, does not wait. Repetition belongs to the one scheduler that calls it every 250ms. A source that looped forever would be a second scheduler nobody could stop.

Where does it hand things? To the object it is given:

contracts/harness.py:86 
class RawEventDelivery(Protocol):
    def deliver(self, raw_event: RawEvent) -> IngestionResult: ...
Why pass this in rather than let the source call the database? Because the source then knows nothing about storage — not the database, not the file, not the transaction. It can be tested by handing it a fake collector. This is dependency injection: a component is given what it needs instead of reaching for it. You will see the same move for CheckpointStore, TerminalControl and SessionLifecycleContext.

RawEvent — one observation

contracts/harness.py:30 
@dataclass(frozen=True)
class RawEvent:
    raw_event_id: RawEventId       # must be REPRODUCIBLE, never random
    harness: str
    source_type: str               # "transcript", "rollout", "hook", "otel", …
    source_name: str               # the file path, or the hook's name
    source_position: str           # a byte offset, or the tool's own event id
    session_id: SessionId
    actor_id: ActorId
    parent_actor_id: ActorId | None
    observed_at: float             # when WE received it
    encoding: str                  # "json" | "jsonl" — how to read the bytes
    payload: bytes                 # the bytes, complete and unmodified

raw_event_id must be reproducible, because the same line will be read twice — after a crash, after a restart, whenever a checkpoint is lost. For a file source the id is "{which file}:{byte offset}", so re-reading line 40 produces the same id, and the store recognises it as something it already has. Random ids would fill the database with duplicates.

payload is the whole bytes, newline included, never trimmed or prettified. It is the evidence.

EventSourceContext — who is speaking

contracts/harness.py:90 
@dataclass(frozen=True)
class EventSourceContext:
    session_id: SessionId
    lead_actor_id: ActorId         # the session's main agent
    actor_id: ActorId              # whose file THIS source reads
    parent_actor_id: ActorId | None
    source_reference: str

A session has several files: the lead's, and one per subagent. Each gets its own source with its own context, so every byte is attributed as it is collected — not guessed at later. lead_actor_id is carried alongside actor_id so a source can ask "am I the lead?" without being told separately.

Checkpoints — remembering how far you read

contracts/harness.py:44 
@dataclass(frozen=True)
class SourceCheckpoint:
    session_id: SessionId
    source_identity: str           # a stable name for THIS source
    position: str                  # opaque: only the source knows what it means


class CheckpointStore(Protocol):
    def load(self, source_identity: str) -> SourceCheckpoint | None: ...
    def commit(self, checkpoint: SourceCheckpoint) -> None: ...

position is a string, not a number, and that is intentional. For a file it is a byte offset. For a source watching a directory of task files it is a JSON snapshot of them all. For a source watching a process it is the literal word "finished". The store keeps it without understanding it; only the source that wrote it has to.

source_identity is derived from the file path, not from the object. That is what makes a checkpoint survive a restart: the rebuilt source computes the same identity and resumes at the same byte.

Checkpoints are an optimisation, not a correctness mechanism. Losing one costs re-reading a file. It does not create duplicates, because that is already prevented by the reproducible raw_event_id. Two mechanisms, one job each.

5b. Translate — understanding

translate() takes one RawEvent and returns a verdict.

contracts/harness.py:57 
@dataclass(frozen=True)
class TranslationResult:
    events: tuple[CanonicalEvent[EventPayload], ...]
    decision: TranslationDecision
    reason: str | None = None

    def __post_init__(self) -> None:
        if self.decision == "translated" and not self.events:
            raise ValueError("translated observations must produce at least one event")
        if self.decision != "translated" and self.events:
            raise ValueError("ignored observations cannot produce canonical events")
__post_init__ runs immediately after a dataclass is constructed. Here it makes a contradictory verdict impossible to build — you cannot claim you translated something and produce nothing, and you cannot claim you ignored something while producing events. The check happens at the moment of creation, not later at the point of use.

The verdicts:

contracts/harness.py:26 
TranslationDecision: TypeAlias = Literal["translated", "ignored_unknown", "ignored_nonsemantic"]
RecordedTranslationDecision: TypeAlias = TranslationDecision | Literal["translation_failed"]
verdictmeaningalarming?
translatedUnderstood; here are the facts.no
ignored_nonsemanticUnderstood, and it means nothing worth keeping. Plumbing.no — expected in bulk
ignored_unknownNot recognised at all. Tools emit plenty we do not model.no — expected in bulk
translation_failedThe translator raised an exception.yes — this is the actionable one

Notice the two type aliases. A plugin may only return the first three. translation_failed exists only in the recorded vocabulary — a plugin cannot claim it, because it is what the store writes when the plugin crashes:

contracts/harness.py:69 
class TranslationError(ValueError):
    def __init__(self, reason: str, *, context: str | None = None) -> None:
        super().__init__(reason)
        self.reason = reason
        self.context = context

context usually carries the byte offset of the record that could not be read, so the failure row in the database points at the exact evidence.

IngestionResult — what came back

contracts/harness.py:77 
@dataclass(frozen=True)
class IngestionResult:
    raw_event_id: RawEventId
    translation_decision: RecordedTranslationDecision
    accepted_event_ids: tuple[CanonicalEventId, ...]      # facts new to us
    deduplicated_event_ids: tuple[CanonicalEventId, ...]  # facts we already had
    latest_cursor: int | None

The split between accepted and deduplicated is what makes re-reading safe. Several independent sources may report the same fact; the first one to arrive is stored, and the rest are recorded as corroboration rather than repeated. Side effects fire only for accepted facts, so replaying a file does not re-open a terminal pane.

6. Hooks — when the tool calls us

Everything above is baqylau reading. A hook is the opposite: the tool runs a program of ours and waits for an answer. Claude Code does this on every tool call, every prompt, every session start.

contracts/harness.py:169 
class HarnessHook(Protocol):
    def receive(self, payload: bytes) -> HookIntake: ...
contracts/harness.py:160 
@dataclass(frozen=True)
class HookIntake:
    session: RecognizedSession
    raw_events: tuple[RawEvent, ...]
    output: bytes = b""                       # written back to the tool
    controls: tuple[ControlRequest, ...] = ()
    actions: tuple[HookAction, ...] = ()

receive is pure: it parses and returns a description of what should happen. It writes nothing itself. The caller then performs the steps in a fixed order, and the order is the interesting part:

1. register the session — it must exist before facts refer to it 2. deliver every raw_event — the evidence commits 3. run every control — acting comes after recording 4. ensure the host is up — the thing that will observe the actions 5. start every action — native side effects, LAST 6. return output to the tool
contracts/harness.py:154 
class HookAction(Protocol):
    """A plugin-owned native action started only after hook facts commit."""

    def start(self) -> None: ...

The docstring states the rule. An action might start a process that begins writing a file baqylau will later read. If it started before the facts committed, output could arrive describing a thing not yet recorded. Step 4 sits where it does for the same reason: an action is only started once the observer that will notice it is confirmed running.

output is a real channel, not a log. Some hooks let the answer change what the tool does next — this is how a command can be rewritten before it runs so its output can be streamed.

7. Lifecycle — reacting to start and end

When a session begins or ends, something outside the data has to happen: terminal panes open, panes close. That belongs to the plugin, because only it knows what its session needs.

contracts/harness.py:174 
@dataclass(frozen=True)
class SessionLifecycleRequest:
    action: Literal["started", "finished"]


@dataclass(frozen=True)
class SessionLifecycleContext:
    terminal: SessionTerminal
    panes: SessionPaneControl


class HarnessLifecycle(Protocol):
    def apply(
        self,
        request: SessionLifecycleRequest,
        session: RecognizedSession,
        context: SessionLifecycleContext,
    ) -> None: ...

Three arguments, three distinct jobs:

  • request — what happened. Exactly two possibilities. A dataclass wrapping one field looks redundant, but it means adding a third event later changes no signature anywhere.
  • session — which session, with its directory and its native id.
  • context — the tools to do it with. The plugin never reaches for the terminal itself; it is handed exactly two capabilities. It cannot close a tab it was not given the power to close, and in a test it is handed fakes and touches nothing real.
A live example of why the shape matters. Until this session, one plugin's apply named its second parameter recognized_session while the Protocol says session. Structural typing did not care. But a caller using keyword arguments — apply(request=…, session=…, context=…) — would have worked on one harness and raised TypeError on the other. Parameter names are part of a contract, not decoration. A test now enforces it.

8. Controls — driving the tool

This is the largest section of the file, because "make the session do something" has many shapes. The design is one closed list of verbs, one object per verb, and one result type per shape of answer.

The closed list of verbs

contracts/harness.py:193 
ControlName: TypeAlias = Literal[
    "send_text", "interrupt", "close_session", "rename_session", "auto_name_session",
    "open_rewind", "apply_rewind", "migrate_account", "compact",
    "select_model", "select_effort", "answer_question", "read_plan_choices", "decide_plan",
]

Fourteen. That is all of them. A web request naming anything else is rejected before it reaches a plugin.

Every request shares a base

contracts/harness.py:211 
@dataclass(frozen=True)
class ControlTarget:
    session_id: SessionId
    request_id: str

request_id is generated by the browser and echoed back in the result, so an answer can be matched to its question when several are in flight.

Each verb then extends it with only the fields it needs:

contracts/harness.py:224 
@dataclass(frozen=True)
class SendText(ControlTarget):
    control_name: ClassVar[ControlName] = "send_text"
    text: str
    attachments: tuple[AttachmentReference, ...] = ()
    replace_terminal_draft: bool = False


@dataclass(frozen=True)
class Interrupt(ControlTarget):
    control_name: ClassVar[ControlName] = "interrupt"        # no extra fields at all
ClassVar means "this belongs to the class, not to each instance". Every SendText ever created has control_name == "send_text"; it is not a field you pass in and cannot be set to something else. It is a label the class carries, which is what lets the dispatcher look at any request and know which handler to call.

The fourteen are then gathered into one type:

contracts/harness.py:312 
ControlRequest: TypeAlias = (
    SendText | Interrupt | CloseSession | RenameSession | AutoNameSession
    | OpenRewind | ApplyRewind | MigrateAccount | Compact
    | SelectModel | SelectEffort | AnswerQuestion | ReadPlanChoices | DecidePlan
)

The | is "or" — a value of this type is exactly one of these. Because the list is closed, a tool can tell you if you forget to handle one.

What the plugin is given to work with

contracts/harness.py:119 
@dataclass(frozen=True)
class ControlContext:
    session: RecognizedSession
    terminal: TerminalControl                    # the ability to type and press keys
    current_model: ModelReference | None
    current_effort: str | None
    current_account: AccountReference | None

The current state is handed in rather than looked up, so the plugin does not query the database and every gesture sees one consistent snapshot. pending_attention matters for answering: to reply to a question you must know which question is open.

The results

contracts/harness.py:330 
@dataclass(frozen=True)
class ControlResult:
    request_id: str
    status: Literal["acknowledged", "rejected", "indeterminate"]
    reason: str | None = None

Three outcomes, and the third is the one worth learning:

statusmeaningHTTP
acknowledgedDone.200
rejectedRefused up front — not live, not supported, not allowed.409
indeterminateAttempted, but never confirmed. The gesture ran and the tool did not visibly comply.202
202 is a failure code here. It is a success code in HTTP generally, which is why a browser check of "was the status 2xx?" reported a model switch as successful while the terminal sat unchanged with a dialog open. The verdict has to be read from status, not from the HTTP code.

Some gestures need to say more, so there are subclasses — extra fields with sensible defaults, so anything that only understands ControlResult still works:

@dataclass(frozen=True)

    degraded: bool = False          # it worked, but not as completely as asked


@dataclass(frozen=True)

RewindResult.degraded is worth pausing on. Rewinding a conversation can partly succeed — the messages come back but the files do not. That is neither "done" nor "failed", so it is reported as done with a flag, rather than being rounded to whichever is closer.

The controller itself is not a Protocol

contracts/harness.py:377 
ControlHandler: TypeAlias = Callable[[ControlRequest, ControlContext], ControlOutcome]


@dataclass(frozen=True)
class HarnessController:
    handlers: Mapping[ControlName, ControlHandler]

    def execute(self, request: ControlRequest, context: ControlContext) -> ControlOutcome:
        handler = self.handlers.get(request.control_name)
        if handler is None:
            return ControlResult(request.request_id, "rejected", "unsupported control")
        return handler(request, context)

This is the one place the file provides an implementation rather than a shape, and it is worth noticing why. A plugin supplies a dictionary from verb to function. Supporting a gesture means adding a key; not supporting one means leaving it out, and the "unsupported" answer is written once, here, for everybody.

Callable[[A, B], C] is the type of a function taking an A and a B and returning a C. The handlers are plain functions, not classes.

9. Launching

contracts/harness.py:394 
@dataclass(frozen=True)
class LaunchRequest:
    working_directory: str
    initial_text: str | None                  # a first prompt to send
    model_id: str | None
    effort: str | None
    account_id: str | None
    resume_session_id: SessionId | None       # continue an old session
    attachments: tuple[AttachmentReference, ...] = ()


@dataclass(frozen=True)
class HarnessLaunchPlan:
    command: str
    arguments: tuple[str, ...]
    title: str


class LaunchRejected(ValueError):
    pass


class HarnessLauncher(Protocol):
    def prepare(self, request: LaunchRequest) -> HarnessLaunchPlan: ...

Note what prepare does not do: it does not launch anything. It returns a plan — a command and its arguments — and the application runs it. Only the plugin knows how to spell its own command line; only the application knows how to open a terminal tab. Each does the half it knows.

Refusal is an exception rather than a result, because a plan that cannot be made has nothing to return. LaunchRejected is caught by the caller and turned into a LaunchResult(status="rejected").

10. Catalog — what the menus offer

The interface has dropdowns: models, effort levels, accounts, slash commands. Their contents are the tool's business, not the interface's.

contracts/harness.py:509

This Protocol has a field, not just methods — sections declares which parts of the catalogue this harness fills in. A harness with no notion of "effort" leaves it out, and the interface hides the control rather than showing an empty menu.

Every field defaults to empty, so a plugin fills in only what it has. One option type is worth a look:

contracts/harness.py:482

    command: str
    description: str

minimum_prompt_count encodes a real refusal: some tools will not compress a conversation that has barely started. Rather than the interface guessing, the harness states the floor and the button greys out below it.

Decimal instead of float. Floating-point numbers cannot represent most decimal fractions exactly — 0.1 + 0.2 is famously not 0.3. 12. Memory

contracts/harness.py:572 
class HarnessMemory(Protocol):
    def enabled(self, working_directory: str) -> bool: ...
    def item_count(self, session_id: SessionId) -> int: ...
    def snapshot(self, session_id: SessionId) -> HarnessMemorySnapshot: ...
    def document(self, path: str | None, stem: str | None) -> MemoryDocument: ...

Some setups keep a notes vault the agent reads from and writes to. This exposes which notes a session touched.

The four methods are graded by cost, deliberately. enabled() is a cheap yes/no that decides whether to show the feature at all. item_count() is cheap enough for a badge. snapshot() is the full list. document() reads one note. A caller pays only for what it displays.

A snapshot has two halves, and the distinction is a real one:

contracts/harness.py:558 
@dataclass(frozen=True)
class HarnessMemorySnapshot:
    notes: tuple[MemoryNoteRecord, ...]      # notes the session OPENED
    searches: tuple[MemorySearchRecord, ...] # questions it ASKED of the vault

A search names notes it never opened. Recording only the opened notes would lose the moment the session asked memory a question and got nothing useful back.

A search record carries its hits, and a hit is a note the search named:

contracts/harness.py:534 
@dataclass(frozen=True)
class MemorySearchHit:
    path: str
    relative_path: str
    name: str
    line_number: int | None
    title: str
    score: str                  # the ranking, as the tool spelled it
    snippet: str                # the matching text

score is a string rather than a number because it is the search tool's own output, reproduced rather than reinterpreted. Parsing it into a float would mean inventing a scale that the tool never promised.

    def input_state(self, screen: TerminalScreen, window_id: str) -> TerminalInputState | None: ...

Two nested optionals, each meaning something different. TerminalSessionState.window_id is None when the session has no terminal window at all — it has been parked, or is being watched from another machine. input_state is None when there is a window but the probe could not read it. "Not running" and "running but unreadable" are different situations and the interface reacts differently to each, so they are not collapsed into one absence.

Some things a tool never writes down. Half-typed text in the input box exists only as pixels. This reads them back off the screen, so the web composer can show what is already typed in the terminal instead of overwriting it.

The plugin is handed a TerminalScreen — the ability to read one window's text — and nothing else. It cannot type, cannot close, cannot press keys. The narrowest capability that does the job.

Screen reading is the most fragile thing in the system. Layouts change between versions of a tool with no warning, which is exactly how a model-switch driver broke this week: the tool removed a screen and the driver was still looking for it. Anything screen-derived should be treated as a best effort that can return None.

Reading the columns left to right is roughly the life of a session: it is recognised, then watched, it pushes events at us, its start and end move panes, and meanwhile we drive it.

The four ideas that recur

  1. Separate collecting from understanding. sources and translate are two methods for this reason. Bytes we cannot interpret are still kept, and can be re-interpreted when the interpreter improves.
  2. Hand in capabilities; do not let components reach. RawEventDelivery, CheckpointStore, SessionLifecycleContext, TerminalControl, TerminalScreen are all passed in. A plugin can do exactly what it was handed the means to do — which makes it testable, and bounds what a bug in it can reach.
  3. Closed lists over free strings. Fourteen control names, three statuses, four verdicts, two lifecycle actions. Every one is a Literal, so "did we handle them all?" is a question a tool can answer.
  4. Make the impossible unconstructible. TranslationResult.__post_init__ refuses a contradictory verdict at the moment of creation, rather than letting it travel and fail somewhere far away.

What is deliberately absent

Reading a contract for what it omits is as informative as reading what it contains.

  • No presentation. Nothing returns HTML, colours or glyphs. A separate check refuses payload fields named html, css, glyph, ansi and six others at startup.
  • No storage. No plugin is handed a database. It receives a deliver and a checkpoint store, and knows nothing about SQL.
  • No scheduling. drain does one pass. No plugin owns a loop, a thread, or a timer.
  • No harness names anywhere below this file. A test forbids the words claude, codex, transcript and rollout from appearing in the eight shared directories. This contract is the exact line where those words stop.
