5Access patterns and processes

Six patterns

  1. Store class holding a path. CanonicalEventStore, SessionStore, RawEventRecorder, OperationOutputStore — each calls initialize() in its own __init__, so the schema is applied four times per process start.
  2. Module-level function over a fixed path. diagnostics/record.py, dashboard/prefs/*, terminal/panes/{preferences,views}.py, claude_code/usage/state.py. No object, no injection; tests substitute an environment variable rather than a collaborator.
  3. Read-only class holding a path. OperationalDiagnostics.
  4. Query object reaching around a store. EvidenceQueries — holds a store, uses it for .database_path.
  5. Service reaching around the store layer. SessionApplicationService.
  6. Free function over a caller-supplied path. core/locks.py — the only accidentally-injectable one.

15One access pattern

The pattern

A Protocol-typed repository, implemented once over SQLite, constructed once by app/bootstrap.py, and handed to its consumers as a constructor parameter. Consumers name the Protocol, never the implementation. No module-level storage function, no path passed around, no lazily-created connection, no initialize() outside SqliteDatabase.

The six patterns of §5 collapse into that one. What replaces each:

WasBecomes
1 — store class holding a pathRepository class holding a SqliteDatabase. Two instances exist in a daemon (main, audit); a third for locks. initialize() runs once each, fixing F5.
2 — module-level function over a fixed pathInjected repository. dashboard/prefs/ and terminal/panes/{preferences,views}.py disappear; the surviving policy (env-var defaults, prune limits, the view-mode vocabulary) moves to a service or into SQL.
3 — read-only class holding a pathDiagnosticReadRepository over a read-only SqliteDatabase (EXC-B).
4 — query object reaching around a storeTranslationEvidenceRepository. engine/queries/evidence.py is deleted; the audit CLI uses the repository directly.

6 — free function over a caller-supplied pathProcessLockRepository, constructed in app/bootstrap.py and in dashboard/cli.py (which is a separate process and needs its own).
The invariant, with no exceptions at all

Nothing outside a repository implementation touches a database. import sqlite3 appears in exactly two directories — repository/impl/sqlite/, and harness/impl/codex/canonical/title.py, which is also a repository implementation (CodexThreadTitleRepository, declaring NativeSessionTitleRepository) and lives where it does only because test_canonical_shared_code_contains_no_concrete_harness_vocabulary forbids the word “codex” in a shared package. No connection string, no cursor, no SQL, no schema, no sqlite3.Row exists anywhere else in the tree. There is no read-only escape hatch, no forensic exception, no “just this one query”. That rule has zero exceptions and §24's test_only_a_repository_implementation_opens_a_database is what keeps it that way.

The two exceptions — and what they are exceptions to

Both of the following go through the contract and its SQLite implementation like everything else. Neither is an exception to the invariant above; they are exceptions to two weaker, separate rules.

EXC-4“only the daemon builds repositories in-process”The audit CLI constructs its own read-only SqliteDatabase and the two repositories it needs, instead of being an HTTP client of the daemon.It is the tool you run when the daemon is the suspect, so it cannot depend on the daemon answering. 18Bulk methods: no connections, no handles

Revision 1's unit of work is withdrawn

The previous draft exposed EventStore.write() returning a context manager over eight repositories, so the interpreter could span three tables in one transaction. That put transaction management in the caller — exactly what requirement 10 rules out. It is replaced by coarse methods that own their own transaction.

The tree has exactly one multi-table write, and one method now covers it:

# engine/interpret/loop.py — after
def _translate_one(self, raw_event: RawEvent) -> None:
    plugin = self.harnesses.plugin(raw_event.harness)
    translator = self.core_translators.get(raw_event.source_type, plugin.translator)
    try:
        translation = translator.translate(raw_event)
    except Exception as error:
        translation = TranslationResult((), "translation_failed", f"{type(error).__name__}: {error}")
    else:
        translation = _checked(raw_event, translation)      # envelope checks, moved up from the store

    outcome = self.canonical_events.record_translation(     # ONE call, ONE transaction
        raw_event, plugin.info.plugin_version, translation, self.clock())
    self._react(outcome.accepted, plugin)

D3Should audit.db also be consolidated?No. Two reasons, either sufficient: it is written by ~20 short-lived processes that must never contend with the interpreter's write lock, and it is what you read when main.db is the suspect.One file. Simpler to reason about and to back up; costs the isolation above.

Smaller diff, no new behaviour, but the uploads directory keeps growing unattributably.
D5Phase 10 (response models) in the same programme?Yes, but merged separately. It touches no storage code, and its diff is large and mechanical.Ship it first, so the browser contract is pinned before the layers below it move.
