Terminology review · 17 August 2026

One audit vocabulary. Two databases.

The consolidation is naming-only: diagnostics, provenance, and evidence no longer compete as subsystem names. main.db still owns actual operations; audit.db still owns optional debug records.

Implemented model: a RawEventAudit joins one raw event to an optional InterpretationAudit. That interpretation contains its verdict and zero or more InterpretationAuditEvent values. Debug infrastructure is consistently named audit.

What the old words meant

Evidenceold read-model name

TranslationEvidence was the forensic aggregate returned for a raw event. It mixed the observation, verdict, and interpreted canonical events into one flat object.

harness/models/evidence.py · app/evidence_cli.py (before)

Provenanceold relation name

canonical_provenance linked an interpretation attempt to each canonical event it produced or deduplicated. It was part of interpretation audit, not a separate subsystem.

canonical_provenance · ProvenanceEntry · provenance_values()

Auditchosen umbrella

The retained name. It describes inspection records: raw-event interpretation audits in main.db, and machinery/debug audit records in audit.db.

RawEventAudit · InterpretationAudit · AuditRecorder

Diagnosticsold debug name

The package and repository names that implemented debug auditing. These were direct synonyms for audit and added no useful distinction.

diagnostics/ · DiagnosticWriteRepository · SqliteDiagnosticWriteRepository

The consolidated model

Raw event

Exact source bytes, source identity, position, session, actor, and harness.

raw_events

→

Interpretation audit

Translator version, decision, reason, completion time.

interpretations

→

Interpretation events

Ordered canonical outputs with accepted/deduplicated storage result.

interpretation_events + canonical_events

Separate storage responsibility: debug audit

Errors, state-file actions, spawned processes, and opened streams explain Baqylau itself. They remain best-effort and isolated in audit.db.

errors · state_files · spawns · streams

Runtime flows

Writes and forensic reads

A. Actual operation → main.db
HarnessRawEventSource.read(position) │ ▼ RawEventRepository.record(raw_events) ▼ main.db.raw_events │ unverdicted(500) ▼ Interpreter._translate_one(raw_event) │ Translator.translate(raw_event) ▼ CanonicalEventRepository.record_translation(...) ├─ INSERT interpretations ├─ INSERT/DEDUPE canonical_events └─ INSERT interpretation_events one transaction; failures propagate
B. Debug observation → audit.db
Service / API / interpreter failure │ AuditRecorder.error/state_file/spawn/stream ▼ AuditWriteRepository ▼ SqliteAuditWriteRepository │ if BAQYLAU_AUDIT != 0 │ storage errors are swallowed ▼ audit.db ├─ errors ├─ state_files ├─ spawns └─ streams
C. Raw event audit read
bin/baqylau-raw-events-audit.py raw|session <id> ▼ app.raw_events_audit_cli.main(...) ▼ SqliteRawEventAuditRepository(read_only(main.db)) ├─ audit(raw_event_id) └─ audits_for_session(session_id) ├─ raw_events ├─ interpretations ├─ interpretation_events └─ canonical_events ▼ harness.models.RawEventAudit └─ interpretation: InterpretationAudit | None ▼ JSON with raw_event + nested interpretation/events

Database ownership and migration

DatabaseContentsSemantics
main.dbraw_events, interpretations, interpretation_events, canonical_events, projectionsAuthoritative application operations. Atomic writes; failures propagate.
audit.dberrors, state_files, spawns, streamsDebug-only. Optional, best-effort, and unable to break application behavior.

Schema migration: version 1 → 2

ALTER TABLE translation_records RENAME TO interpretations
ALTER TABLE canonical_provenance RENAME TO interpretation_events

No columns, keys, foreign keys, or rows change. audit.db is not migrated because its schema and ownership are unchanged.

Claude Code audit skill review

The skill keeps its name and follows the new schema

.claude/skills/audit-debug/SKILL.md now teaches the two-database boundary and uses interpretations, interpretation_events, and the raw-events audit CLI.

  • main.db first: establish the actual operation and its interpretation.
  • audit.db second: add best-effort machinery context.
  • Writer topology: the daemon owns main writes; audit writes may also come from short-lived processes.
  • Exactly two stores: stale locks.db guidance is removed.

Boundary rule

main.db

If the application needs it to ingest, interpret, project, resume, or render truth, it is an actual operation and belongs here.

audit.db

If it exists only to explain Baqylau's behavior or a failure, it is debug audit data and belongs here.
